## 작업 한 줄 요약

동료(yrkim)가 올린 PR #5585(어드민 신규 메뉴 "평가 결과 검색" — 조건 그룹으로 마감된 평가 결과를 조회하는 API 5개, 인덱스 마이그레이션 2건)를 `review-ppback` 스킬로 리뷰했다. 처음 리뷰에서 **등급 우선순위가 다른 화면 4곳과 어긋나는 것**(가장 큰 지적), `ORDER BY` 컬럼 모호성, 마이그레이션 base class 버전, 조건 모달에 결과 없는 프로세스 노출을 찾았다. 이후 세 레포 브랜치를 맞추고 작성자가 제공한 시드 스크립트로 데이터를 넣어 `/web-e2e`로 화면까지 검증했다(10개 케이스 중 8건 확인). 마지막으로 **작성자가 내 성능 지적을 반영한 커밋에서 안전 범위 필터가 사라지는 회귀를 발견**해, 재현·원인·수정안까지 정리해 인라인으로 올렸고 작성자가 A안으로 고쳤다(`ff85a8c98`). 그 수정과 함께 추가된 회귀 테스트를 뮤테이션 테스트로 검증해 "정확히 그 example 하나만 실패"까지 확인했다.

## 이번 작업에서 처음 배운 개념

- **`ActiveRecord::Relation#merge` 는 같은 컬럼의 술어를 `AND` 하지 않고 덮어쓴다** — 이번 세션의 가장 큰 배움이다. `base.merge(condition_scope)` 로 안전 범위 relation에 사용자 조건을 붙였는데, 양쪽에 `appraisal_id` 술어가 다 있어서 `base` 의 `appraisal_id IN (마감 평가 서브쿼리)` 가 조건의 `appraisal_id = <클라이언트 값>` 으로 **교체**됐다. `.where(a).where(b)` 체이닝은 누적(AND)인데 `merge` 는 인자로 들어온 쪽이 이긴다 — Rails 내부적으로 `WhereClause#merge` 가 `predicates_unreferenced_by(other)` 로 "상대가 참조하는 컬럼의 equality 술어"를 자기 쪽에서 **빼고** 합치기 때문이다. 실제 SQL을 뽑아 대조한 게 결정적이었다:

  ```sql
  -- merge (버그)                          -- where 체이닝 (정상)
  WHERE workspace_id = 2                   WHERE workspace_id = 2
    AND appraisal_id = 4                     AND appraisal_id IN (SELECT ... status IN (2,3) ...)
                                             AND appraisal_id = 4
  ```

  무서운 건 **`workspace_id = 2` 는 살아남았다**는 점이다. 조건 쪽에 `workspace_id` 술어가 없어 겹치지 않았기 때문. 테넌트 격리가 지켜진 게 설계가 아니라 **우연**이었고, 그 우연 때문에 사고 범위가 좁아 보여 더 찾기 어려웠다. → [레슨 60](../lessons/0060-relation-merge-overwrites-predicates.html)
- **서브쿼리는 자기만의 `WHERE` 를 갖는 독립 스코프다 — 바깥 필터가 적용되지 않는다** — 레슨 7에서 서브쿼리를 "쿼리 안의 쿼리"로 배웠는데 그때는 모양만 봤다. 이번 쿼리는 두 갈래로 돌았다: (가) 표시할 행을 고르는 술어는 **바깥 `WHERE` 에 `AND` 로 얹히고**, (나) 대상자를 판정하는 술어는 `appraisee_user_id IN (SELECT ...)` 로 **따로 실행된다**. 그래서 조건 술어에서 안전 범위를 걷어내는 같은 리팩터링이 (가)에서는 순수한 중복 제거(정당한 개선)이고 (나)에서는 방어 제거(회귀)가 된다. **판단 기준은 "이 술어가 어디서 실행되는가" 하나**다. 성능 개선으로 조건을 걷어낼 때 이걸 먼저 물어야 한다.
- **성능 수치가 개선의 증거가 아니라 결함의 증상일 수 있다** — 작성자가 측정한 "서브쿼리 6회 → 2회"는 사실 마감 필터가 사라진 결과였다. 같은 조건으로 세 상태를 실측해서 이 관계를 드러냈다: 원래 6회(정확하나 중복) → 개선 후 2회(빠르나 필터 유실) → 최종 4회(정확하고 중복도 줄어듦). **"늘어난 2회가 곧 안전 범위 방어"** 라는 식으로 숫자에 의미를 붙여야 리뷰에서 설득이 된다. 숫자만 보면 4회는 퇴보처럼 보인다.
- **프론트가 막아주는 것과 서버 계약이 지켜지는 것은 다르다** — 회귀를 찾고 나서 "UI로 재현 가능한가"를 따로 확인했다. 조건 모달은 마감 평가만 내려주고, 저장된 조건을 복원할 때도 프론트가 필터 API 응답과 대조해 **조건 단위로** 걸러낸다(잘 만들어진 가드다). 그런데 두 군데가 샜다 — (1) 평가 목록 캐시가 `staleTime: Infinity` 이고 검증이 `useRef` 로 마운트당 1회라, 조건을 세팅한 채 페이지에 머무는 동안 평가가 재개되면 이후 조회마다 낡은 id가 그대로 전송된다. (2) 저장된 조건이 `useState` 초기값으로 바로 들어가는데 조회 버튼은 조건 유무만 보므로, 검증이 끝나기 전에 누를 수 있다. 결론은 "재현 가능하지만 확률은 낮음" → 심각도를 **높음 → 중간으로 스스로 내렸다.** 다만 서버 계약이 프론트 코드 한 곳에 의존하게 된 것 자체가 문제라는 점은 유지했다.
- **등급 조정(상대 배분)은 등급 조정 프로세스만의 것이 아니다** — 첫 리뷰의 가장 큰 지적이었다. PR은 `CASE WHEN appraisal_process_name = 'grade_adjust' THEN grade_adjustment_rank_id ELSE rank_id END` 로 갈랐는데, `V1::Appraisals::GradeAdjusts` 와 `CreateBulkGradeAdjustmentsWorker` 가 대상 영역을 `appraisal_processes.name IN ('manager','result_confirm') AND is_grade_adjust = true` **또는** `name = 'grade_adjust'` 로 잡는다. 즉 **상위자 평가 프로세스 행에도 조정 등급이 붙고**, 그 행은 `check_grade_adjust` 가 true라 원 등급까지 함께 채워져 두 컬럼이 다 남는다. 로컬 실데이터로 확인했다 — 조정 등급이 있는 영역행 2건이 전부 `manager` 이고, 그중 1건(행 68)은 원 등급 `B` / 조정 후 `A` 로 값이 달랐다. 반면 기존 화면 4곳(대시보드 표·차트, 결과 공개, 탤런트 세션)은 전부 `grade_adjustment_rank || rank` 로 조정 후를 보여준다. → 이 화면만 조정 **전** 등급으로 판정하게 될 자리였다.
- **`IN` 서브쿼리에 `ORDER BY` 가 따라붙는다** — `finished_appraisals` 가 `workspace.order_appraisals`(정렬이 걸린 association)에서 출발해서, `where(appraisal_id: finished_appraisals.select(:id))` 로 쓸 때 서브쿼리에 의미 없는 `ORDER BY` 가 실렸다. 조건 모달 목록은 정렬이 필요하고 서브쿼리는 아니므로 `finished_appraisal_ids`(`workspace.appraisals` 기반, 정렬 없음)를 따로 만드는 게 정석이다.
- **`ORDER BY` 의 이름 해석은 SELECT 목록을 먼저 본다** — 정렬 상수가 `appraisee_user_id, appraisal_id, ..., id` 처럼 컬럼명만 나열돼 있었는데, 조인한 세 테이블에 `id` 와 `appraisal_id`, `appraisal_group_id` 가 전부 있어 모호했다. 그런데 실행하면 동작했다. 실측으로 갈렸다 — **전체 컬럼(`table.*`)을 SELECT 하면 MySQL이 select list에서 이름을 먼저 해석해 통과하지만, `pluck(:id)` 처럼 select list를 좁히는 순간 `Column 'appraisal_id' in order clause is ambiguous` 로 500이 난다.** 지금은 안 터지지만 누가 `.select` 를 붙이면 조용히 깨지는 자리였다.
- **뮤테이션 테스트를 남의 PR 리뷰에 쓰는 법** — 레슨 55(회귀 스펙의 판별력)를 내 코드가 아니라 **리뷰 대상 코드**에 적용했다. 작성자가 회귀 테스트를 추가했다고 했을 때, 그 말을 믿는 대신 수정 코드를 `merge` 로 되돌려 돌려봤다. `68 examples, 1 failure` — 정확히 그 example 하나만 실패했다. "테스트를 추가했다"보다 "이 테스트가 이 버그를 잡고, 다른 건 건드리지 않는다"가 훨씬 강한 근거다. 여러 개가 같이 실패하면 그 테스트가 무엇을 지키는지 불분명하다는 뜻이기도 하다.

## 작업하면서 막혔던 것과 해결 방법

- **`bias_adjust` 를 문제로 잘못 지목했다가 되돌렸다.** 조건 모달에 "결과 행이 없는 프로세스"가 노출된다고 지적하면서 `element_setting`(문항 설정)과 `bias_adjust`(평균 편차 조정)를 같이 묶었다. 근거를 파보니 `bias_adjust` 는 **틀렸다** — `StartBiasAdjustProcessWorker:40` 이 `CreateReadOnlyResponsesService` 를 직접 호출해 실제 점수 행을 만든다. 프론트 양식 모달의 "평균 편차 조정은 평가자를 지정하지 않는 프로세스" 문구를 "평가자가 없다"로 잘못 읽은 게 원인이었다(관리자가 수동 지정하지 않는다는 뜻이고, 평가자는 자동 생성된다 — `standardized_score_service.rb:10` 의 `bias_adjust_process.appraisers`). `result_confirm` 도 로컬에 영역행 17건이 있어 정상이었다. **지적 범위를 `element_setting` 하나로 좁혀 다시 보고했다.** 교훈: "행이 없다"를 주장할 때 프로세스 이름별 행 수를 먼저 세야 했다. 실제로 세보니 로컬에 `element_setting`·`bias_adjust` 프로세스가 **0개**라 애초에 재현도 불가능한 상태였고, 그걸 "코드 근거만 있음"으로 명시해야 했다.
- **차수 불일치 지적이 무근거였음을 프론트 코드로 확인했다.** 조건 모달은 `id`·`name` 만 받고 결과 표는 서버 `process_index` 를 쓰니 두 화면의 "1차 상위자 평가" 라벨이 어긋날 수 있다고 봤다. 서버 규칙이 직관과 달랐기 때문이다 — `find_process_index` 가 `manager` 와 `grade_adjust` 를 **한 카운터로 합쳐** 센다(로컬 실측 `{["manager",1]=>8, ["manager",2]=>3, ["grade_adjust",2]=>2}`). 프론트가 이걸 재현할 이유가 없어 보였다. 그런데 `talenx-admin` 을 열어보니 `ORDINAL_PROCESSES = ["manager", "grade_adjust"]` 로 **정확히 같은 공유 카운터**를 쓰는 헬퍼(`makeIndicesOfOrdinalProcesses`)가 이미 있었고, 평가 그룹 설정·양식 모달과 공용이었다. `/web-e2e` 로 화면에서도 조건 모달·결과 표·양식 모달 세 곳이 전부 `1차 상위자 평가 → 2차 등급 조정` 으로 일치하는 것을 확인했다. **지적을 철회했다.** 교훈: 프론트 계약이 걸린 지적은 프론트 레포를 열어 확인하기 전엔 올리지 말 것(이건 이미 [피드백 메모](../NOTES.md)에 있던 항목인데 또 걸렸다).
- **8001 포트를 서비스하는 체크아웃이 PR 브랜치가 아니었다.** `/web-e2e` 를 시작하려는데 `talenx-admin` 체크아웃이 두 개(`~/Desktop/talenx-admin`, `~/Desktop/Eggplant/Eggplant-admin`)였고, 8001을 띄우고 있던 건 후자에 다른 브랜치였다. PR 브랜치가 올라간 쪽에는 `node_modules` 가 없었다. dev 서버를 임의로 죽이거나 `yarn install` 을 몇 분 돌리는 건 둘 다 사용자 환경을 건드리는 일이라 **선택지를 정리해 물어보고 진행**했다. 결국 8001을 서비스하던 clean 체크아웃에서 브랜치만 갈아타고(vite HMR이 새 라우트를 잡아줬다) 검증 후 원래 브랜치로 복원했다. `lsof -a -p <pid> -d cwd -Fn` 으로 포트 → PID → 작업 디렉터리를 역추적하는 방법을 처음 썼다.
- **결정적 케이스가 시드 데이터에 없어서 한 행을 직접 보강했다.** 등급 우선순위 수정이 화면까지 작동하는지 보려면 **`manager` 프로세스 행에 두 등급 컬럼이 다 채워진 행**이 필요했다. 시드는 `grade_adjust` 행에만 조정 등급을 넣어서, 수정 전·후 코드가 같은 결과를 내는 케이스만 있었다(둘 다 조정 등급을 씀). 로컬 실데이터의 행 68이 정확히 그 형태였는데 그 평가가 `ongoing` 이라 이 화면으로는 도달 불가였다. 그래서 시드가 만든 `manager` 행 하나(행 92)에 조정 등급 `D` 를 넣어 `조정 전 S / 조정 후 D` 를 만들고, 같은 조합에 원래 `D` 인 행이 3개 있음을 확인해 **"새 코드 4건 / 옛 코드 3건"** 으로 갈리는 판별 케이스를 구성했다. 화면에서 4건이 나오고 행 92의 `rank_id` 가 조정 후 값으로 오는 것까지 확인한 뒤 원복했다. 시드 태그(`[결과검색]`) 안의 데이터라 `--clean` 으로 되돌아가는 범위인 것도 먼저 확인했다.
- **회귀를 찾고 나서 심각도를 스스로 내렸다.** 처음엔 "높음"으로 적었다. 그런데 UI 경로를 끝까지 따라가 보니 프론트에 제대로 된 가드가 있었고, 새는 경로는 평가 재개·삭제라는 상태 변화가 끼어야 했다. 그리고 표시 행은 바깥 마감 필터에 걸려 **같은 그룹에 마감 조건이 함께 있을 때만** 결과가 보였다. 그래서 "실사용 확률 낮음 / 그래도 서버 계약 위반이고 수정 2줄"로 근거를 나눠 적고 **중간**으로 조정했다. 리뷰에서 심각도를 부풀리지 않는 것도 신뢰의 문제라고 봤다.
- **대안을 제시했다가 작성자 판단으로 빠진 것.** 수정안으로 (A) 서브쿼리에 안전 범위 복원, (B) 경계에서 조건의 `appraisal_id` 를 검증해 400 을 주는 방법 두 가지를 냈다. B가 성능 6→2를 유지해서 더 깔끔해 보였는데, 작성자가 "지금은 조용히 0건인데 400이 되면 동작이 바뀌고, 지적하신 프론트 유실 경로에서 화면이 조회 자체를 못 하게 될 수 있다"고 답했다. **내가 찾은 프론트 결함이 내 대안을 반박하는 근거가 된 셈이다.** A로 가고 계약 문제는 별도로 다루자는 판단이 맞다고 봤다.

## 다음에 더 공부하고 싶은 것

- `merge` 의 덮어쓰기가 정확히 어떤 Arel 노드에 적용되는지 — `WhereClause#merge` 의 `predicates_unreferenced_by` 가 `equality_node?` 로 걸러내는데, `IN (subquery)` 같은 비-equality 노드는 어떻게 취급되는지 소스를 직접 읽어보기. 이번엔 "실측으로 사라진다"까지만 확인했다.
- `rewhere` / `and` / `or` 를 각각 언제 쓰는지 — `merge` 가 덮어쓰기라면 명시적으로 덮어쓰고 싶을 때 쓰는 `rewhere` 와의 차이, 그리고 `or` 가 요구하는 "구조 호환성"이 무엇을 검사하는지. 이번 PR의 `matched_appraisee_user_ids` 가 `.or` 를 쓰는데 왜 안전한지는 "같은 `base` 에서 나왔으니 호환"으로만 넘어갔다.
- 프론트 캐시 무효화 패턴 — `staleTime: Infinity` + `useRef` 1회 검증 조합이 만든 유실 경로를 찾았는데, react-query에서 "페이지 체류 중 서버 상태가 바뀌는 경우"를 어떻게 다루는 게 표준인지(refetchOnWindowFocus, invalidateQueries 타이밍) 모른다. FE 출신인데 react-query는 안 써봤다.
- 조건 조립 쿼리 객체의 테스트 전략 — 이번 회귀는 request spec으로 잡혔지만, `AppraisalResultsQuery` 단위로 "생성된 SQL에 특정 술어가 남아 있는가"를 검증하는 스펙이 있으면 더 빨리 잡혔을 것 같다. SQL 문자열을 어서션하는 게 좋은 습관인지 아닌지 판단이 안 선다.
