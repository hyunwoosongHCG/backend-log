# 직무 역량 양식 영역 응답 초기화 API 구현 + 문항 설정 잠금 판정 서버 이관

> 날짜: 2026-09-11
> PR: [ppback #5606](https://github.com/hcgtheplus/ppback/pull/5606)
> 선행: [2026-09-10 직무직군 문항 설정 데이터 재설정 정책 기획](2026-09-10-job-template-element-setting-reset-policy.md)

## 작업 한 줄 요약

어제 설계한 정책(기본값 = 전 프로세스 응답 폐기, 옵션 = 문항 설정 제출 내용 초기화)을 실제 API로 구현했다. 구현 중 문항 설정 재진입 잠금이 응답이 아니라 **평가자 상태**로 판정된다는 걸 확인해 잠금 판정을 서버로 옮기는 작업이 함께 들어갔고, 초안에서 평가자 상태만 되돌렸다가 다른 영역 응답이 조용히 사라지는 버그를 내고 고쳤다. 후속으로 "직무가 바뀌면 양식을 갱신하는" 진짜 재설정까지 확장하는 3축 스냅샷 설계 PRD를 따로 작성했다.

## 이 작업에서 처음 배운 개념

### 불변식이 선언 없이 조회 조건으로만 존재할 때 → [레슨 61](../lessons/0061-invariant-that-lives-only-in-queries.html)

이 도메인은 "응답 행의 `status`는 그 응답을 쓴 평가자의 `status`와 같다"를 전제한다. 그런데 이 전제가 모델에도 스키마에도 주석에도 없고, **`where(status: appraiser.status)`라는 조회 조건 9곳에 흩어져** 있을 뿐이다.

그래서 평가자만 `closed`로 내리는 코드를 짰더니 다른 영역에 남아 있던 응답이 화면에서 사라졌다. 조회가 전부 저 조건으로 거르니 `tempsaved` 응답은 `closed` 평가자에게 안 보인다. 더 나쁜 건 그 상태로 재제출하면 `completed_responses.discard_all`이 화면에 없던 그 행을 지운다는 것 — 사용자는 사라진 줄도 모른다.

기존 코드에 `UpdateAppraiserStatusService#dup_and_update_status_res`라는 관례가 있었다. 상태를 바꿀 때 응답을 새 상태로 **복제**하고 원본은 이력으로 남긴다. 처음엔 왜 복제까지 하나 싶었는데, 그게 바로 이 불변식을 지키는 장치였다.

### fail-open이냐 fail-closed냐 — 틀릴 때 어느 방향으로 틀리는가

잠금 판정에 필요한 옵션을 안 넘기면 뒤 순번 프로세스 목록이 빈 배열이 되어 **"잠기지 않음"으로 판정**됐다. 잠금 기능이 열리는 쪽으로 틀린다.

호출처가 하나뿐이라 당장은 안전했지만, 방어 코드는 "누락됐을 때 어느 방향으로 틀리는가"를 먼저 정해야 한다. `ArgumentError`로 바꿨다.

### 같은 판정이 프론트와 백엔드에 따로 살면 값이 갈린다

문항 설정 잠금을 프론트(`lib/appraisal/elementSetting.ts`)와 백엔드가 각자 판정하고 있었는데 기준이 달랐다.

| | 뒤 차수 문항 설정 | 뒤 순번 일반 프로세스 |
|---|---|---|
| 프론트 | 완료 + 임시저장 | 완료 + 임시저장 → 잠금 |
| 백엔드 | **완료만** | **판정 안 함** |

화면에서 막은 요청이 서버에서는 통과하는 상태였다. 상수(`RESPONDED_STATUSES`)를 모델로 올려 값을 맞추고, 판정 자체를 서버로 옮겨 결과만 내려주는 방향으로 정리했다. 프론트가 남의 응답을 볼 수 없어서(공개 범위) 영역 단위 판정을 직접 할 수 없다는 제약도 같은 결론을 가리켰다.

### live 참조 vs 스냅샷 — 평가 도메인의 설계 선택

```ruby
# appraisal_appraisee.rb:101
has_many :job_category_users, through: :user
```

대상자의 직무가 평가에 스냅샷되지 않고 **유저를 타고 간다.** 그래서 `CreateScopeElementService`는 언제 불려도 현재 직무 기준으로 양식을 가져온다(재생성만 하면 직무 변경이 자동 반영된다는 뜻이기도 하다).

대신 "평가 시작 시점에 이 직무였던 대상자"를 조회할 수 없다. 직무가 이미 바뀐 사람은 빠져나가서, 정작 갱신이 필요한 사람이 대상에서 누락된다. 조직도는 `TeamSnapshot`으로 스냅샷을 갖는데 직무는 없는 비대칭이다. 후속 PRD에서 이 스냅샷을 제안한 근거.

### 특성화 테스트(characterization test)가 리팩터링의 선행 조건

소프트 리셋은 운영 평가에 쓰이는데 스펙이 얇다. 현재 동작이 어디에도 고정돼 있지 않으니 리팩터링하면 뭐가 바뀌었는지 알 수 없다. 후속 PRD의 롤아웃 0단계로 못 박았다 — 리팩터링 여부와 무관하게 값어치가 있는 단계다.

## 기존에 알던 것의 새 변주

### `let_it_be` 오염 — 이번엔 속성이 아니라 연관 캐시

[레슨 48](../lessons/0048-let-it-be-shared-object-pollution.html)·[59](../lessons/0059-let-it-be-stale-attribute-skips-update-sql.html)가 다루는 건 인메모리 **속성** 오염인데, 이번엔 **association cache**였다.

`let_it_be`로 공유한 프로세스 객체의 `appraisers` 연관이 앞 describe에서 로드된 채 남아, 다음 describe의 판정에 섞였다. `--order defined`와 random에서 결과가 달랐다. 운영에서는 부모 엔티티가 매번 새로 로드하므로 스펙만 비현실적이었던 것 — 스펙이 운영과 다른 방식으로 객체를 얻고 있으면 그 차이가 버그로 나타난다.

고친 방법은 `represent` 헬퍼에서 매번 DB에서 다시 로드하기. 순서 3회(defined·random×2) 돌려 안정성 확인.

### `after_create` 콜백이 만드는 암묵적 데이터가 픽스처를 오염

`AppraisalSection`의 `after_create :create_appraisal_joins`가 그룹의 모든 프로세스에 join을 자동 생성한다. 그걸 모르고 스펙에서 join을 또 만들어 `section_ids: [1, 1]` 중복이 났다.

팩토리로 레코드를 만들 때 콜백이 뭘 더 만드는지 확인하지 않으면, 내가 만든 픽스처가 내가 의도한 모양이 아니다.

### `update_all` vs `update!` — 같은 서비스에서 갈리면 리팩터링 폭탄

한 서비스에서 같은 컬럼을 한쪽은 `update_all`(콜백·검증 스킵), 다른 쪽은 `update!`로 바꾸고 있었다. 지금은 무해하지만 콜백이 추가되면 한쪽만 탄다.

`update!`로 통일하면서 **기존 데이터가 검증을 통과하는지 먼저 dry-run**으로 확인했다(워크스페이스 평가자 262명, 실패 0). `update_all`은 검증을 안 타므로, 전환은 "기존에 저장 가능했던 행이 이제 저장 불가가 될 수 있다"는 리스크를 동반한다. 로컬에서 통과했다고 운영도 통과한다는 뜻은 아니라서 PR에 한계로 적었다.

### Grape `Boolean`이 문자열을 강제 변환한다

`reset_element_setting_submission: "yes"`를 보냈더니 `true`로 변환돼 파괴적인 하위 옵션이 켜졌다. 프론트는 axiauth를 타서 실제 boolean을 보내니 위험도는 낮지만, 오타 하나로 문항 설정 제출 내용이 삭제될 수 있는 자리다.

### `Grape::Entity`의 `options`를 preload 전달 용도로

로드맵에 있는 건 `options` 기반 **조건부 필터링**인데, 이번엔 부모 엔티티가 이미 로드한 프로세스 컬렉션을 `all_processes`로 넘겨 **N+1을 막는** 데 썼다. 엔티티 안에서 다시 조회하면 프로세스 수만큼 질의가 늘어난다.

## 막혔던 것과 해결 방법

**로컬 Ruby 버전이 없어 검증을 못 한다고 판단했던 것.** `.ruby-version`이 3.4.10인데 로컬엔 3.4.7까지만 있어서 `bundle exec rspec`이 `Bundler::GemNotFound`로 죽었다. 초반에 구문 검사만 하고 "검증 못 함"으로 보고했는데, **docker 컨테이너 안에는 젬이 다 깔려 있었다.** `docker compose exec -T -e RAILS_ENV=test app bundle exec rspec`으로 그냥 돌아갔다. 호스트에서 막히면 컨테이너를 먼저 떠올릴 것.

**평가 기간이 지난 그룹은 응답 폼이 읽기 전용.** E2E 픽스처를 만들려는데 버튼과 입력이 전부 disabled였다. 복제한 평가의 프로세스 기간이 2026-05-21에 끝나 있었다. `PUT .../groups/:group_id/datetime`으로 기간을 연장해서 풀었다(rails runner로 DB 직접 수정하지 않고 실제 API 사용).

**스펙이 통과했는데 실제로는 순서 운이었던 것.** 처음 엔티티 스펙 5건이 통과해서 "검증 완료"로 보고했는데, 리뷰 과정에서 describe를 하나 추가했더니 3건이 깨졌다. 랜덤 순서라 운 좋게 통과했던 것. 연관 캐시 누수(위)가 원인이었다. **한 번 초록색이 나왔다고 스펙이 옳다는 뜻이 아니다** — 순서를 바꿔 돌려봐야 한다.

**리뷰에서 내 문서의 모순을 잡힌 것.** PRD에서 "엔드포인트 통합하지 말자"고 써놓고 다른 섹션에서는 "상수를 없애자"고 썼다. 상수를 없애면 소프트 리셋이 직무 영역을 먹게 되니 사실상 통합인데, "스위치를 확장 가능하게"와 "소프트 리셋이 직무를 처리하게"를 뭉뚱그린 탓이었다. 사용자 지적으로 정정했다.

## 다음에 더 공부할 것

- 선언되지 않은 도메인 불변식을 찾아내는 방법 — 이번엔 "같은 조건이 여러 조회에 반복된다"가 신호였는데, 다른 신호는 뭐가 있을까
- 판정 로직을 서버로 모을 때 프론트에 무엇까지 내려줄 것인가 — boolean만이면 안내 문구를 못 만들고, 사유까지 내리면 결국 같은 정보를 다시 노출하게 된다
- `Data.define` 값 객체로 서비스 인자를 묶는 패턴 — 지금 재설정 서비스들이 인자 3~7개에 순서도 제각각이라 호출부에서 실수가 안 드러난다
