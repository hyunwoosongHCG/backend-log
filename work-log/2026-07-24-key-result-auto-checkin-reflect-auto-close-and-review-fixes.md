# 핵심성과 체크인 자동 반영 기능 — LOW 리뷰 반영 + 반영 상위 목표 자동 마감 추가

> 이어지는 작업: [2026-07-24 API 노출 작업](2026-07-24-key-result-auto-checkin-reflect-api-exposure-review.md)

## 작업 한 줄 요약

지난 코드 리뷰에서 남겨둔 LOW 항목 2건(엔티티 desc 누락, `.includes` 해시 스타일 불일치)을 정리하고, 체크인 승인 시 자동 반영으로 진행률이 100%가 된 "상위" 목표는 자동 마감 대상에서 빠지는 갭을 찾아 고쳤다. 이 과정에서 트랜잭션을 얼마나 길게/어떻게 나눠야 하는지를 놓고 여러 번 설계를 뒤집었다.

## 이 작업에서 처음 배운 개념

- [x] 중첩된 `ActiveRecord::Base.transaction do end`은 `requires_new: true` 없이는 진짜 커밋 경계가 아니다 — 이미 열려있는 트랜잭션이 있으면 그냥 거기 합류(join)할 뿐, 별도로 BEGIN/COMMIT하지 않는다. → [레슨 45](../lessons/0045-nested-transaction-and-requires-new.html)
- [x] `requires_new: true`는 MySQL의 진짜 SAVEPOINT를 만들어서 "부분 실패 격리"(한 항목의 실패가 다른 항목이나 바깥 트랜잭션 전체를 롤백시키지 않게)는 되지만, **락을 조기에 풀어주는 효과는 없다** — 바깥 트랜잭션이 끝날 때까지 락은 계속 물려 있는다. → [레슨 45](../lessons/0045-nested-transaction-and-requires-new.html)
- [x] `transaction do end` 블록 안에서 예외가 나면, 그 블록 뒤에 있는 코드는 별도의 `rescue`나 플래그 체크 없이도 자동으로 실행되지 않는다 — Rails가 ROLLBACK 후 예외를 다시 던지고(re-raise), Ruby의 순차 실행 규칙상 그 뒤 코드는 그냥 스킵된다. 실제로 `rails runner`로 재현해서 확인했다.
- [x] `Rails/FindEach` 코팝 — `find_each`는 큰 테이블을 배치로 순회할 때 쓰는 것이라, 계층 깊이만큼의 소수(한 자릿수) 레코드에는 안 맞고, 트랜잭션 안에서 쓰는 것도 Rails가 권장하지 않는다. `.each`가 맞는 상황도 있다는 걸 코드 리뷰에서 배웠다.

## 작업하면서 막혔던 것

- **"트랜잭션이 너무 길어지지 않을까"라는 지적을 받고 설계를 두 번 뒤집었다.** 처음엔 반영(reflect) 재귀 안에서 바로 자동 마감 서비스를 호출하려 했는데, 이러면 체인 깊이만큼 하나의 트랜잭션이 계속 길어진다는 지적을 받았다. 그래서 "반영 트랜잭션이 끝난 뒤 별도로 자동 마감을 처리"하는 구조로 바꿨는데, 실제 호출부 6곳 중 4곳(벌크 승인 경로)은 이미 바깥에 트랜잭션이 열려있어서 이 분리가 실제로는 락 시간을 못 줄인다는 걸 뒤늦게 발견했다. 결국 "락 시간 단축"은 2곳에서만 되고, 나머지 4곳은 `requires_new: true`로 "부분 실패 격리"만 얻는 것으로 정리했다.
- **재귀 함수에 누적 상태(Set) 2개를 인자로 계속 실어 나르다 보니 코드가 "3중 for문 같다"는 지적을 받았다.** 이 서비스는 `.call` 한 번에 인스턴스 하나만 쓰는 패턴이라, 누적 상태를 인자로 넘기는 대신 인스턴스 변수로 빼서 재귀 함수 시그니처를 원래 코드와 거의 같은 모양으로 되돌렸다. 같은 문제(반영 대상 상위 목표 id 중복 처리)를 해결하면서도 코드가 더 단순해졌다.
- **한 상위 목표에 서로 다른 두 하위 핵심성과가 동시에 반영되는 경우, 자동 마감 서비스가 두 번 호출될 뻔했다.** 순환 참조 가드(`visited_key_result_ids`)는 핵심성과 id 기준이라 이 케이스(같은 목표, 다른 핵심성과)를 못 잡는데, 자동 마감 로직을 목표 id 기준 `Set`으로 모았다가 마지막에 한 번씩만 처리하는 구조로 바꾸면서 자연스럽게 해결됐다.
