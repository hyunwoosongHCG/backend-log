# 핵심성과 자동 반영 — 1/n 분할 전환

> 날짜: 2026-08-06
> PR: ppback `feature/key-result-auto-checkin-reflect` (커밋 `157b3c06b`, `0dc18149a`, `62deb09c5`, `1caaa049b`, `a3c8339b3`)

## 작업 한 줄 요약

하위 목표 체크인이 상위 핵심성과에 반영될 때 **하위 하나의 값으로 덮어쓰던 것**을,
**연계된 하위 전체의 평균으로 매번 다시 계산**하도록 바꿨다. 그 과정에서 이미 만들어둔
"모호한 배치를 400으로 차단하는" 밸리데이션을 전량 폐기했다.

## 이 작업에서 처음 배운 개념

- [x] [연관관계 스코프의 비대칭](../concepts/association-scope-asymmetry.md) — 연관관계가 조인 대상 테이블의
  상태를 검사하지 않아, 같은 정책을 표현한다고 믿었던 두 연관관계가 서로 다르게 동작하는 문제
  → [레슨 51](../lessons/0051-association-scope-asymmetry.html)
- [x] 멱등성(Idempotency)의 **설계 도구로서의** 쓰임 — 개념 자체는 [레슨 31](../lessons/0031-atomicity-vs-idempotency.html)에서
  이미 배웠지만, 그때는 "장애를 분류하는 프레임"이었다. 이번엔 반대로 **멱등하게 설계하면 없앨 수 있는 문제**를
  먼저 알아보고 구조를 바꾸는 쪽으로 썼다. 아래 "막혔던 것" 참고.

## 작업하면서 막혔던 것

### 1. 밸리데이션을 다 짜고 나서 방향이 틀렸다는 걸 알았다

원래 문제는 이거였다. 상위 핵심성과 하나에 하위가 여럿 연계돼 있고 그 하위들이 한 배치
(일괄 승인 / 어드민 일괄 체크인)에 함께 들어오면, **마지막에 처리된 하위의 값이 이긴다.**
그런데 두 벌크 워커는 ID 집합으로 재조회하고 `ORDER BY`가 없고 `Objective`에 `default_scope`도
없어서, 호출부가 순서를 통제할 방법이 없다. 게다가 반영은 최대 5단계까지 재귀로 올라가서
비결정성이 위로 증폭된다.

처음 접근은 **그런 배치를 탐지해서 400으로 막는 것**이었다. `AmbiguousAutoReflectBatch`라는
탐지 서비스를 만들고, 컨트롤러 5곳에 분기를 넣고, i18n 7개 언어를 채우고, 스펙까지 다 짰다.

그런데 팀에서 "일괄 처리할 때 너무 많이 막힐 것 같다"는 우려가 나왔고, 프론트에서도
조부모 케이스(부모A·부모B가 같은 조부모 KR에 물린 구조)는 사전 검증이 불가능하다는 답이 왔다.

여기서 배운 게 있다. **모호함을 탐지해서 막는 것과, 모호함이 발생하지 않게 만드는 것은 다르다.**
순서가 결과를 바꾸는 이유는 값을 *절대 대입*하기 때문이었다. 대입 대신 **연계된 하위 전체에서
매번 다시 계산**하면 순서가 무엇이든 같은 값으로 수렴한다. 차단할 대상 자체가 사라진다.

```ruby
# 전: 하위 하나의 진행률을 상위에 그대로 대입 → 마지막 처리자가 이김
BigDecimal(child_progress.to_s).div(100, 8).mult(key_result.target, 8).round

# 후: 연계된 하위 전체의 가중 평균에서 매번 다시 계산
progress_sum.div(weight_sum, 8).div(100, 8).mult(key_result.target, 8).round
```

**누적(델타)이 아니라 재계산인 것이 핵심**이다. 하위 하나의 기여분을 더하는 방식이었다면
Sidekiq 재시도로 같은 작업이 두 번 실행될 때 값이 중복 가산된다. 재계산은 몇 번을 실행해도
같은 상태로 수렴한다 — 이게 멱등성이다.

부수 효과도 있었다. 재귀에서 `child_progress`를 인자로 들고 올라갈 필요가 없어졌다.
각 단계가 자기 하위를 직접 읽으므로, "위로 무슨 진행률을 넘길 것인가"라는 고민 자체가 사라졌다.

### 2. 같은 정책인 줄 알았던 두 연관관계가 달랐다

분모(N)를 구하려고 기존 연관관계를 쓰려다 발견했다.

| | 스코프 | archived 목표 소속 |
|---|---|---|
| `child_objectives` | `stage: ACTIVE + CLOSED` + `kept` | 제외 |
| `child_key_results` | `active: true` **만** | **포함** |

`child_key_results`에는 소유 목표의 상태 조건이 없다. 그런데 목표를 삭제(archive)하는
`archive_and_create_history`는 `stage`만 바꾸고 핵심성과의 `active`는 건드리지 않는다.
그대로 쓰면 **삭제된 목표의 핵심성과가 분모에 들어간다.**

나중에 알았는데, 프론트 엔티티(`ShowEntity`)가 이미 이 조건을 Ruby `select`로 덧대서
화면단에서 보정하고 있었다. 즉 알려진 문제였고 계산 쪽에만 반영이 안 돼 있던 것이다.
자세한 건 [레슨 51](../lessons/0051-association-scope-asymmetry.html)에 정리했다.

### 3. D4 논리를 엉뚱한 곳에 옮겨 썼다

분모에 `pending_check_in`(체크인 승인 대기)을 **포함**하기로 정했다. 제외하면 하위가
체크인을 *요청만 해도* 분모가 줄어 상위 값이 올라가고, 승인이든 반려든 처리되면 다시 내려간다.
실제 달성과 무관한 결재 상태가 값을 흔든다.

그런데 나중에 "상위 목표가 결재 대기 중이면 반영이 건너뛰어진다"는 문제를 보고, 같은 논리로
`objective.open?` 게이트도 풀자고 제안했다. **이건 비약이었다.**

- 분모 결정은 하위를 **읽는** 문제 (셀 것인가)
- `open?` 게이트는 상위에 **쓰는** 문제 (값을 바꿀 것인가)

읽기는 부작용이 없지만 쓰기는 진행 중인 결재와 충돌한다. 실제로 코드를 확인해보니
`RequestService`는 결재 대기 중인 목표에 체크인이 들어오면 **400으로 거부**하고 있었고,
`check_in_revision`/`objective_revision` 모델에도 같은 상호 배제가 있었다.
`open?` 게이트는 고아 규칙이 아니라 그 정책의 일부였다.

같은 단어(`pending_check_in`)가 나온다고 같은 판단이 적용되는 게 아니다.
**무엇을 하려는 연산인지**를 먼저 봐야 한다.

### 4. 협의로 뒤집힌 결정 — 정수 반올림

1/n으로 값이 작아지면 정수 반올림이 문제가 된다고 봤다. `unit` target 10에 하위 72개면
하위 하나가 0→100%로 가도 변화량이 0.139라 반올림에서 0이 되고, `next_value == prev_value`
조기 반환에 걸려 상위 전파도 히스토리도 안 남는다. 그래서 `.round(6)`을 제안했다.

협의 결과는 **정수 유지**였다. 절대값 소수 표기는 과제가 커진다는 이유였다.

받아들이고 나서 다시 보니, 내 우려 자체가 **옛 구조 기준**이었다. 재계산에서는 매번
하위 전체 평균에서 다시 구하므로 기여분이 영구히 사라지지 않는다. 몇 건 쌓이면 반올림
경계를 넘어 계단식으로 오르고, **하위 전체가 100%면 정확히 target**이 된다.

| target 10 · 하위 72개 | 계산값 | 저장값 |
|---|---|---|
| 1건 | 0.139 | 0 |
| 4건 | 0.556 | 1 |
| 72건 | 10.0 | 10 |

"통째로 사라진다"는 표현이 틀렸던 것이다. 구조를 바꾸면 예전 판단의 전제가 같이 바뀐다는 걸
놓치고 있었다.

### 5. 스펙을 지우지 않은 것

밸리데이션을 폐기할 때 `git checkout .`으로 한 번에 되돌리고 싶었지만, 세워둔 스펙 픽스처가
아까웠다. `batch_approval_spec.rb`가 조부모 구조(조부모 KR ← 부모A/부모B ← 각자의 손자)를
세팅하고 있었는데, **1/n 검증에 필요한 픽스처가 정확히 그 모양**이었다.

기대값만 "400 차단" → "순서를 바꿔도 최종값 동일"로 뒤집으니 이번 변경의 핵심 회귀 테스트가 됐다.
폐기하기 전에 스펙만 먼저 커밋해두길 잘했다.

그리고 기존 서비스 스펙 22건은 **손대지 않아도 그대로 통과**했다. 픽스처가 전부 하위 1개라
N=1 재계산이 기존 수식과 수학적으로 동일하기 때문이다. 이걸 미리 알아채서 재작성 범위가 크게 줄었다.

  연계별 가중치가 생기면 그 메서드 하나만 바뀐다. 이런 "지금은 무의미하지만 나중에 갈라질
  지점"을 어디까지 미리 열어두는 게 적절한지 감이 아직 없다.
