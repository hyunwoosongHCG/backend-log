# 스크럼보드 스크럼·댓글 검색 재개발과 구 스크럼 검색 제외 (자동 종료된 PR #4766의 후속)

> 날짜: 2026-10-22  
> PR: ppback [#5671](https://github.com/hcgtheplus/ppback/pull/5671) (draft, 커밋 4개), ppfront [#11589](https://github.com/hcgtheplus/ppfront/pull/11589) (draft, 커밋 3개). 원 PR은 hcgtheplus/ppback#4766 (base 브랜치 삭제로 자동 종료)  
> 소스: Performance Plus(실무) — Rails/Grape/Elasticsearch, React/TypeScript  
> 내 역할: 구현(+조사·설계) — 백엔드와 프론트를 모두 맡음. 팀 규모는 기록하지 않았다

## 작업 한 줄 요약

스크럼보드의 스크럼 답변과 그 댓글이 통합 검색에 나오지 않던 것을, 닫힌 PR을 되살리는 대신 `origin/dev` 기준으로 다시 만들어 검색·권한·재인덱싱·화면 이동까지 잇고, 쓰지 않는 구 스크럼은 검색 대상에서 뺐다.

## 성과

**Before → After**

- Before: 스크럼보드 답변은 ES에 인덱싱만 되고 `SearchService`에 조건이 없어 검색 결과에 한 건도 나오지 않았다. 인덱싱된 권한 값도 틀려 있었다(공개 여부를 boolean으로 저장해 `== 'all'` 비교가 항상 거짓, 허용 사용자는 참조자만). 스크럼보드 댓글은 `Search::Comment`가 이 대상을 몰라 공개·비공개 어느 조건에도 걸리지 않았고, performance 워크스페이스는 조건에서 아예 제외했다. 구 스크럼 답변과 구 스크럼 댓글은 performance 워크스페이스에서 계속 검색됐다.
- After: 열람 권한이 있는 보드의 답변과 댓글이 검색에 나오고, 클릭하면 해당 보드·작성자·날짜 화면으로 이동한다. 검색 범위에 `스크럼보드` 칩이 생겼다. 보드의 공개 범위·멤버·보관·삭제가 바뀌면 답변과 댓글 문서가 다시 인덱싱된다. 구 스크럼 답변과 구 스크럼 댓글은 두 도메인 모두 검색에서 빠진다.
- 숫자로 말할 수 있는 개선은 없다. **둘 다 draft이고 실제 ES에서 돌려 보지 못했다.**

**측정 방법**

- 실측: 컨테이너에서 rspec 실행 결과, `tsc`·eslint 실행 결과, "한 트랜잭션에서 두 번 저장하면 커밋 콜백이 어떻게 보이는지"를 임시 스펙으로 직접 돌려 확인(대조군 1회 큐잉, 두 번째 저장이 있으면 0회).
- 모의 응답으로만 확인: 화면 렌더링과 클릭 이동은 검색 API 응답을 Playwright로 가로채 스크럼 답변과 댓글 결과를 주입해서 봤다. 실제 백엔드·ES가 내려준 응답이 아니다.
- 확인하지 못함: ES가 새 매핑으로 실제 인덱싱·검색되는지, `put_mapping`이 실제로 동작하는지, 비공개 보드가 비멤버에게 안 보이는지, 보관 보드가 제외되는지, 이동 뒤 댓글이 펼쳐지는지(`openComment`). 로컬에 ES가 없어(9200 미구동, ECR 이미지 필요) 화면에서는 어떤 방법으로도 볼 수 없다.

**검증 근거**

- ppback: 검색·스크럼보드·댓글 관련 스펙 654개 중 4건이 실패했는데, 변경이 없는 `origin/dev`를 임시 워크트리로 만들어 같은 스펙을 돌리니 **똑같은 4건**이 실패했다(어드민 권한 403). 이번 변경이 만든 실패는 없다. 이후 변경분의 관련 스펙 80개는 모두 통과.
- ppfront: 변경 파일에 `tsc` 오류 없음, eslint 오류 0.
- ES를 쓰는 스펙(`:elasticsearch` 태그)은 환경이 없어 건너뛰어졌다. 검색 쿼리 본문은 ES 요청을 가로채서 검증했다.
- 화면(ppfront 3000, 제 커밋을 잠시 체크아웃해서 사용): 스크럼 답변은 `스크럼보드 2026-10-21`, 댓글은 `스크럼보드 2026-10-21 > 댓글` 라벨로 표시된다. 칩을 누르면 요청에 `category[]=board_scrum_item_response`가 실린다. 답변과 댓글을 누르면 `/scrum_boards?ended=2026-10-21&member=3&scrum_board_id=2&started=2026-10-21`로 이동해 해당 보드가 열린다. 접근할 수 없는 보드 id로 주면 화면이 접근 가능한 보드로 되돌린다(기존 동작). 프론트의 구 스크럼 결과 분기는 지우지 않았다. 백엔드가 구 타입을 내리지 않게 된 뒤에 정리한다.
- 코드 리뷰 에이전트: CRITICAL·HIGH 없음. MEDIUM 3건 중 하나는 이미 통과한 스펙으로 닫혔고 둘은 반영했다.

## 이번 작업에서 처음 배운 개념

- [ ] [보편] **검색 문서에 복제한 권한은 원본이 바뀌면 stale 해진다.** 답변·댓글 문서에 `allowed_user_ids`·`privacy`를 박아 두면, 보드를 비공개로 바꾼 뒤에도 문서는 옛 권한이다. 원본(보드)이 바뀌는 모든 경로에서 하위 문서(답변과 댓글)를 다시 인덱싱해야 하는데, 이 레포의 연쇄 갱신 선례는 `Task`·`TaskList`뿐이었다 → ROADMAP 섹션 4 "검색 (Elasticsearch)"에 신규
- [ ] [보편] **`dynamic: strict` 인덱스에 필드를 더하는 방법은 두 가지다 — 재생성과 `put_mapping`.** 재생성(`search:reindex_type`)은 인덱스를 지우고 배포된 코드의 매핑으로 다시 만들어서 "코드 배포 → 재생성" 순서이고 실행 중에는 결과가 빈다. 필드만 더하는 거라면 `put_mapping`으로 인덱스를 두고 더할 수 있다고 알고 있고(ES 문서 기준, 이 환경에서 실행해 보지 못함) 배포 전에 콘솔에서 먼저 할 수도 있다. 이번에는 큰 Comment 인덱스는 `put_mapping`, 스크럼 답변 인덱스는 재생성을 택했다. 새 키를 해당 타입 문서에만 싣는 것도 영향 범위를 줄인다 → 신규
- [ ] [보편] **재생성 rake의 가져오기는 부분 실패를 삼킨다.** `SetupWorker`의 가져오기가 `rescue StandardError`로 경고만 출력하고 끝나서 일부만 들어간 채 성공처럼 보인다. 실행 뒤에 DB 행 수와 ES 문서 수를 비교해야 안다 → 신규
- [ ] [보편] **불리언 필터 컬럼의 `nil`은 세 번째 상태라 조용히 검색에서 빠진다.** 공개는 `term: { search_privacy: false }`, 비공개는 `allowed_user_ids` 일치로 가르는 설계에서 값이 `nil`이면 어느 쪽에도 안 걸린다. `Search::Comment#search_privacy`의 `case`가 `BoardScrum`을 몰라 `nil`을 돌려준 것이 "스크럼은 나오는데 댓글은 안 나온다"의 원인이었다. 새 대상을 추가할 때는 `case`의 `else`(암묵적 `nil`)가 무엇이 되는지부터 본다 → 신규
- [ ] [보편] **한 서비스가 도메인별로 조건 목록을 따로 가지면 같은 변경이 도메인마다 다르게 보인다.** `SearchService`는 댓글 제외 대상이 performance는 `BoardScrum`, talenx는 `Scrum`이었다. 변경 전에 `이전 → 현재 → 이 PR`을 도메인별로 나눠 표로 확인하면 "한쪽 도메인에서만 보이던 것이 뒤집힌다"를 놓치지 않는다 → 신규
- [ ] [보편] **새 결과 타입은 받는 쪽(프론트)이 먼저 배포돼야 한다.** 프론트의 분기 체인은 모르는 타입에 빈 객체 `{}`를 돌려주고 이어서 `label.key`에서 오류가 날 것으로 보인다(코드를 읽고 추정했고 실행해서 확인하지는 않았다). 구 스크럼 분기를 지우는 것도 백엔드가 구 타입을 내리지 않게 된 뒤로 미뤘다 → 신규
- [ ] [Rails 전용] **한 트랜잭션에서 두 번 저장하면 커밋 콜백은 마지막 저장의 변경분만 본다.** `PUT :id`가 `update!` 뒤에 슬랙 채널 처리용 `save!`를 한 번 더 호출해서, `after_update_commit`의 `saved_change_to_is_private?`가 거짓으로 보인다. 임시 스펙으로 확인: 단일 저장은 1회, 두 번째 저장이 변경 없음이든 다른 컬럼 변경이든 0회 → 기존 `after_commit` 항목을 심화
- [ ] [Rails 전용] **`ActiveRecord.after_all_transactions_commit`** — 보드 행을 건드리지 않고 멤버만 바꾸는 경로에서는 모델의 `after_commit`이 발동하지 않아서, 호출부가 직접 부르되 실행은 커밋 뒤로 미룬다. 진행 중인 트랜잭션이 없으면 즉시 실행하고, 롤백되면 실행하지 않는다 → `after_commit` 항목을 심화
- [ ] [Ruby 전용] **중첩 모듈 안에서 같은 이름의 상수는 모델이 아니라 가장 가까운 모듈을 가리킨다.** `module Search` 안의 워커가 `BoardScrumItemResponse.joins`를 부르면 모델이 아니라 `Search::BoardScrumItemResponse`(검색 concern)가 잡혀 `undefined method 'joins' for module`이 난다. 댓글을 더하면서 `Comment`도 `Search::Comment`와 겹쳐 `::BoardScrumItemResponse`, `::Comment`로 최상위를 명시했다 → "Ruby 특유 개념"에 신규
- [ ] [Rails 전용] **`let_it_be` 객체는 롤백 뒤에도 메모리 속성이 남는다.** 한 예제가 `update!(is_private: true)`를 하고 DB가 롤백돼도 객체는 `true`를 기억해서, 다음 예제의 `update!(is_private: true)`가 "변경 없음"으로 UPDATE를 건너뛴다 → 기존 `let_it_be` 항목을 심화
- [ ] [Rails 전용] **스텁의 호출 집계에 준비 단계의 콜백이 섞인다.** 워커 스펙에서 `comment.discard!`로 삭제 상태를 만들었더니 `Searchable` 콜백이 `UpdateWorker`를 한 번 더 큐잉해 `have_received`가 2회로 잡혔다. 콜백 없이 상태만 만들려면 `update_all`을 쓴다 → 테스트 항목에 신규
- [ ] [보편] **같은 "열람 대상"을 정책과 검색이 따로 계산하면 어긋난다.** `ScrumBoardPolicy#show?`는 담당자·관리자·참조자를 모두 허용하는데 검색 concern은 참조자만 인덱싱하고 있었다. 검색 권한은 실제로 쓰이는 정책과 같은 범위로 맞추고, 변경 감지(`audience_ids`)와 문서 내용(`allowed_*_ids`)이 같은 정의를 쓰는지 주석으로 연결해 둔다 → "권한"의 기존 항목을 심화
- [ ] [보편] **호출하는 곳이 없는 정책 메서드는 죽은 채 남아 있다.** `BoardScrumItemResponsePolicy#show?`가 `ScrumBoard`에 정의되지 않은 `permitting_user_ids`를 부르는데 호출처가 없어 아무도 몰랐다 → 기존 "정책이 죽었는지 확인하는 세 겹" 항목을 재확인

## 작업하면서 막혔던 것과 해결 방법

- **새 스펙 15개가 한꺼번에 실패**: `BoardScrum`의 `after_initialize`가 `user`가 있을 때만 템플릿 항목별 답변을 만드는데, FactoryBot은 객체를 만든 **뒤** 속성을 할당해서 그 시점의 `user`가 비어 있었다. 답변을 스펙에서 명시적으로 만들도록 고쳤다.
- **요청 스펙 두 건이 "큐잉 0회"로 실패**: 서버 코드 문제가 아니라 `let_it_be` 객체의 메모리 속성 오염이었다. 디버그 출력으로 요청 시점의 `is_private`가 `false`인 것을 보고 찾았고, 예제마다 `ScrumBoard.find`로 다시 읽게 했다.
- **워커 스펙 5건 실패**: `undefined method 'joins' for module Search::BoardScrumItemResponse` — 상수 탐색. 스펙이 없었다면 배포 후 재인덱싱 워커가 전부 실패했을 버그다.
- **"스크럼은 나오는데 댓글은 안 나온다"**: 댓글 인덱싱 코드를 읽어 보니 `search_privacy`·`allowed_*_ids`가 `Scrum`·`Objective`·`Feedback`·`Task`만 다루고 `BoardScrum`은 `nil`이었다. 프론트도 댓글 분기가 `BoardScrum`을 몰라 빈 객체로 떨어졌다. 둘 다 고쳤다.
- **구 스크럼을 검색에서 빼야 하는지**: 사용자 판단("마이그레이션 이후로 안 쓴다")을 Slack 히스토리로 확인했다. `#ch-sc` 2026-07-23 구 스크럼 제거 스레드에서 구 스크럼 API·마이그레이션 모달 제거를 공유했고 데이터는 남겨 두기로 했다. 다만 제거가 실제로 반영됐는지는 못 찾았고 `dev`에는 구 스크럼 모델·API·검색 concern이 아직 남아 있다. 구 스크럼 답변 조건만 검색에서 걷어냈다(구 스크럼 댓글은 두 도메인의 댓글 조건이 같아지면서 함께 빠졌다).
- **테스트 실행 환경**: 워크트리에서 `docker compose`를 돌리면 별도 프로젝트로 인식돼 DB·Redis 포트가 충돌하고, `app-code` named volume이 다른 체크아웃의 경로에 바인드돼 있어 `-p`로 붙으면 엉뚱한 코드가 실행된다. 워크트리를 직접 마운트한 일회성 `docker run`으로 기존 네트워크의 DB·Redis에만 붙었다(ROADMAP에 이미 있는 항목을 다시 겪음).
- **RuboCop 필터가 제 줄이 아닌 지적 41건을 보여줌**: 파일 목록을 `$FILES`로 넘겼는데 zsh는 따옴표 없는 변수를 단어 분리하지 않아 필터가 파일을 못 찾았다. `search_service.rb:15` 같은 제가 건드리지 않은 줄이 나온 것을 보고 필터 자체를 의심해 찾았다. 도구 출력을 믿기 전에 필터가 제대로 걸렀는지 먼저 본다.
- **Playwright 가로채기가 화면 주소까지 가로챔**: `**/workspaces/*/search?*` 패턴이 API 요청뿐 아니라 화면 주소에도 맞아서 페이지가 모의 JSON으로 바뀌었다. API 경로(`/api/v1/`)까지 좁힌 정규식으로 해결했다. 알림 서비스(4002) 연결 실패로 뜨는 오류 다이얼로그가 클릭을 가로막는 것도 닫고 진행했다(변경과 무관한 환경 문제).
- **PR 본문 사진 첨부**: `gh`로는 이미지를 올릴 수 없고 Playwright 브라우저는 GitHub에 로그인돼 있지 않았다. 사용자의 Chrome 확장은 이미 로그인돼 있어 파일 업로드 도구로 `user-attachments` 이미지를 올릴 수 있었다. 다만 Chrome 창이 백그라운드(`visibilityState: hidden`)면 화면이 그려지지 않아 스크린샷과 메뉴 로딩이 실패하고, 창을 앞으로 가져오면 해결됐다.
- **에이전트 보고를 그대로 믿지 않기**: 보안 리뷰 에이전트가 "배포 순서는 인덱스 재생성 → 코드 배포"라고 했는데 재생성은 배포된 코드의 매핑을 쓰므로 반대다(`setup_worker.rb`를 읽어 바로잡음). 코드 리뷰 에이전트의 "`put_mapping`을 코드 배포 전에 먼저"는 맞지만 rake 작업이 같은 PR 코드에 들어 있어서 배포 전에는 콘솔 한 줄로 먼저 실행하도록 PR 본문에 적었다. "DatabaseCleaner 조합 때문에 콜백이 안 돌 수 있다"는 추정은 이미 통과한 스펙 실행으로 반박됐다.
- **범위 조정**: ppback 범위를 "구 스크럼 제거만"으로 좁혔다가 댓글 검색까지 넓혔다. 신 스크럼 검색, 구 스크럼 제외, 댓글 검색을 별도 커밋으로 나눠 둔 덕에 조정이 쉬웠다.

## 다음에 더 공부하고 싶은 것

- 보드가 바뀔 때마다 하위 문서를 전부 다시 쓰는 방식 말고, 검색 시점에 권한을 조회하는 구조(예: ES의 terms lookup)는 어떤 대가가 있는지
- `put_mapping`을 PR에 썼지만 실제 ES에서 실행해 보지 못했다. 스테이징에서 동작을 확인하고, 스크럼 답변 인덱스도 재생성 대신 `put_mapping` + 제자리 재인덱싱으로 했다면 결과가 빈 구간 없이 배포됐을지 비교하고 싶다
- 대량 가져오기가 부분 실패했을 때 이를 자동으로 감지하는 방법(문서 수 비교를 배포 절차에 넣는 것 이상으로)
- 같은 보드에 대한 재인덱싱 요청이 짧은 시간에 반복될 때 중복 job을 줄이는 방법(지금은 한 요청 안에서만 막는다)
- 프론트가 모르는 결과 타입에 안전한 기본 분기를 두는 방법(지금은 `{}`로 떨어져 오류가 날 것으로 보인다)
- 구 스크럼 제거가 끝난 뒤 남는 정리: 구 스크럼 답변·댓글 문서, `Search::Comment`의 `Scrum` 분기, 프론트의 구 스크럼 분기, 이름이 답변인데 댓글도 다루는 워커
- `policy_scope`의 쓰임(`BoardScrumItemResponsePolicy::Scope`를 봤지만 이번에 학습하지는 않았다)
