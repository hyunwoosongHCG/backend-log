## 작업 한 줄 요약

커밋 5(자동 마감을 30초 지연 워커로 분리)를 구현·검증까지 마쳤는데, 팀 논의에서 "목표별 트랜잭션으로 쪼갠 지금 구조에서는 반영이 끝나는 즉시 마감 판정하는 게 맞다"는 결론이 나와 되돌렸다. 되돌린 뒤 셀프 검토를 하다가 원래 우려(반영끼리의 경합)보다 훨씬 넓은 기존 결함 — `AutoCloseObjectiveIfProgressCompleteService` 호출부 6곳 중 5곳에 `closed?` 재확인이 아예 없던 것 — 을 발견해서, 지연이 아니라 서비스 자체를 락으로 감싸는 방식으로 고쳤다. 그 과정에서 랜덤 시드에서만 실패하는 스펙을 만나 `let_it_be` + Dirty Tracking의 새로운 함정을 하나 더 배웠고, 마지막으로 마이그레이션 타임스탬프가 dev보다 뒤처져 있던 걸 발견해 재발급했다. PR 본문도 지금까지 리버트된 아웃박스 설계 서술을 걷어내고 실제 코드 기준으로 전면 재구성했다.

## 이번 작업에서 처음 배운 개념

- **방어 로직은 호출부가 아니라 공유되는 낮은 지점에 둔다.** `AutoCloseObjectiveIfProgressCompleteService`를 부르는 곳이 반영 워커·체크인 승인·자기 승인 체크인·수정 승인·메신저봇 승인·상태 변경까지 여섯 곳이었는데, `closed?` 재확인은 반영 워커 한 곳에만(그마저도 락 없이) 있었다. 담당자의 직접 체크인 승인과 하위 목표의 자동 반영이 우연히 같은 목표를 동시에 100%로 만들면 둘 다 마감을 시도해 `Closed` 히스토리가 중복 생성될 수 있었다 — 서로 다른 호출부가 서로의 존재를 모르니 호출부마다 가드를 반복해서 심는 건 애초에 완결될 수 없는 접근이고, 여러 경로가 모이는 서비스 자체를 `objective.with_lock`으로 감싸야 호출부 코드를 하나도 안 건드리고 전부 방어된다는 걸 실제 버그로 체감했다.
- **잠금 읽기(`SELECT ... FOR UPDATE`)는 REPEATABLE READ 스냅샷을 무시하고 최신 커밋을 본다 — 그리고 같은 트랜잭션이 이미 쥔 행 락은 재요청해도 곧바로 통과한다.** 호출부 중 하나(`request_service.rb`)는 이미 자기 `with_lock` 안에서 이 서비스를 부르고 있어서, 서비스가 또 `with_lock`을 거는 게 안전한지 확인해야 했다. MySQL InnoDB는 같은 트랜잭션이 이미 보유한 행 락을 다시 요청하면 즉시 통과시키고(재진입), 잠금 읽기는 트랜잭션이 언제 시작됐든 그 시점의 최신 커밋 데이터를 본다 — 그래서 중첩된 `with_lock` 호출도 데드락 없이 안전하고, 다른 트랜잭션의 변경도 놓치지 않는다는 걸 코드로 확인했다.
- **`let_it_be`로 공유된 레코드에 매번 같은 값을 `update!`하면, 예제 순서에 따라 실제 SQL이 안 나갈 수 있다(레슨 59).** 이전에 배운 `let_it_be` 함정(레슨 48)은 "저장 없이 인메모리만 바꾸는 경우"였는데, 이번엔 매번 정식으로 `update!`를 불렀는데도 걸렸다 — 앞선 예제가 그 값을 이미 `true`로 만들어두면, 다음 예제의 트랜잭션 롤백은 DB만 되돌리고 인메모리 값은 그대로 `true`로 남는다. 그 상태에서 다시 `true`를 대입하면 Dirty Tracking이 "변경 없음"으로 보고 `partial_writes`가 그 컬럼을 UPDATE SQL에서 빼버려, DB는 계속 롤백된 값(`false`)에 머문다. `workspace.reload.objective_setting.update!(...)`처럼 `reload`로 진짜 현재 값부터 확보해야 한다는 걸, 이미 옆 스펙 파일에 그 방어가 심어져 있었다는 걸 뒤늦게 발견하며 배웠다.
- **마이그레이션 타임스탬프가 이미 병합된 마이그레이션보다 앞서면, 새 파일을 만들고 `schema_migrations`를 직접 relabel한다.** 브랜치 작업 중 dev가 진행돼 우리 마이그레이션(2026-07-22)보다 늦은 타임스탬프가 여럿 병합됐다. 로컬 DB엔 이미 적용된 상태라 컬럼을 다시 만들 수 없으니, Rails 생성기로 실제 지금 시각의 새 파일을 만들어 `change` 내용만 옮기고, `schema_migrations` 테이블의 버전 값만 SQL로 갱신해(`UPDATE schema_migrations SET version = ... WHERE version = ...`) 컬럼은 그대로 두고 버전 식별자만 재부여했다. `db:migrate:status`가 `up`을 정확히 보고하는지, `db/schema.rb`를 재덤프했을 때 버전 줄 하나만 바뀌는지로 안전하게 됐는지 확인했다.
- **문서는 이전 문서 내용이 아니라 `git diff`로 갱신해야 한다.** PR 본문을 "현재 구현에 맞게" 다시 쓰라는 요청을 받고, 기존 PR 본문을 다듬는 대신 `git diff dev...HEAD`로 실제 변경된 파일 48개를 전부 훑었다. 그 결과 본문이 설명하던 아웃박스 테이블(`key_result_reflection_events`)이 이미 리버트돼 존재하지 않고, 실제로는 boolean 컬럼 2개만 남아 있다는 걸 확인했다 — 문서를 문서에서 파생시키면 이미 죽은 설계가 계속 복제된다는 걸 실제로 겪었다.

## 작업하면서 막혔던 것과 해결 방법

- 자동 마감 재현 스펙에서 "형제 두 개가 동시에 같은 상위를 100%로 미는" 경합을 스레드로 재현하려 했는데 중복이 안 났다. 원인은 두 형제 모두 이미 100% 값을 가진 채로 픽스처를 만들어서, 두 번째 반영 잡이 "새 값 == 현재 값"으로 판정돼 `nil`을 반환하고 애초에 마감 시도 자체를 안 탄 것이었다 — 재현하려던 경합과 실제 코드의 멱등성 가드가 우연히 같은 방향으로 작동해 "버그 없음"처럼 보였다. 이후 호출부 6곳 전수 조사로 방향을 바꿔서야 진짜 결함(직접 체크인 vs 반영 경로 간 경합)을 찾았다.
- `objective.destroy!`로 "삭제된 목표" 케이스를 재현하려다 `images.objective_id` 컬럼이 없다는 무관한 에러를 만났다. Discard 기반 소프트 삭제 모델에 하드 `destroy!`를 쓴 게 원인이었고, `Objective`엔 `default_scope`가 없어 `discard!`로도 `find_by`가 여전히 레코드를 찾아버려 재현이 안 됐다 — 결국 존재하지 않는 id(`-1`)를 직접 넘기는 쪽으로 단순화했다.
- 신규 auto-close 워커 스펙의 "진행률 100%면 마감한다" 테스트가 시드 7940에서만 실패했다. `key_results.loaded?`, `progress` 값 등을 계속 의심하다 안 풀려서, 프로덕션 워커 코드에 임시 `puts`를 박아 실제 실행 경로를 추적했고, 그제서야 `objective_setting.completion_trigger_rate_enabled`가 `false`로 읽히고 있다는 걸 확인해 원인(레슨 59)에 도달했다.

## 다음에 더 공부하고 싶은 것

- `let_it_be(reload: true)` 옵션이 레슨 59의 문제를 애초에 방지해주는지, 이 프로젝트에 같은 패턴(공유 픽스처 + 반복 `update!`)의 스펙이 더 있는지 훑어보고 싶다.
- MySQL InnoDB 잠금 재진입(같은 트랜잭션이 이미 쥔 락 재요청)의 정확한 동작 범위 — 다른 격리수준이나 다른 잠금 모드(공유 vs 배타) 조합에서도 항상 안전한지.
- 이번에 고친 자동 마감 서비스처럼, "여러 호출부가 공유하는 로우레벨 서비스"를 사전에 식별하는 체크리스트 같은 걸 만들 수 있을지 — 이번엔 우연히(리버트 셀프 검토 중) 찾았지 의도적으로 찾은 게 아니었다.
