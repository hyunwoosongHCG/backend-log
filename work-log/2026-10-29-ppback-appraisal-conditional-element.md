# [평가] 평가 양식 조건부 문항 도입과 방식 묶음 호환 보정 축소

> 날짜: 2026-10-29 ~ 2026-11-03  
> PR: [hcgtheplus/ppback#5699](https://github.com/hcgtheplus/ppback/pull/5699) (base: `dev`, 11-09 릴리스) · 백로그 ssq-backlog#1721  
> 소스: Performance Plus(실무) — Rails 8.1 · Grape · MySQL 8  
> 내 역할: 설계·구현 — 백엔드 단독. admin 조건부 작성 UI(talenx-admin #4665·#4678)와 응답 화면(ppfront #11634)은 FE 담당

## 작업 한 줄 요약

360 피드백에만 열려 있던 조건부 문항(상위 문항 점수에 따라 노출되는 문항)을 평가 양식에도 저장·검증·응답 처리할 수 있게 열었다. 같은 PR에서 평가 방식 묶음 호환 보정(`fill_method_group_number_from_legacy`)을 "지우기" 대신 "데이터 모양으로 대상을 좁히기"로 바꿨다. 원래 #5694(보정 제거) → #5697(구 값 정리 rake) → #5699 세 단계 스택이었는데, 이번 릴리스에서는 #5699 하나로 합치고 #5694·#5697은 닫았다.

## 성과

**Before → After**

- 평가 양식 조건부 문항: 저장해도 조건부로 읽히지 않았고 저장 검증이 없었다 → 상위 번호와 기준 조건(`parent_standard_kind`)이 둘 다 있을 때만 조건부로 보고, 저장 검증·응답 엔티티(`is_conditional`)·응답 저장 처리까지 연결했다.
- 방식 묶음 보정: 저장 요청의 **모든 행**을 구 필드로 다시 계산해 덮어썼다 → `method_group_number` 키가 있는 행은 보낸 값 그대로, 키가 없는 행만 구 필드로 채우고, 조건부 행은 계산에서 뺀다. 그대로 뒀다면 새 어드민(#4665) 요청의 묶음이 전부 null이 되고, 조건 문항이 상위 문항 묶음에 합쳐졌다(테스트 세션이 spec으로 재현).
- 조건부 판정 위치: `Element#conditional?`와 검증기가 각자 `element_link_type`을 분기했다 → 문항을 가진 양식·영역 모델이 `conditional_element?`로 정하고 `Element`는 위임한다. 360 규칙은 `Feedbackpool`로 그대로 옮겼다.
- 조건부 동작 범위: 양식 영역(`item: template`)과 평가 대상자별 양식에서만 동작한다. 목표·핵심성과·배지·직무 영역은 `is_conditional: false`이고 응답 처리도 하지 않는다.
- 응답 저장: 숨겨진 조건부 문항의 응답은 임시저장·제출 모두 버리고, 제출 때 노출된 필수 조건부 문항이 비어 있으면 400을 낸다. 일반 문항의 필수 검사는 원래 서버에 없어서 넣지 않았다.
- 숨긴 문항이 영역 점수 분모에 남는 문제: 점수 계산을 고치지 않고 "조건부 문항은 `check_score` 불가"(400)로 입력을 막아 분모에 들어갈 일을 없앴다.
- 응답 엔티티의 deprecated `is_optional` 노출 제거(운영 admin·ppfront는 이미 `isConditional`만 읽음).

**측정 방법**

- 실측(2026-10-29, 사용자가 프로덕션 replica 조회): 평가 element의 `parent_standard_kind`·`parent_standard_score` non-null 0건. 옮길 데이터가 없으므로 계약을 새로 정할 수 있었다.
- 실측(로컬): 영역 `item`별 분포와 대상자별 양식 영역 4건이 모두 `item: template`인 것을 DB로 확인했다. 쿼리 수는 `ActiveSupport::Notifications`로 센 값이다.
- 실측(2026-11-02, 테스트 세션): 화면 조작으로 만든 양식·평가에 백엔드·admin·ppfront 조합을 붙여 요청 본문과 DB 값을 확인했다.

**검증 근거**

- 관련 RSpec 536건: 526 통과, 10 실패. 실패 10건은 변경 전부터 있던 것이다(`template_pools_spec`의 `icons`·`recommend`·`bulk` 9건은 로컬 S3 설정 없음, `group_multisource_feedback/multisource_feedback_spec.rb:91`은 dev에서도 403).
- 캡처한 어드민 실제 요청 10건 모두 키 없는 행이 0건이었고, 생성·일괄 업로드 요청을 새 브랜치에 다시 보내면 보낸 `method_group_number`가 그대로 저장됐다.
- 로컬 E2E 5/6 통과: 조건부 양식 저장, 양식 영역·대상자별 양식 영역 응답(숨긴 응답이 DB에 없음), 열어 둔 옛 탭, dev admin 단독 묶음 조작. 360 화면은 로컬 S3 설정 없음(500, 변경 전에도 동일)으로 확인하지 못해 스테이징 확인이 남았다.
- 쿼리 수 spec: 영역 3개·문항 18개 요청과 영역 1개·문항 2개 요청의 쿼리 수가 같다. `includes(:element_link)`를 빼면 5 → 21로 늘어 spec이 실패하는 것을 확인했다.

## 이번 작업에서 처음 배운 개념

- [x] [보편] **호환 코드는 지우는 대신 "데이터 모양으로 대상을 좁힐" 수 있다**
  - 처음 방침은 보정을 지우는 것이었다. 그러면 "프론트가 먼저 나가면 묶음이 null로 덮이고, 백엔드가 먼저 나가면 구 탭이 깨지는" 배포 순서 의존이 생긴다.
  - 키가 있으면 신뢰하고(`key?(:method_group_number)`), 조건부 행(`parent_standard_kind` 있음)은 계산에서 빼면 보정이 남아 있어도 새 클라이언트와 충돌하지 않는다. 지우는 일은 구 클라이언트가 사라진 뒤 다음 스프린트로 미룬다.
  - 같은 맥락에서 "구 값이 절대 만족할 수 없는 조합으로 의미를 정의"(조건부 = 상위 번호 **그리고** 기준 조건)하면 남은 구 값이 저장돼도 무해하다.
- [x] [Rails 전용] **`declared(params, include_missing: false)`로 "키가 없음"과 "null을 보냄"을 구분한다**
  - 보정 규칙이 `key?(:method_group_number)` 한 줄로 갈리는 이유다. `null`을 보냈으면 "단독 문항"이라는 뜻이라 그대로 저장하고, 키 자체가 없을 때만 구 필드로 채운다.
- [x] [보편] **판정을 한 곳에 두려고 위임하면, 위임 대상을 읽는 비용이 숨는다**
  - 처음에는 값만 받는 클래스 메서드(`Element.conditional_values?`)로 규칙을 모았다. 리뷰와 위치 논의 끝에 "공통 모델이 모든 도메인의 규칙을 알면 안 된다"는 쪽으로 가서, 문항을 가진 양식·영역 모델에 `conditional_element?`를 두고 `Element#conditional?`가 `element_link`에 묻게 바꿨다(Rails `delegated_type` 문서의 "타입을 묻지 말고 각 타입이 같은 메서드를 구현하라"와 같은 방향).
  - 대가: `Element#conditional?`가 `element_link`를 읽으므로 문항마다 쿼리가 나갈 수 있다. 응답 서비스는 `includes(:element_link)`로 막고 쿼리 수 spec으로 고정했다.
- [x] [Rails 전용] **`has_many :through`·`ElementGroup#elements`로 불러온 레코드는 `inverse_of`로 부모가 채워지지 않는다**
  - 양식·영역의 `has_many :elements, inverse_of: :element_link`는 `element_link`가 이미 채워져 쿼리가 없다. 360 `MultisourceFeedback#elements`(through)와 `ElementGroup#elements`는 채워지지 않아 360 엔티티 5곳이 N+1이 됐다. 내 쿼리 수 검증은 응답 저장 경로만 봐서 놓쳤고, 다른 세션이 찾아 수정했다.
- [x] [보편] **응답이 어느 단위로 저장되는지 확인하기 전에 "영역 단위"라고 가정하면 안 된다**
  - `AppraisalResponse`의 유일성 scope는 `section_id`뿐 아니라 `objective_id`·`key_result_id`·`badgepool_id`·직무 질문 id까지 포함한다. 목표 영역에서는 같은 문항이 목표마다 따로 응답된다. 제가 `[section_id, element_id]`로만 판정해서, 목표 A의 상위 답으로 목표 B의 조건부 응답을 저장·삭제할 수 있었다(리뷰 세션 지적, 코드로 확인).
  - 고치는 방향: 항목 단위 판정을 새로 만드는 대신 "조건부는 양식 영역에서만 동작"으로 범위를 줄였다. 서버는 영역 종류(`item`)만 보면 되고 프론트 계약도 단순해졌다.
- [x] [보편] **같은 데이터가 화면에 두 경로로 내려가면 "타입 기준 판정"이 경로마다 갈린다**
  - 응답 화면은 영역 설정에 따라 영역 문항(복사본, `AppraisalSection`) 또는 대상자별 양식 문항(`AppraisalTemplate`)을 받는다. 링크 타입으로 판정하니 한쪽만 `true`가 됐다. "응답 화면은 항상 false"라고 단정했다가 틀렸고, 판정 기준을 정할 때는 값이 엔티티에서 프론트 사용처까지 어떤 경로로 나가는지 따라가 봐야 한다.
  - 대상자별 양식 영역은 별도 `item`이 아니라 `item: template` 영역에 `appraisal_template_id: nil`로 대상자별 양식을 붙이는 구조였다(로컬 DB로 확인).
- [x] [보편] **계산을 고치기 어려우면 입력을 제약해 그 상태가 생기지 않게 한다**
  - 숨긴 문항을 분모에서 빼려면 평가자마다 노출 여부를 판정해야 해서 범위가 컸다. 조건부 문항은 점수 반영을 못 쓰게 막으면 숨긴 문항이 분모에 들어갈 일이 없다. 360은 같은 규칙을 넣으면 기존 양식 저장이 400이 될 수 있어 넣지 않았다 — 새 검증은 기존 데이터에 먼저 비춰 본다.
- [x] [Rails 전용] **`extend`로 객체 하나에만 모듈을 섞어 nested attributes 의미를 바꾸는 코드가 있다**
  - 평가 양식 수정은 `template_pool.extend(ModifyNestedAttributes)`로 그 인스턴스만 요청 목록에 없는 문항을 `_destroy`한다. 360은 그렇지 않다. "저장될 최종 상태"를 계산하는 검증기도 유형별로 다르게 합쳐야 했다.
- [x] [Rails 전용] **`abstract_class` 하위 클래스의 `polymorphic_name`은 자기 클래스명이다**
  - `TemplatePool`은 STI가 아니어서 `element_link_type`에 `Feedbackpool`·`AppraisalTemplate`이 그대로 들어간다.
- [x] [Git/GitHub] **스택 PR을 접는 법: `git rebase --onto`와 `gh stack unstack`**
  - `git rebase --onto origin/dev <아래 PR의 마지막 커밋> <브랜치>`로 위 PR의 커밋만 새 base 위로 옮긴다(아래 PR 커밋은 빠진다). 원격이 다른 세션에 의해 다시 쓰여 해시가 바뀌었으니 어디까지가 "아래 PR"인지 로컬 해시가 아니라 원격 기준으로 확인해야 했다.
  - GitHub 스택에 묶인 PR은 base를 바꿀 수 없다. 스택 번호는 PR 응답의 `stack`(REST) 또는 `pullRequest.stack.number`(GraphQL)로 찾고 `gh stack unstack <번호>`로 푼다. 이 명령은 PR을 닫거나 브랜치를 지우지 않는다.
  - 강제 push는 확인한 원격 해시에 고정한 `--force-with-lease=<브랜치>:<해시>`로 해서 그사이 다른 push가 있으면 실패하게 했다.

## 작업하면서 막혔던 것과 해결 방법

1. **방침이 세 번 바뀌었다.** 처음에는 "저장 시 null로 바꾸는 임시 보정 + 정리 rake"였고, 10-29에 "판정 규칙으로 흡수"로 바뀌었고, 11-02에 "보정은 두고 좁히기 + 구 값 정리는 다음 스프린트 마이그레이션"으로 바뀌었다. 매번 근거는 새로 얻은 사실이었다(프로덕션 0건 조회, 테스트 세션의 spec 재현, 배포 순서 의존). 카드 설명보다 인계 문서와 가장 최근 결정을 우선했다.
2. **"읽는 쪽"을 전수 조사했더니 범위 밖 문제가 둘 나왔다.** 평가 응답에는 서버 필수 검증이 아예 없고, 영역 점수는 `check_score` 문항 전부를 분모에 넣는다. 처음에는 "평가 영역은 조건부 미지원"으로 범위에서 뺐다가, "조건에 안 맞으면 숨기는 게 당연하다"는 제품 판단으로 뒤집었고, 필수 응답은 조건부 문항에만 서버가 검사하고 점수는 `check_score` 차단으로 막았다.
3. **Figma 시안을 못 읽었다.** Framelink 토큰 만료(403). 설정 의도는 사용자 확인으로 정했다(360과 동일, 오류 문구에서 "피드백"만 뺌).
4. **원격 브랜치가 다른 세션에 의해 다시 쓰였다.** 인계 문서의 해시·체크아웃 위치가 실제와 달랐다. 작업을 이어 가기 전에 `git ls-remote`와 worktree 목록으로 현재 상태를 먼저 확인했다.
5. **dev가 gem을 올려서(`jwt 2.10.3`) 기존 테스트 볼륨이 쓸모없어졌다.** 이 worktree 전용 bundle 볼륨에만 `bundle install`을 하고 메인 앱 볼륨은 건드리지 않았다.
6. **#5694를 닫으면 사라질 합의가 있었다.** 승인된 PR에 "구형 관리자 `theplus-front`가 `isOptional`을 읽지만 사용자가 없어 대응하지 않는다", "E2E 시드·배포 순서" 같은 합의가 있었다. 닫기 전에 리뷰를 읽고 #5699 본문으로 옮겼다.

## 다음에 더 공부하고 싶은 것

- 평가자 여러 명의 응답으로 한 사람의 점수를 낼 때, 평가자마다 노출 문항이 다르면 분모를 어떻게 정의해야 공정한가(조건부 문항에 점수 반영을 열 때 필요)
- 목표·핵심성과·배지·직무 영역에서 조건부를 지원하려면 항목(목표·직무 질문) 단위로 응답 키를 어떻게 모델링해야 하는가
- 평가 대상자별 양식 문항이 복사본이 아니라 원본 양식에 연결돼 있다면(테스트 세션 관찰), 평가 시작 뒤 양식 수정이 진행 중인 평가에 어떻게 반영되는가 — 따로 확인할 업무
- 서버에 없는 검증을 나중에 추가할 때 기존 클라이언트 제출 동작이 바뀌는 위험을 어떻게 단계적으로 여는가(경고 로그 → 차단)
