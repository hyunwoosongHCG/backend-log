## 작업 한 줄 요약

360 피드백에만 열려 있던 조건부 문항(상위 문항 점수에 따라 노출되는 문항)을 평가 양식에도 저장·검증할 수 있게 열었다. 평가 문항은 상위 문항 번호와 기준 조건(`parent_standard_kind`)이 **둘 다** 있을 때만 조건부로 본다. 그래서 예전 어드민이 방식 묶음 용도로 보내는 `parent_element_number`는 서버 보정 없이도 일반 문항으로 저장된다. 평가 영역(`AppraisalSection`) 문항도 같은 규칙으로 판정해 응답 화면에 `is_conditional`을 내려주고, 조건부 문항은 점수 반영(`check_score`)을 쓸 수 없게 막았다.

## 성과

**Before → After**

- 평가 양식 조건부 문항: `Element#conditional?`의 링크 타입 가드 때문에 저장해도 조건부로 읽히지 않았고, 저장 검증도 없었다. 이제 저장할 때 `ConditionalElementValidator`로 검증하고, 응답 엔티티에 `is_conditional: true`로 내려간다.
- 예전 어드민(`dev`)이 다중 방식 문항을 저장하는 요청: 계속 200이다. 판정 규칙이 기준 조건 없는 값을 걸러 내기 때문이다. 처음 설계는 "저장 시 null로 바꾸는 임시 보정 + 다음 릴리스에서 보정 제거 카드 + 3번 전용 정리 rake"였는데, 셋 다 필요 없어졌다.
- 응답 화면의 `is_conditional`: 영역 문항(`elements`)은 항상 `false`, 평가 대상자별 양식 문항(`use_appraisee_template.elements`)만 `true`가 될 수 있던 불일치 → 두 경로 모두 같은 규칙으로 내려간다.
- 숨긴 문항이 영역 점수 분모에 남는 문제: 점수 계산을 고치지 않고 "조건부 문항은 `check_score` 불가"(400)로 입력을 막아 분모에 들어갈 일 자체를 없앴다.
- 조건부 판정 위치: `conditional?` 한 곳과 검증기의 `parent_element_number.present?` 한 곳에 따로 있었다 → `Element.conditional_values?` 한 곳으로 모았고, 모델 인스턴스와 저장 전 요청 해시가 둘 다 이 규칙을 쓴다.

**측정 방법**

- 실측(2026-10-29, 사용자가 프로덕션 replica 조회): 평가 element의 `parent_standard_kind`·`parent_standard_score` non-null 0건. 옮길 데이터가 없으므로 계약을 새로 정할 수 있었다.

**검증 근거**

- `element_spec` · `base_entity_spec` · `template_pools_spec` 163건 실행: 154 통과, 9 실패. 실패 9건은 변경 전부터 있던 `icons` / `recommend` / `bulk index` 예시다(로컬 S3 설정 없음).
- 새로 넣은 예시: 평가 양식 생성 성공, 예전 어드민 묶음 요청 200, 기준 점수 누락 400, 부모 자격 위반 400, 점수 미반영 양식 400, 조건부 문항 점수 반영 400, 수정 시 부모 변경 400, 목록에서 뺀 문항은 검증하지 않음, 평가 양식·영역 문항의 `is_conditional`.
- 커밋은 성격별로 셋으로 나눴다: 양식 저장·검증 도입 / 평가 영역 조건부 판정과 `is_conditional` / 조건부 문항 `check_score` 차단.
- RuboCop: 바꾼 줄에서 지적 0건(클래스 메서드 위치 1건은 고침).

## 이번 작업에서 처음 배운 개념

- [x] [보편] **하위 호환은 임시 보정 대신 판정 규칙으로 흡수할 수 있다**
  - 구 클라이언트가 같은 컬럼에 다른 의미의 값(방식 묶음 번호)을 계속 보낸다. 이 값을 저장 시 지우는 보정 코드를 넣으면 "보정 제거"라는 후속 작업이 생기고, 보정이 살아 있는 동안은 규칙이 두 벌이 된다.
  - 대신 "조건부 = 상위 번호 **그리고** 기준 조건"처럼 **구 값이 절대 만족할 수 없는 조합**으로 의미를 정의하면 구 값은 저장돼도 무해하다. 남은 값은 정리 rake(2번 PR)가 지운다.
  - expand/contract 배포에서 contract 단계를 서두르지 않아도 되는 이유가 여기서 나온다.
- [x] [보편] **판정 규칙은 데이터 모양이 달라도 한 벌이어야 한다**
  - 응답 노출(`Element` 인스턴스)과 저장 검증(아직 저장 안 된 요청 해시)이 같은 질문 "이 문항이 조건부인가"를 따로 답하고 있었다.
  - 규칙을 인스턴스 메서드에 두면 해시에서 못 쓴다. 그래서 값만 받는 **클래스 메서드**(`Element.conditional_values?(link_type, parent_number, kind)`)로 규칙을 두고, 인스턴스 메서드는 자기 컬럼을 넘겨 위임하게 했다.
- [x] [Rails 전용] **`extend`로 객체 하나에만 모듈을 섞어 nested attributes 의미를 바꾸는 코드가 있다**
  - 평가 양식 수정은 `template_pool.extend(ModifyNestedAttributes)`로 그 인스턴스만 `assign_nested_attributes_for_collection_association`을 오버라이드한다. 요청 목록에 없는 문항에 `_destroy: true`를 붙여 **지운다**. 360은 그렇지 않다(요청에 없으면 유지).
  - 같은 엔드포인트라도 유형마다 "요청에 없는 문항"의 의미가 반대라서, "저장될 최종 상태"를 계산하는 검증기도 유형별로 다르게 합쳐야 했다.
- [x] [보편] **같은 데이터가 화면에 두 경로로 내려가면 "타입 기준 판정"이 경로마다 갈린다**
  - 응답 화면은 영역 설정에 따라 영역 문항(복사본, `AppraisalSection`) 또는 대상자별 양식 문항(`AppraisalTemplate`)을 받는다. 둘 다 같은 양식에서 왔는데 링크 타입으로 판정하니 한쪽만 `true`가 됐다.
  - 판정 기준을 정할 때 "이 값이 어떤 경로로 화면에 나가는가"를 엔티티부터 프론트 사용처(`Wrap.jsx`)까지 따라가 봐야 한다. 처음에 "응답 화면은 항상 false"라고 단정했다가 틀렸다.
- [x] [보편] **계산을 고치기 어려우면 입력을 제약해 그 상태가 생기지 않게 한다**
  - 숨긴 문항을 분모에서 빼려면 평가자마다 노출 여부를 판정해야 해서 범위가 컸다. 조건부 문항은 점수 반영을 못 쓰게 막으면 숨긴 문항이 분모에 들어갈 일이 없다.
  - 프론트가 이미 막고 있어도 서버에서 한 번 더 막는다. 360은 같은 규칙을 서버에 넣으면 기존 양식 저장이 400이 될 수 있어 넣지 않았다 — 새 검증은 기존 데이터에 먼저 비춰 본다.
- [x] [Rails 전용] **`abstract_class` 하위 클래스의 `polymorphic_name`은 자기 클래스명이다**
  - `TemplatePool`은 `self.abstract_class = true`라 STI가 아니다. 각 하위 클래스가 자기 테이블을 쓰므로 `element_link_type`에는 `Feedbackpool` / `AppraisalTemplate`이 그대로 들어간다(STI였다면 기반 클래스명이 들어간다).

## 작업하면서 막혔던 것과 해결 방법

1. **인계받은 카드 범위가 이미 낡아 있었다.** 카드에는 "임시 보정"과 "정리 rake"가 있었지만, 같은 날 판정 규칙으로 대체하기로 정해졌다. 카드 설명보다 인계 문서(결정 날짜 포함)를 우선했다.
2. **판정을 넓히기 전에 "읽는 쪽"을 전수 조사했더니 범위 밖 문제가 둘 나왔다.**
   - 평가 응답에는 서버 필수 검증이 아예 없다(`InitAppraiserResponsesService`는 범위 id와 점수 상한만 본다). 필수 여부는 ppfront만 막는다.
   - 영역 점수(`CreateResultSectionScoreService`)는 `check_score` 문항 전부를 분모에 넣으므로, 숨겨진 문항이 있으면 점수가 깎인다.
   - 처음 결론: 평가 영역은 조건부를 지원하지 않기로 해서 두 문제 모두 범위에서 뺐다.
   - 뒤집힌 결론: 대상자별 양식 경로로는 응답 화면에 `true`가 나간다는 걸 확인했고, "조건에 안 맞으면 숨기는 게 당연하다"는 제품 판단으로 평가 영역도 조건부로 판정하게 바꿨다. 필수 응답은 원래 서버 검증이 없어 프론트 몫으로 두고, 점수 분모는 `check_score` 차단으로 막았다. **읽는 쪽부터 세어 본 것**이 어디까지 서버가 책임지는지 정하는 근거가 됐다.
3. **Figma 시안을 못 읽었다.** Framelink 토큰 만료(403). 설정 의도(평가 양식에도 `check_scores` 필수인지)는 사용자 확인으로 정했다(360과 동일, 오류 문구에서 "피드백"만 뺌).
4. **360 상위 문항 조건을 서버·admin·ppfront 세 곳에서 대조했다.** 셋 다 "`check_score`를 켠 `choice` 문항"만 상위로 허용한다. 평가 다중 방식 문항에서는 이 조건을 만족하는 방식의 `number`를 가리키게 계약했다.
