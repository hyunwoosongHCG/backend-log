# [평가] 평가 양식 조건부 문항 도입과 방식 묶음 호환 보정 축소

> 날짜: 2026-10-29 ~ 2026-11-03  
> PR: [hcgtheplus/ppback#5699](https://github.com/hcgtheplus/ppback/pull/5699) (base: `dev`, 11-09 릴리스) · 백로그 ssq-backlog#1721  
> 소스: Performance Plus(실무) — Rails 8.1 · Grape · MySQL 8  
> 내 역할: 설계·구현 — 백엔드 단독. admin 조건부 작성 UI(talenx-admin #4665·#4678)와 응답 화면(ppfront #11634)은 FE 담당

## 작업 한 줄 요약

360 피드백에만 열려 있던 조건부 문항(상위 문항 점수에 따라 노출되는 문항)을 평가 양식에도 저장·검증할 수 있게 열었다. 같은 PR에서 평가 방식 묶음 호환 보정(`fill_method_group_number_from_legacy`)을 "지우기" 대신 "데이터 모양으로 대상을 좁히기"로 바꿨다. 원래 #5694(보정 제거) → #5697(구 값 정리 rake) → #5699 세 단계 스택이었는데, #5699 하나로 합치고 #5694·#5697은 닫았다. 평가 응답 저장에 넣었던 서버 조건부 처리는 속도 이슈로 이번 범위에서 뺐다.

## 성과

**Before → After**

- 평가 양식 조건부 문항: 저장해도 조건부로 읽히지 않았고 저장 검증이 없었다 → 양식 저장 검증(상위 문항 자격, 기준 조건 필수, 조건부 문항 `check_score` 불가)과 응답 엔티티의 `is_conditional`까지 연결했다.
- 조건부 판정: `Element`가 `element_link_type`으로 360·평가를 분기했다 → **값만 본다**(상위 문항 번호 + 기준 조건, 360·평가 공통). 판정이 연관 레코드를 읽지 않아 N+1 걱정이 없다.
- 조건부 동작 범위: 양식 영역(`item: template`)과 평가 대상자별 양식에서만 동작한다. 목표·핵심성과·배지·직무 영역은 평가 시작 때 문항을 복사하면서 조건부 설정 컬럼을 null로 비운다(`AppraisalSection#copy_elements_from`). 판정 코드가 아니라 **쓰는 시점에 보장**한다.
- 방식 묶음 보정: 저장 요청의 **모든 행**을 구 필드로 다시 계산해 덮어썼다 → `method_group_number` 키가 있는 행은 보낸 값 그대로, 키가 없는 행만 구 필드로 채우고, 조건부 행은 계산에서 뺀다. 그대로 뒀다면 새 어드민(#4665) 요청의 묶음이 전부 null이 되고 조건 문항이 상위 문항 묶음에 합쳐졌다.
- 응답 엔티티의 deprecated `is_optional` 노출 제거(운영 admin·ppfront는 이미 `isConditional`만 읽음).
- 평가 응답 저장의 숨긴 응답 정리·필수 조건부 검사: 구현하고 쿼리 수 spec까지 만들었다가 **이번 범위에서 뺐다**. 응답 저장이 이미 느려서(아래 기준값), 같은 문항·영역 조회를 더하는 대신 응답 처리 구조를 정리할 때 함께 다루기로 했다. 숨긴 응답은 ppfront가 보내지 않는다.

**측정 방법**

## 이번 작업에서 처음 배운 개념

- [x] [보편] **호환 코드는 지우는 대신 "데이터 모양으로 대상을 좁힐" 수 있다**
  - 보정을 지우면 "프론트가 먼저 나가면 묶음이 null로 덮이고, 백엔드가 먼저 나가면 구 탭이 깨지는" 배포 순서 의존이 생긴다.
  - 키가 있으면 신뢰하고(`key?(:method_group_number)`), 조건부 행은 계산에서 빼면 보정이 남아 있어도 새 클라이언트와 충돌하지 않는다. 지우는 일은 구 클라이언트가 사라진 뒤 다음 스프린트로 미룬다.
- [x] [Rails 전용] **`declared(params, include_missing: false)`로 "키가 없음"과 "null을 보냄"을 구분한다**
  - 보정 규칙이 `key?` 한 줄로 갈리는 이유다. null은 "단독 문항"이라는 뜻이라 그대로 저장하고, 키 자체가 없을 때만 구 필드로 채운다.
- [x] [보편] **판정 규칙을 둘 곳은 세 번 바뀌었다 — 마지막에 남은 건 "값만 보고, 정책은 쓰는 쪽에서 지킨다"**
  1. `Element`가 `case element_link_type`으로 분기 → 공통 모델이 모든 도메인 규칙을 앎
  2. 주인 모델에 위임(`conditional_element?` → `supports_conditional_elements?`) → 4개 모델에 상수 같은 메서드가 흩어져 "하드코딩처럼" 보였고, 판정이 `element_link`를 읽어 N+1이 숨었다
  3. 판정은 값만 보고, "양식 영역만 조건부"라는 정책은 평가 영역 문항이 만들어지는 **유일한 길(복사)** 에서 조건 값을 비워 지킨다
  - 3번이 가능했던 조건: 영역 문항을 쓰는 경로가 두 곳뿐이고 둘 다 같은 코드였다(전수 조사), 운영 데이터가 이미 그 보장을 지키고 있었다(조회). 이 둘을 확인하지 않고 바꿨다면 거친 변경이었다.
  - 대가: 판정 코드만 읽어서는 "목표 영역은 조건부가 아니다"가 보이지 않는다. 판정 주석에 보장 위치를 적었다.
- [x] [Rails 전용] **`has_many :through`·`ElementGroup#elements`로 불러온 레코드는 `inverse_of`로 부모가 채워지지 않는다**
  - 2번 구조에서 360 엔티티 5곳이 N+1이 됐다(리뷰 세션이 발견). 쿼리 수 검증을 판정이 쓰이는 경로 하나에만 해서 놓쳤다. 3번 구조로 바꾸면서 `includes(:element_link)`도 함께 걷어 냈다.
- [x] [보편] **응답이 어느 단위로 저장되는지 확인하기 전에 "영역 단위"라고 가정하면 안 된다**
  - `AppraisalResponse`의 유일성 scope는 `objective_id`·`key_result_id`·`badgepool_id`·직무 질문 id까지 포함한다. 목표·직무 영역은 같은 문항이 목표·직무 질문마다 따로 응답된다. 리뷰 세션 지적으로 확인했고, 항목 단위 판정 대신 "양식 영역에서만 동작"으로 범위를 줄였다.
- [x] [보편] **검증을 하나 더 넣는 것도 비용이다 — 이미 느린 엔드포인트에서는 측정부터**
  - 숨긴 응답 정리·필수 조건부 검사를 서버에 넣고 쿼리 수까지 고정했지만, 엔드포인트가 이미 P95 511ms였고 응답마다 쿼리가 반복되는 구조였다. 같은 문항 조회를 한 번 더 하는 대신 프론트가 숨긴 응답을 보내지 않는 것으로 두고, 서버 처리는 응답 구조를 정리할 때로 미뤘다.
  - Skylight의 Agony는 느린 정도와 요청량을 함께 본 **앱 안 상대 순위**라, 배포 전후 비교에는 P50·P95를 쓴다.
- [x] [보편] **같아 보이는 두 기능을 합치기 전에 "계약"이 같은지부터 본다**
  - 평가 필터와 360 응답 검증기를 합치는 안을 검토했다. 360은 숨긴 문항의 응답을 **받아서 저장하고 결과 화면에서만 숨긴다**(2024-01 #3704 도입 때 #sq-perf에서 화면 단계 처리로 정한 것이 굳음, 명시적 결정 기록은 없음). 평가는 저장하지 않기로 했다. 범위(영역 vs 360 피드백)·입력 키·결과 형태도 달라서, 합치면 차이를 흡수하는 층이 공통 로직보다 길어진다(과도한 추상화).
- [x] [Rails 전용] **`extend`로 객체 하나에만 모듈을 섞어 nested attributes 의미를 바꾸는 코드가 있다**
  - 평가 양식 수정은 `template_pool.extend(ModifyNestedAttributes)`로 그 인스턴스만 요청 목록에 없는 문항을 `_destroy`한다. 360은 그렇지 않다. 저장 검증기도 유형별로 "최종 상태"를 다르게 합쳐야 했다.
- [x] [Git/GitHub] **스택 PR을 접는 법: `git rebase --onto`와 `gh stack unstack`**
  - `git rebase --onto origin/dev <아래 PR의 마지막 커밋> <브랜치>`로 위 PR 커밋만 옮긴다. 원격이 다른 세션에 의해 다시 쓰였으니 경계는 원격 기준으로 확인했다.
  - 스택에 묶인 PR은 base를 바꿀 수 없다. 스택 번호는 PR REST 응답의 `stack` 또는 GraphQL `pullRequest.stack.number`로 찾고 `gh stack unstack <번호>`로 푼다(PR을 닫거나 브랜치를 지우지 않음).
  - 강제 push는 확인한 원격 해시에 고정한 `--force-with-lease=<브랜치>:<해시>`로 했다.

## 작업하면서 막혔던 것과 해결 방법

1. **방침이 여러 번 바뀌었다.** 임시 보정 + 정리 rake → 판정 규칙으로 흡수 → 보정을 두고 좁히기 + 구 값 정리는 다음 스프린트 → 응답 서버 처리 추가 → 속도 이슈로 제외. 매번 근거는 새로 얻은 사실이었다(프로덕션 조회, 테스트 세션 재현, 리뷰 지적, Skylight 수치). 카드 설명보다 가장 최근 결정과 그 근거를 우선했다.
2. **"읽는 쪽"을 전수 조사했더니 범위 밖 문제가 나왔다.** 평가 응답에는 서버 필수 검증이 없고, 영역 점수는 `check_score` 문항 전부를 분모에 넣는다. 조건부 문항은 `check_score`를 못 쓰게 막아 점수 문제를 입력 단계에서 없앴다.
3. **같은 브랜치를 여러 세션이 만졌다.** 내 worktree에 다른 세션의 미커밋 변경(360 N+1 수정)이 있었고, 원격 브랜치에 다른 세션의 커밋(dev 병합, 문구 원복)이 쌓였다. 지우거나 덮지 않고 내용을 확인한 뒤 내 커밋을 그 위에 쌓았다.
4. **dev가 gem을 올려서(`jwt 2.10.3`) 테스트 볼륨이 쓸모없어졌다.** worktree 전용 bundle 볼륨에만 `bundle install`을 했다.
5. **#5694를 닫으면 사라질 합의가 있었다.** 승인된 PR의 리뷰 합의(`theplus-front`의 `isOptional`은 사용자가 없어 대응하지 않음, E2E 시드, 배포 순서)를 #5699 본문으로 옮긴 뒤 닫았다.
6. **PR 코멘트에 인용을 쓸 때 실제 발언과 대조했다.** 초안이 슬랙 발언을 바꿔 따옴표로 인용하고 있어서 실제 문장으로 고쳤다. 리뷰 코멘트는 사용자의 pending 리뷰가 있어 단독 인라인 코멘트가 막혔고(422), pending 리뷰에 추가하는 방식으로 붙였다.

## 다음에 더 공부하고 싶은 것

- 평가 응답 저장의 응답 행마다 반복되는 쿼리(discard, 유일성 검증, insert)를 콜백·검증을 지키면서 일괄 처리로 바꾸는 방법
- 목표·핵심성과·배지·직무 영역에서 조건부를 지원하려면 항목(목표·직무 질문) 단위 응답 키를 어떻게 모델링해야 하는가

- 평가 대상자별 양식 복사(`deep_clone(includes: ...)` 오타로 양식이 복제되지 않는 것으로 보임)가 진행 중인 평가에 주는 영향
