> 브랜치: `feature/key-result-auto-checkin-reflect`

## 작업 한 줄 요약

어제 리뷰한 "조상 KR 전역 순서 락" 방식이 접히고, 상위 핵심성과 자동 반영을 **체크인 트랜잭션 안의 아웃박스 기록 + 커밋 후 Sidekiq 워커**로 옮기는 구현을 직접 했다. 어제 기록 마지막에 적은 "전제를 놓으면 같은 기계가 ~15줄이 된다"가 실제로 그렇게 됐다.

## 어제 기록과 이어지는 지점

어제 결론: 락 기계 90줄은 **"체크인과 상위 반영이 한 트랜잭션이어야 한다"는 전제 하나**에서 파생됐고, 전제를 놓으면 훨씬 작아진다.

오늘 그 전제를 실제로 놓았다. 락 구현 전체(`with_ancestor_locks`, `LockPreconditionError`, 진입점 8곳 래핑)는 stash에만 남기고 폐기했다. 남은 락은 워커 안의 한 줄이다.

```ruby
ActiveRecord::Base.transaction(isolation: :read_committed) do
  Objective.where(id: lock_objective_ids).order(:id).lock.load   # 첫 문장
  Objective::CheckIns::ReflectToSuperKeyResultService.call(event: event)
  event.update!(processed_at: Time.current)
end
```

어제 배운 "락을 트랜잭션이 열리기 **전에** 잡아야 한다"는 제약이, **새 트랜잭션을 워커에서 직접 열면 첫 문장으로 잡을 수 있으니** 자연스럽게 사라졌다. 제약을 우회한 게 아니라 제약이 성립하는 조건 자체를 없앤 것.

## 이 작업에서 처음 배운 개념

- [x] **트랜잭션 아웃박스를 서비스 *내부*에서 쓰기** ([레슨 56](../lessons/0056-outbox-moving-the-transaction-boundary.html)) — 로드맵 §5의 "2PC → Saga → Outbox"([레슨 32](../lessons/0032-distributed-transaction-2pc-saga-outbox.html))는 **서비스 간** 메시지 유실을 막는 패턴으로 배웠는데, 이번엔 **같은 DB 안에서 트랜잭션 경계를 쪼개려고** 썼다. 목적이 다르다: 메시지 유실 방지가 아니라 "무거운 후처리를 커밋 밖으로 빼되, 후처리가 필요하다는 사실만은 원자적으로 남기기". `key_result_reflection_events` 행은 체크인과 같은 트랜잭션이라 커밋과 워커 발행 사이에 프로세스가 죽어도 남는다.
- [x] **`after_commit`은 최외곽 커밋에서 발화한다** — 진입점 6곳 중 5곳이 이미 바깥 트랜잭션 안(벌크 승인은 배치 전체가 한 트랜잭션)이라 발행 시점이 걱정이었는데, Rails가 중첩 트랜잭션의 `after_commit`을 **최외곽 커밋까지 미뤄서** 실행해준다. 그래서 진입점 재구성 없이 모델 콜백 한 줄로 끝났다. 콜백 안에서는 예외를 삼켜야 한다 — 이미 커밋된 트랜잭션은 되돌릴 수 없으므로, Redis 장애로 발행이 실패했다고 사용자 체크인을 500으로 만들면 안 된다.
- [x] **`dependent: :destroy`는 선언 순서대로 실행된다** — 새 테이블이 `objectives`와 `check_in_revisions`를 둘 다 FK로 참조하는데, `Objective`에서 `has_many :check_in_revisions`보다 **먼저** 선언해야 목표 삭제 시 참조하는 revision보다 먼저 정리돼 FK 위반이 안 난다. 처음엔 뒤에 썼다가 주석과 코드가 어긋나서 알아챘다.
- [x] **회귀 스펙의 판별력(discriminating power)을 따로 검증해야 한다** ([레슨 55](../lessons/0055-regression-spec-discriminating-power.html)) — 어제 "저자의 근거를 검증하는 방법을 몰랐다"고 적었는데, 오늘은 **내가 쓴 스펙**을 같은 방식으로 의심했다. 워커의 `.lock`을 임시로 빼고 돌려봤더니 값 수렴 스펙 2개가 **그대로 통과**했다. 이유: 두 체크인을 워커 실행 **전에** 모두 커밋해두면 두 워커가 같은 값을 계산해서 경합 자체가 성립하지 않는다. 통과하는 초록색이 아무것도 증명하지 않고 있었다.
- [x] **경합을 재현하려면 인터리빙을 강제해야 한다** — 위를 고치려고 첫 반영이 값을 계산한 **뒤에** 형제 체크인을 커밋하도록 순서를 강제했다(`Queue`로 계산 직후 일시정지 → 형제 커밋 → 두 번째 워커 시작 → 재개). 이제 락을 빼면 90 대신 50이 나오며 실패한다.

## 되돌린 결정 — 이력은 반드시 하위 수만큼 남아야 한다

위 귀인 문제를 보고받은 뒤 "값 정확성을 얻더라도 이력은 3건 0→100→150→250으로 남겨야 한다"는 요구가 확정됐다. 그래서 설계를 한 번 더 바꿨다.

**워커가 자기 이벤트 하나만 처리하지 않고, 잠근 조상 집합 안에서 끝나는 미처리 이벤트를 id 오름차순으로 이어서 처리한다.** 그리고 각 단계에서 **아직 반영되지 않은 형제를 체크인 전 값으로 본다.**

| 단계 | 계산 | 값 | 이력 |
|---|---|---|---|
| e1 (C1) | (100 + **0** + **0**)/3 = 33.33% | 100 | 0 → 100 |
| e2 (C2) | (100 + 50 + **0**)/3 = 50% | 150 | 100 → 150 |
| e3 (C3) | (100 + 50 + 100)/3 = 83.33% | 250 | 150 → 250 |

여기서 처음 배운 것:

- [x] **"체크인 전 값"은 이미 아웃박스에 있었다** — 목표 연계는 `source_prev_progress`, 핵심성과 가져오기는 `check_in_revision.data[].prev`. 이력 표기용으로만 저장해둔 값이 **값 계산의 입력으로 승격**됐다. 스키마를 설계할 때 "이 컬럼이 나중에 계산 입력이 될 수도 있다"는 여지를 남겨둔 게 결과적으로 유리했다.
- [x] **`KeyResult#progress(value = self.value)`가 인자를 받는다** — 그래서 `prev` 값을 진행률로 환산하는 로직을 새로 쓸 필요가 없었다. `interval` kind의 `key_result_option.calculate_progress`까지 그 안에서 처리된다. **기존 메서드의 시그니처를 먼저 읽어본 덕에 중복 구현을 피했다.**
- [x] **드레인 범위는 "잠근 행"으로 제한해야 한다** — 잠그지 않은 조상까지 닿는 이벤트를 같이 처리하면 갱신 손실 방어가 무너진다. 그래서 후보 이벤트의 조상 집합이 내가 잠근 집합의 **부분집합일 때만** 드레인한다. 다행히 같은 상위에 붙은 형제들은 조상 집합이 동일해서, 정작 필요한 케이스는 전부 커버된다.
- [x] **다단계는 이 보정이 필요 없다** — 조부모는 중간 부모의 KR 값을 통해 전파받으므로, 부모의 값이 단계적으로 오르면 조부모도 자동으로 단계적으로 오른다. 보정이 필요한 건 **같은 부모에 직접 붙은 형제**뿐이었다. 처음엔 전체 계층에 보정을 퍼뜨려야 한다고 생각했는데, 전파 구조를 따라가 보니 아니었다.

## 리뷰 지적에서 나온 것들

설계가 끝난 뒤 받은 지적 세 개가 전부 실재했고, 그중 둘은 내가 측정하지 않은 축이었다.

- [x] **잠금 범위도 가지치기해야 한다, 다만 그냥 좁히면 안 된다** — 잠금 대상을 eligibility 없이 체인 끝까지 모으고 있었다. 측정하니 옵션이 꺼진(기본값!) 조상·구간관리 조상·승인 대기 조상까지 잠기고, **서로 다른 팀의 반영이 아무도 쓰지 않는 공통 조상에서 락을 공유해 직렬화**됐다(교집합 1개 → 0개). 그런데 `stage`는 승인마다 바뀌므로 가지치기만 하면 사전 조회 이후 잠기지 않은 목표에 쓸 수 있다. **"좁히고 + 어긋나면 예외 + 사전 조회부터 재시도"** 세 개가 한 세트여야 안전하다. 조용히 틀리는 대신 시끄럽게 실패하고 자동 회복하는 형태.
- [x] **성능 측정에는 여러 축이 있고, 한 축을 재고 다 쟀다고 착각하기 쉽다** ([레슨 55](../lessons/0055-regression-spec-discriminating-power.html)) — 락 보유를 "같은 조상을 공유하는 배치 크기" 축으로 재고 만족했는데, 지적받은 건 **"워크스페이스 전체 미처리 이벤트 수"** 축이었다. 재보니 후보마다 재귀 조회를 돌아 이벤트당 쿼리가 5N, 120건에서 스캔 1회 337ms·596쿼리·전체 13.14초였다. 후보를 잠근 목표의 직계 하위로 SQL 단계에서 좁혀 이벤트당 쿼리 24.0 고정(O(N))으로 바뀌었다. **"무엇을 재지 않았는지"를 스스로 묻는 습관이 없었다.**
- [x] **인덱스가 있다 ≠ 인덱스가 쓰인다** — 2,000행 적재 + `ANALYZE` 후 EXPLAIN을 보니 MySQL이 복합 인덱스가 아니라 `workspace_id` 단독 인덱스를 **풀스캔**(`type: index`, 2,331행)했다. `ORDER BY id`의 filesort를 피하려고 11.7배 더 읽는 선택이었다. `[workspace_id, objective_id, processed_at]`로 바꿔 `type: range` + `Using index` 커버링(200행)이 됐다. **인덱스를 추가한 것으로 끝내지 말고 EXPLAIN으로 확인해야 한다.** 행이 없으면 통계가 없어 EXPLAIN이 의미 없다는 것도 같이 배웠다.

## 이 PR과 무관했던 기존 결함들

조사하다 나온 것들. 인과관계가 없어 이 PR에서 빼고 별도 리포트로 넘겼다 — **결함을 발견한 것과 그것을 지금 고치는 것은 별개 판단**이라는 게 이번의 교훈.

- **`update(stage:)`의 silent failure** — `update`는 validation 실패 시 예외 없이 `false`만 돌려주고, 반환값을 확인하지 않으면 "revision은 accepted인데 stage는 pending"인 고장 상태가 영구히 남는다. 재현했다: `update` 반환값 `false` → stage 그대로 → `UpdateAccepted` 이력만 남음 → 다시 승인하면 `objective_revision_diff.rb:17`에서 `NoMethodError: undefined method 'each' for nil`. **트랜잭션을 추가해도 안 고쳐진다** — 예외가 안 나니 롤백도 안 된다. `update!` 전환이 함께 가야 한다. `git log -L`로 2022-02-17 커밋까지 올라가는 것도 확인.
- **Sentry로 실제 발생량을 확인하는 법** — `PERPL-BACK-44H`(batch_approval, 7건) + `PERPL-BACK-44F`(단건 update_approval, 5건). 둘 다 같은 워크스페이스의 **같은 목표 하나**에서 17분간 12회 500. 한 사람이 12번 시도하고 포기한 흔적. **빈도(낮음)와 심각도(영구적·자력 복구 불가)를 따로 봐야 한다**는 걸 숫자로 배웠다. `search_events`의 aggregate로 `count()`·`min/max(timestamp)`를 뽑으면 "몇 명이 며칠 동안"이 바로 나온다.
- **`Objective#destroy!`가 이미 깨져 있었다** — `has_many :images`가 폴리모픽 연관(`images.target_type/target_id`)인데 `as: :target`을 빼먹어 `images.objective_id`를 찾는다. 그래서 내 `dependent: :destroy`를 실제 파기 경로로 검증할 수 없었고, **선언 순서 불변식을 직접 단정하는 스펙**으로 대체했다(순서를 뒤집어 실패하는지도 확인). 검증하려던 경로가 이미 고장나 있을 수 있다.

## 이번에 직접 검증한 것

- **격리수준은 실제로는 없어도 통과한다.** `isolation: :read_committed`를 빼고 동시성 스펙을 돌려도 11개 전부 통과했다. 어제 배운 규칙(잠금 읽기는 read view를 열지 않는다) 때문에, 잠금 SELECT가 첫 문장이면 기본 REPEATABLE READ로도 스냅샷이 락 이후에 고정되기 때문이다.
  그럼에도 명시하기로 한 이유는 **그 보장이 코드로 강제되지 않는 암묵 전제**라서다. 이 트랜잭션 안에 잠금 SELECT보다 먼저 실행되는 조회가 한 줄만 들어가도 갱신 손실이 되살아나고 **테스트는 통과한다**(방금 그걸 겪었다). 명시적 격리수준은 그 전제에 의존하지 않게 하고, 이미 열린 트랜잭션 안에서 호출되면 `TransactionIsolationError`로 시끄럽게 터진다.
  → "동작하니까 됐다"와 "보장되니까 됐다"는 다르다는 걸 처음으로 코드 선택 근거로 써봤다.
- **환경 실측** (`ppback-db-1`): MySQL 8.4.11 / `REPEATABLE-READ` / `binlog_format=ROW`(READ COMMITTED 복제 안전) / `innodb_deadlock_detect=ON` / `innodb_lock_wait_timeout=50`. 레포에 `isolation:` 사용 선례는 없었다 — 이번이 최초.
- **락이 실제로 걸리는지 `performance_schema.data_locks`로 확인.** 어제 "다음에 공부할 것"에 적었던 항목을 바로 썼다. `LOCK_DATA` 컬럼에 PK 값이 들어와서, 값 계산 시작 시점에 상위 목표 행이 잠겨 있는지 스펙으로 단정할 수 있었다.
- **락 보유 시간을 측정했다** — 어제 "숫자로 말하지 못했다"고 적은 그 항목이다. 하위 N개가 같은 상위에 붙은 최악 구조 + 배치 전체 1트랜잭션 승인:

  | 하위 수 | 사전조회(락 밖) | 락 보유 | 이벤트당 | 이력 |
  |---|---|---|---|---|
  | 5 | 31ms | 1.06초 | 212ms(워밍업) | 5건 |
  | 20 | 122ms | 1.27초 | 63ms | 20건 |
  | 50 | 65ms | 4.26초 | 85ms | 50건 |
  | 160 | 183ms | 11.29초 | 71ms | 160건 |

  `innodb_lock_wait_timeout` 50초까지 약 4.4배 여유(≈700건). 어제 접힌 락 방식은 50건에 15.9초 / 약 160건에서 timeout이었으니 **50건 기준 3.7배 개선**. 다만 순차 드레인을 도입하면서 **"락 보유가 배치 크기와 무관"이라는 성질은 일부 내놓았다** — 이력 요구를 만족시키기 위한 의도된 교환이다.
  측정 방법: `Process.clock_gettime(Process::CLOCK_MONOTONIC)`으로 사전조회 구간과 트랜잭션 구간을 나눠 재고, 라이브 Sidekiq이 끼어들지 못하게 `perform_async`를 no-op으로 덮었다.
- 스펙: 목표 관련 전체 **434 examples 0 failures**(`RUN_CONCURRENCY_SPECS=1` 포함).
- QA 가이드 콘솔 스크립트를 실제로 돌려 검증: S24(전체 토폴로지) **15건 PASS**, S25(kind 혼합 배치) **12건 PASS**, 2회 연속 동일.
- 이력 시퀀스가 **경로와 무관하게 같아진 것**도 확인: batch_approval API(배치 전체 1트랜잭션)와 어드민 벌크 워커(목표당 1트랜잭션) 모두 `0→100→150→250` 3건.

## 작업하면서 막혔던 것

- **스펙이 실행 순서에 따라 갈렸다.** 워커 스펙 8개 중 1개만 `TransactionIsolationError`로 실패했다. 원인은 DatabaseCleaner의 바깥 트랜잭션이 **첫 예제에만** 열려 있고 이후 예제에는 없다는 것 — 즉 어떤 예제가 첫 번째로 실행되느냐에 따라 결과가 달라지는 상태였다. 프로브 스펙을 하나 만들어 `transaction_open?`을 직접 찍어보고서야 알았다.
  해결: 격리수준을 쓰는 파일은 `:truncation` 태그로 **바깥 트랜잭션 없이** 돌리게 했다. 어제 `:concurrency` 태그로 만들어뒀던 규약을 `:truncation`까지 포함하도록 넓혔다.
- **`after_commit`이 스펙에서 발화하는지 몰라서 잘못 가정했다.** 계획 단계에서는 "DatabaseCleaner `:transaction`이면 발화 안 한다"고 전제하고 스펙 전략을 짰는데, 실제로 돌려보니 **발화했다**(`perform_async`가 2번 불린 걸로 들켰다 — 콜백 + 내가 수동 호출). 문서/전해 들은 내용이 아니라 실행 결과가 기준이어야 한다는 걸 또 확인했다.
- **배치 승인의 `AutoCheckedIn` 이력 건수가 줄어드는 걸 QA 스크립트가 잡아줬다.** 예전엔 하위 3개면 3건이었는데 1건이 됐다 — 배치가 한 트랜잭션이라 세 하위 값이 모두 커밋된 뒤 워커가 돌고, 전량 재계산이라 첫 이벤트가 이미 최종값을 쓰기 때문. 최종값은 같지만 감사 이력의 결이 달라진다. 내가 예상 못 한 파급이었고, **문서에 있던 검증 스크립트를 실제로 돌려봤기 때문에** 발견했다.
- 그런데 그 건수가 실행마다 1이 됐다 2가 됐다 했다. dev에 진짜 Sidekiq이 떠 있어서 스크립트의 수동 소진과 경합하고 있었다. 처음엔 건수 단정을 포기하고 "존재하는가"로 바꿨다 — **비결정적인 것을 단정하는 스펙은 없는 것만 못하다.**
- **그리고 남은 1건의 귀인이 틀렸다는 게 더 큰 문제였다.** payload를 직접 떠 보니 `source`가 `C1` 하나만 가리키면서 `0→250`을 기록한다. 실제로는 셋이 함께 만든 값이고, C1 혼자면 100이어야 한다. "이력이 줄었다"가 아니라 "남은 이력이 거짓말을 한다"였다. **건수만 세지 말고 payload를 열어봐야 알 수 있는 종류의 결함이다.**

- **가지치기를 넣자 새 구멍이 드러났다.** 잠금 대상을 좁히니 사전 조회 이후 조상이 늘어난 경우 `drainable_event_ids`가 **트리거 이벤트 자신을 부분집합 조건에서 탈락**시켜, 잡이 조용히 아무것도 안 하고 성공으로 끝났다. 이벤트는 미처리로 남고 그 잡은 다시 오지 않으니 고아가 된다. 스펙이 실패해서 알았다 — 가지치기를 안 했으면 이 구멍을 못 봤을 것이다. **최적화가 숨은 결함을 드러내는 경우가 있다.**
- **마이그레이션이 롤백 불가였고, 외래키가 조용히 사라져 있었다.** PR 체크리스트에 "롤백 가능"이라고 적었는데 실제로 `db:rollback`을 돌려보니 `add_foreign_key(column:)`의 자동 역방향이 제약을 못 찾아 실패했다. 더 나쁜 건 그 실패한 롤백 시도가 FK를 지워서, **`SHOW CREATE TABLE`에는 FK가 하나도 없는데 `db/schema.rb`는 4개가 있다고 주장**하는 상태가 됐다는 것. `change` → `up`/`down`(`down` = `drop_table`)으로 바꾸고 실제로 drop·재생성해 검증했다. **schema.rb를 진실로 믿지 말고 DB에 직접 물어봐야 한다. 그리고 롤백은 "된다고 적는 것"이 아니라 "돌려보는 것"이다.**
- **죽은 팩토리를 남겼다.** `spec/factories/key_result_reflection_event_factory.rb`가 미사용이었을 뿐 아니라 NOT NULL 외래키 4개가 비어 있어 **호출하면 실패하는** 팩토리였다. 각 스펙이 시나리오마다 특정 objective/revision에 정확히 물려야 해서 결국 직접 `create!`로 만들었는데, 계획 단계의 팩토리를 지우지 않았다. 레포에 `FactoryBot.lint`가 없어 아무도 잡지 못한다. **"만들어뒀다가 안 쓴 것"을 스스로 훑는 패스가 필요하다.**
- **annotate가 클래스 상단 주석을 덮어쓴다.** `position_in_class: before` 설정이라 클래스 직전 주석 블록을 스키마 정보로 교체한다. 아웃박스가 왜 필요한지 적어둔 설명이 `db:migrate` 한 번에 통째로 사라져 있었다. 클래스 본문 안으로 옮겨 해결.

## 다음에 더 공부하고 싶은 것

- 어제 적은 항목 중 아직 그대로인 것: 낙관적 락(`lock_version`) 트레이드오프.
- **정정** — 어제 "CI가 이 PR의 핵심 회귀를 안 돈다"고 적었고 오늘도 그 전제로 몇 번 말했는데, 확인해보니 틀렸다. `.github/workflows`에는 스펙 실행이 없어서 "CI 없음"으로 결론냈지만, 실제로는 **PR 오픈 시 AWS(CodePipeline/CodeBuild) 쪽에서 돈다.** 레포 안에 CI 정의가 없다고 CI가 없는 게 아니다 — 파이프라인이 레포 밖에 있을 수 있다는 걸 놓쳤다. 다음엔 `.github/`만 보고 단정하지 말고 배포/빌드 경로를 먼저 물어봐야 한다.
- 아웃박스 행의 수명 관리 — 폴링 워커를 두지 않기로 해서, 발행이 유실된 이벤트는 영원히 미처리로 남는다. 스위퍼/클린업 cron을 언제 붙일지 판단하는 기준(테이블 증가 속도, 유실 빈도 관측)을 모른다.
- 감사 이력(audit trail)을 **설계 산출물로 먼저 정의하는 법.** 이번엔 값 정확성만 요구사항으로 잡고 이력은 부산물로 취급했는데, 결과적으로 이력 요구가 설계를 되돌렸다. "무엇이 이력에 남아야 하는가"를 값 설계와 같은 급으로 먼저 못 박아야 했다.
- 락 보유 시간을 줄이는 방법 — 드레인 크기를 상한(예: 50건)으로 끊으면 락은 짧아지지만, "미반영 형제"를 드레인 밖의 이벤트까지 포함해야 해서 **발행이 유실된 이벤트가 형제를 영구히 옛 값에 묶는** 더 나쁜 실패 모드가 생긴다. 상한을 안전하게 두는 방법을 모른다.
- 이벤트당 70ms의 내역 — `reflect_source_*`가 매 이벤트마다 연계 하위 전체를 다시 조회한다. N²에 가까운 구조인데 160건까지는 이벤트당 시간이 평평했다. 어디서 꺾이는지, 어떻게 재는지.
