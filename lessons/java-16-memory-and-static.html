자바 메모리 구조와 static

자바 · 실전 자바 기본편 섹션 8 ~25분
🎯 지금까지 new Student()가 "메모리 어딘가에 객체를 만든다"고만 말하고 넘어갔다. 이번엔 그 "어딘가"를 정확히 나눠본다. 그리고 "인스턴스마다 따로가 아니라 클래스 전체에 딱 하나만 있어야 하는 값"(생성된 개수 세기 같은)을 어떻게 만드는지도 함께 본다.
강의를 수강하지 않고 작성한 레슨이다. 김영한 「실전 자바 - 기본편」 섹션 8의 전개와 예제는 수강생 정리 글을 교차 확인해 따라갔다(하단 출처 — 이번 섹션은 2편만 확인됐다, 정확한 출처만 밝힌다). Ruby·TypeScript 대비와 뿌 연결은 직접 쓴 것이다.

핵심 한 줄

자바 메모리는 메서드 영역 · 스택 · 힙 세 곳으로 나뉜다. static은 인스턴스가 아니라 "클래스 자체"에 붙는 값이라, 객체를 몇 개를 만들든 메서드 영역에 딱 하나만 존재한다.

세 영역 — 메서드 영역 · 스택 · 힙

메서드 영역(Method Area)
클래스 정보를 보관한다 — java-10에서 본 거푸집 자체다. 실행 코드(바이트코드), 필드·메서드 정보, 그리고 오늘 배울 static 변수가 여기 있다. 프로그램 시작부터 끝까지 딱 하나, 모든 곳에서 공유된다.
↓
스택 영역(Stack Area)
메서드를 호출할 때마다 스택 프레임이 하나씩 쌓인다. 지역 변수(매개변수 포함)가 여기 담기고, 메서드가 끝나면 그 프레임째로 사라진다 — 생존 기간이 가장 짧다.
↓
힙 영역(Heap Area)
new로 만든 객체(인스턴스)가 실제로 담기는 곳 — 거푸집으로 찍어낸 블록 하나하나다. 아무도 참조하지 않게 되면 GC(가비지 컬렉션)가 회수한다.

java-10의 거푸집 비유를 메모리 영역에 그대로 포갤 수 있다: 거푸집(클래스 정보)은 메서드 영역에 하나, 찍어낸 블록(인스턴스)은 힙에 여러 개. 그런데 거푸집 자체에도 값을 붙이고 싶을 때가 있다 — "지금까지 몇 개를 찍어냈나" 같은 값은 블록 하나하나가 아니라 거푸집 쪽에 있어야 앞뒤가 맞는다.

인스턴스 필드로는 안 되는 것

Data 객체가 지금까지 몇 개 만들어졌는지 세고 싶다고 하자. 인스턴스 필드로 시도하면 이렇게 된다. 

public class Data3 {
    String name;
    int count;   // ❌ 인스턴스 필드로 시도

    Data3(String name) {
        this.name = name;
        count++;          // 매번 자기 자신의 count만 1이 된다
    }
}

Data3 data1 = new Data3("A");
Data3 data2 = new Data3("B");
System.out.println(data1.count);   // 1 — data2와 무관하게 자기 것만
System.out.println(data2.count);   // 1 — 마찬가지

각 인스턴스는 힙에 따로 만들어지므로 count도 인스턴스마다 따로 생긴다. "전체 개수"라는 건 애초에 인스턴스 하나가 알 수 있는 값이 아니다 — 클래스 자체가 기억해야 하는 값이다.

static — 클래스에 딱 하나

public class Data3 {
    String name;
    static int count;   // static — 메서드 영역에 딱 하나

    Data3(String name) {
        this.name = name;
        count++;
    }
}

Data3 data1 = new Data3("A");
System.out.println(Data3.count);   // 1
Data3 data2 = new Data3("B");
System.out.println(Data3.count);   // 2 — data1과 공유된다

static이 붙는 순간 count는 힙이 아니라 메서드 영역에 자리 잡고, 모든 인스턴스가 같은 count 하나를 공유한다. 접근할 때도 data1.count가 아니라 Data3.count처럼 클래스 이름으로 쓰는 게 관례다 — 인스턴스 것이 아니라는 걸 코드로도 드러낸다.

직접 타이핑해보기 — Data3(String name) 생성자를 작성하세요. this.name에 매개변수를 대입하고, static 필드 count를 1 증가시킵니다.

인스턴스 변수 vs 클래스 변수

인스턴스 변수 클래스 변수(static)
저장 위치 힙 영역 메서드 영역
생성 시점 new할 때마다 클래스 로딩 시 딱 1개
접근 방식 인스턴스 필요 클래스명으로 바로
생명주기 그 인스턴스가 GC될 때까지 JVM이 끝날 때까지

생존 기간으로 줄 세우면 지역 변수 < 인스턴스 변수 < 클래스 변수 순으로 길어진다. static을 "정적"이라 부르는 이유도 여기 있다 — 프로그램이 시작할 때 자리를 잡고(=클래스 로딩 시점), 끝날 때까지 그 자리에서 안 움직인다.

static 메서드 — 객체 없이 부르기

public class Data3 {
    String name;
    static int count;

    Data3(String name) {
        this.name = name;
        count++;
    }

    static int getCount() {
        return count;
    }
}

System.out.println(Data3.getCount());   // 객체 없이, 클래스 이름으로 바로 호출

static 메서드는 객체를 만들지 않고도 클래스 이름으로 바로 부를 수 있다. 지금까지 써온 public static void main(String[] args)도 사실 static 메서드였다 — 프로그램이 시작될 때는 아직 만들어진 객체가 하나도 없으니, 객체 없이도 불릴 수 있는 진입점이 필요했던 것이다.

대신 대가가 있다. static 메서드 안에서는 인스턴스 필드·인스턴스 메서드를 직접 쓸 수 없다. static 메서드는 "어느 인스턴스의 것"인지 알려주는 참조값 없이 클래스 이름만으로 호출되기 때문이다 — this가 가리킬 대상 자체가 없다. 

static void wrong() {
    name = "x";   // ❌ 컴파일 에러 — name은 인스턴스 필드라 "어느 객체의 name"인지 알 수 없다
}

static void okWithParam(Data3 data) {
    data.name = "x";   // ✅ 매개변수로 받은 특정 인스턴스라면 접근 가능
}

매개변수로 인스턴스를 직접 받으면 그 안에서는 인스턴스 필드도 건드릴 수 있다 — 막힌 건 "인스턴스 필드"가 아니라 "어느 인스턴스인지 모르는 상태에서 인스턴스 필드에 접근하는 것"이다.

직접 타이핑해보기 — 객체 없이도 호출할 수 있는 getCount() 메서드를 작성하세요. static 필드 count를 반환합니다. 반환 타입은 int입니다.

Ruby의 클래스 변수(@@count)와 클래스 메서드(def self.count)가 정확히 이 역할이다. TS의 static 키워드도 문법·의미가 자바와 거의 그대로 겹친다. 다만 Ruby의 @@는 상속 관계에서 자식·부모가 같은 변수를 진짜로 공유해서 의도치 않게 꼬이는 경우가 있는데, 자바의 static은 그런 함정 없이 "이 클래스에 딱 하나"라는 규칙이 더 단순하고 명확하다.

뿌에서는 이렇게 보인다

스프링 빈은 기본적으로 싱글턴이다 — 컨테이너 안에 그 타입의 인스턴스가 딱 하나만 만들어지고, 모든 요청이 그 하나를 공유한다. static 필드와 똑같지는 않지만(빈은 여전히 인스턴스 하나이지 클래스 자체는 아니다), "모두가 하나를 공유한다"는 위험만큼은 정확히 같다. 

@Service
public class ListingService {
    private int callCount;   // ⚠️ 싱글턴 빈에 상태를 두면 모든 요청이 이 값을 같이 쓴다

    public void search() {
        callCount++;   // 동시에 두 요청이 들어오면 경쟁 상태(race condition)
    }
}

callCount는 static이 아니지만, 빈이 싱글턴이라 결과적으로 모든 요청이 같은 인스턴스의 같은 필드를 동시에 건드리게 된다. 오늘 배운 "static은 모두가 공유해서 위험할 수 있다"는 감각이, 스프링에서는 "싱글턴 빈에 상태를 두면 안 된다"는 규칙으로 그대로 이어진다.

한 줄로 남기면

메서드 영역(클래스 정보 + static) · 스택(지역 변수) · 힙(인스턴스) 세 곳을 구분하면, static이 "왜 인스턴스마다 안 생기고 딱 하나뿐인지"가 자연스럽게 설명된다. 그리고 "모두가 공유하는 값은 그만큼 위험할 수 있다"는 감각은, 스프링의 싱글턴 빈을 설계할 때 그대로 다시 쓰인다.
