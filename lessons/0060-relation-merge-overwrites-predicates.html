merge는 조건을 합치지 않고 덮어쓴다

레슨 060 Relation#merge · where 체이닝 · 서브쿼리 스코프 ~12분
🎯 PR #5585(평가 결과 검색) 리뷰에서 내가 지적한 성능 개선이 다음 커밋에서 반영됐는데, 그 개선이 안전 범위 필터를 같이 날려버린 것을 찾아낸 과정 — MISSION.md

상황 — 성능 개선이 필터를 같이 지웠다

평가 결과 검색은 "마감된 평가에서 조건에 맞는 사람을 찾는" 어드민 화면이다. 조건 하나가 평가 → 그룹 → 프로세스 → 영역을 지정하고 등급이나 점수를 덧붙인다. 판정 단위가 "행"이 아니라 "사람"인 게 특징이다 — 업적 행과 역량 행은 별개 행이라 한 행이 두 조건을 동시에 만족할 수 없으니, "그 사람이 조건마다 해당 행을 하나씩 갖고 있는가"로 본다.

그래서 쿼리가 두 갈래로 돈다. 이 구분이 이번 버그의 열쇠였다. 

relation
  .where(matched_rows(...))                                   # (가) 어떤 행을 보여줄까
  .where(appraisee_user_id: matched_appraisee_user_ids(...))   # (나) 어떤 사람만 남길까
(가) 표시 행

(나) 대상자 판정

독립 서브쿼리

내가 앞선 리뷰에서 "(가)에 조건마다 안전 범위가 통째로 복제된다"고 지적했고, 작성자가 그걸 고쳐 서브쿼리 등장 횟수를 6회 → 2회로 줄였다. 그런데 (나)에서도 같이 걷어낸 것이 문제였다.

먼저 — base가 왜 있나

appraisal_id 같은 값은 브라우저가 보내는 값이다. 개발자도구로 바꿀 수도 있고, 화면이 낡은 값을 들고 있을 수도 있다. 그래서 서버는 자기 범위를 항상 덧씌운다. 

AppraisalReadOnlyResponse
  .where(workspace_id: workspace.id,
         appraisal_id: finished_appraisal_ids)   # ← 이 두 개가 안전 범위
  .where(appraiser_status: 'completed')
  .joins(...)

이게 base다. 이 레포 AGENTS.md에도 "객체 ID만 믿지 않는다"로 적혀 있는 규칙이고, 원래 코드 주석도 unscope(:where)를 피한 이유로 정확히 이걸 적어뒀었다.

핵심 — where 체이닝과 merge는 다르다

ActiveRecord의 where는 즉시 DB에 가지 않는다. Relation이라는 "조립 중인 SQL 객체"를 돌려주고, 실제 실행은 count나 to_a를 부를 때 일어난다. 그래서 계속 이어 붙일 수 있다. 붙이는 방법이 두 가지인데 같은 컬럼이 겹칠 때 동작이 반대다.

동작같은 컬럼이 겹치면
.where(a).where(b)조건을 누적둘 다 남고 AND로 묶임
.merge(other)다른 Relation을 합침뒤에 온 쪽이 앞의 것을 덮어씀

merge는 원래 "기본 조건을 갖고 있다가 나중에 덮어쓰고 싶을 때" 쓰는 도구다. 이번엔 덮어쓰면 안 되는 걸 덮어썼다. 실제로 생성되는 SQL을 뽑아 비교했다. 

-- merge 로 붙였을 때 (버그)
SELECT ... FROM appraisal_read_only_responses
   WHERE workspace_id = 2
     AND appraisal_id = 4              -- ← 마감 평가 제한이 통째로 사라졌다
     AND appraisal_group_id = 4
-- where 체이닝으로 붙였을 때 (정상)
SELECT ... FROM appraisal_read_only_responses
   WHERE workspace_id = 2
     AND appraisal_id IN (SELECT appraisals.id FROM appraisals
                          WHERE appraisals.workspace_id = 2
                            AND appraisals.status IN (2, 3)      -- closed, completed
                            AND appraisals.deleted_at IS NULL)
     AND appraisal_id = 4              -- ← 둘 다 남아 있다
     AND appraisal_group_id = 4

workspace_id = 2는 살아남았다. 조건 쪽에 workspace_id가 없어서 겹치지 않았기 때문이다. 반면 appraisal_id는 양쪽에 다 있어서 조건 쪽 값이 base의 것을 밀어냈다. 즉 테넌트 격리는 우연히 살아남았고, 마감 범위 방어만 정확히 사라졌다 — 이 우연이 사고를 더 찾기 어렵게 만든다.

(status IN (2, 3)처럼 숫자가 보이는 건 Rails enum이 상태를 정수로 저장하기 때문이다 — closed=2, completed=3.)

그래서 무슨 일이 벌어졌나

정상 SQL의 appraisal_id IN (마감 평가들) AND appraisal_id = 4를 보자. 평가 4가 진행 중이면 마감 목록에 없으니 두 조건을 동시에 만족하는 행이 존재할 수 없어 결과가 0건이다. 이게 의도한 동작이다.

버그 상태에서는 앞쪽이 사라져 appraisal_id = 4만 남는다. 그러면 진행 중 평가의 데이터로 사람을 골라내게 된다. 한 조건 그룹에 마감 평가 조건과 진행 중 평가 조건을 함께 넣어 로컬에서 재현했다.

대상자 판정최종
버그 이전[] (공집합)0건
버그 상태[35]1건
수정 후[]0건 ✅
왜 눈에 안 띄었나가 이 버그의 성격이다. 보여주는 행은 (가)를 통과해야 하고 거기엔 마감 제한이 살아 있다. 그래서 진행 중 평가의 행이 화면에 뜨지는 않는다. 대신 대상자 명단만 조용히 틀린다. 예외도 없고 화면도 정상으로 보이는데 Calibration 대상자를 추리는 결과가 잘못 나온다 — 에러 나는 버그보다 나쁘다.

고치는 방법 — 시작 지점을 인자로 넘긴다

merge를 버리고, 어디서부터 조건을 얹을지를 키워드 인자로 받게 했다. 

def appraisee_scope(conditions)                    # (나) 대상자 판정
  conditions.inject(base.section_data) do |scope, condition|
    matched = condition_scope(condition, from: base.section_data)  # base 에서 시작
                .select(:appraisee_user_id)
    scope.where(appraisee_user_id: matched)
  end
end

def condition_scope(condition, from: AppraisalReadOnlyResponse)    # 기본값은 맨 relation
  scope = from.where(                              # ← from 위에 조건을 얹기만 한다
    appraisal_id: condition[:appraisal_id],
    appraisal_group_id: condition[:appraisal_group_id],
    ...
  )
  scope = rank(scope, condition[:rating_item_id])
  score(scope, condition[:score], condition[:score_operator])
end

인자 하나로 두 용도를 나눈 게 포인트다.

호출from왜
condition_scope(condition) — (가) 표시 술어기본값(맨 relation)바깥 WHERE에 이미 base가 AND로 있으니 또 넣으면 중복
condition_scope(condition, from: base.section_data) — (나) 판정base따로 실행되는 서브쿼리라 자기 안에 안전 범위가 있어야 함

성능 숫자가 6 → 2 → 4로 움직인 이유

같은 조건(그룹 1개 × 조건 2개)에서 마감 평가 서브쿼리(FROM appraisals)가 SQL에 몇 번 등장하는지 셌다.

등장 횟수상태
원래 코드6회정확하지만 중복이 많음
성능 개선 후2회빠르지만 필터가 사라짐
최종 수정4회정확하고, 중복은 여전히 줄어듦

원래 6회가 나온 이유는 condition_scope가 base에서 출발했고 그 결과를 (가) 표시 술어에도 통째로 박아 넣었기 때문이다. 조건마다 안전 범위가 복사됐다. (가)에서 그 중복을 걷어낸 것은 정당한 개선이다. 문제는 (나)에서도 같이 걷어낸 것이었다. 최종 수정은 (가)의 개선은 유지하고 (나)만 되돌린다. 늘어난 2회가 곧 마감 범위 방어다.

레슨 7에서 서브쿼리를 "쿼리 안의 쿼리"로 배웠는데, 그때는 모양만 봤다. 이번에 배운 건 서브쿼리가 자기만의 WHERE를 갖는 독립 스코프라는 점이다. 바깥 쿼리에 필터가 있어도 서브쿼리에는 적용되지 않는다. "바깥에 있으니 괜찮다"는 (가)처럼 같은 WHERE에 얹히는 경우에만 참이다.

어떻게 확인했나 — 코드를 일부러 되돌렸다

작성자가 회귀 테스트를 함께 추가했다. "테스트를 추가했다"만으로는 그 테스트가 이 버그를 잡는지 알 수 없어서, merge로 되돌려 다시 돌려봤다.

퀴즈 2 — 같은 개선을 (가)에는 해도 되고 (나)에는 안 되는 이유

조건 술어에서 base를 걷어내는 것이 (가) 표시 술어에서는 안전하고 (나) 대상자 판정에서는 위험했다. 판단 기준은 무엇인가?

한 줄로 남기면

Relation#merge는 같은 컬럼의 술어를 AND하지 않고 덮어쓴다. 안전 범위(테넌트·상태·soft delete)를 담은 relation에 사용자 입력을 붙일 때는 merge가 아니라 where 체이닝을 써야 한다. 그리고 서브쿼리는 자기만의 WHERE를 갖는 독립 스코프라 바깥 필터가 적용되지 않는다 — 성능 개선으로 조건을 걷어낼 때 "이 술어가 어디서 실행되는지"를 먼저 확인해야, 중복 제거가 안전한 자리와 방어를 없애는 자리를 구분할 수 있다.
