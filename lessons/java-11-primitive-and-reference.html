기본형과 참조형

자바 · 실전 자바 기본편 섹션 3 ~20분
🎯 레슨 java-10에서 Student b = a; 뒤에 b.name을 바꿨더니 a.name도 바뀌는 것을 봤다. 이번에는 그 현상을 문장 하나로 된 대원칙으로 설명하고, 메서드 호출과 null까지 밀고 간다.
강의를 수강하지 않고 작성한 레슨이다. 김영한 「실전 자바 - 기본편」 섹션 3의 전개와 예제는 수강생 정리 글 3편을 교차 확인해 따라갔고(하단 출처), Ruby·TypeScript 대비와 뿌 연결은 직접 쓴 것이다.

핵심 한 줄

자바는 항상 변수에 들어 있는 값을 복사해서 대입한다. 예외가 없다. 기본형이면 그 안의 실제 값이 복사되고, 참조형이면 그 안의 참조값(주소)이 복사된다. "어떤 때는 복사되고 어떤 때는 공유된다"가 아니라, 항상 복사하는데 복사되는 것이 무엇이냐가 다를 뿐이다.

두 종류의 타입

기본형 (primitive type) 참조형 (reference type)
변수에 담기는 것 실제 값 (10) 객체의 위치 (x001)
쓰는 법 바로 쓴다 .이나 []로 찾아가야 쓴다
연산 a + b ⭕ s1 + s2 ❌ 컴파일 에러
대입할 때 복사되는 것 값 → 서로 독립 주소 → 같은 객체를 가리킴
기본값 0, 0.0, false null
종류 int long double boolean 등 8개 그 8개를 뺀 전부 (클래스·배열)

구분하는 눈에 띄는 단서가 하나 있다. 기본형은 소문자로 시작하고 참조형은 대문자로 시작한다 (int vs Integer, double vs Double). 클래스 이름이 대문자 카멜 케이스라는 관례의 자연스러운 결과다.

String만 예외처럼 보인다. 대문자로 시작하니 참조형이 맞는데, String s = "안녕";처럼 기본형같이 값을 바로 대입할 수 있다. 문자열을 워낙 자주 다루니 자바가 특별히 편의를 봐준 것이고, 실체는 참조형이다. (그래서 문자열 비교에 ==를 쓰면 안 된다는 이야기가 뒤에 나온다.)

대원칙에는 예외가 없다

// 기본형 — 값이 복사된다
int a = 10;
int b = a;      // b에 "10"이 복사됨
a = 20;
// a = 20, b = 10   서로 독립

// 참조형 — 주소가 복사된다
Data dataA = new Data();
dataA.value = 10;
Data dataB = dataA;   // dataB에 "x001"이 복사됨
dataA.value = 20;
// dataA.value = 20, dataB.value = 20   같은 객체

두 경우 모두 변수에 든 값을 복사했다는 점에서 하는 일이 완전히 같다. 다만 b가 받은 건 숫자 10이고 dataB가 받은 건 주소 x001이라, dataB를 통해 그 주소로 찾아가면 dataA가 보던 것과 같은 객체가 있을 뿐이다. java-10에서 본 "블록 하나에 송장 번호 둘"이 바로 이것이다.

메서드 호출도 대입이다

여기가 이 섹션의 핵심이다. 매개변수(파라미터)도 결국 변수다. 그러니 메서드에 인자를 넘기는 것도 대입이고, 같은 대원칙이 그대로 적용된다. 

static void changePrimitive(int x) { x = 20; }

int a = 10;
changePrimitive(a);
System.out.println(a);   // 10 — 그대로다
static void changeReference(Data d) { d.value = 20; }

Data data = new Data();
data.value = 10;
changeReference(data);
System.out.println(data.value);   // 20 — 바뀌었다

"기본형은 값 전달, 참조형은 참조 전달"이라고 외우면 다음 코드에서 반드시 틀린다. 

static void replace(Data d) {
    d = new Data();      // 새 객체를 만들어 d에 대입
    d.value = 99;
}

Data data = new Data();
data.value = 10;
replace(data);
System.out.println(data.value);   // 10 — 안 바뀐다!

참조형인데 왜 안 바뀌었나. d는 data가 들고 있던 주소의 복사본일 뿐이라, d에 다른 주소를 넣는다고 data가 들고 있는 주소가 달라지지 않는다. 객체 안의 내용을 고치면 원본에 보이고, 변수가 가리키는 대상을 갈아끼우면 원본에 안 보인다. 자바에 진짜 의미의 참조 전달(pass by reference)은 없다 — 전부 값 전달인데, 그 값이 주소일 뿐이다.

JS에서 function f(o) { o.x = 1 }은 원본이 바뀌지만 function f(o) { o = {x: 1} }은 안 바뀌던 것, Ruby에서 arr << 1은 원본이 바뀌지만 arr = [1]은 안 바뀌던 것과 완전히 같은 규칙이다. 새로 배울 개념은 없다. 자바가 얹는 것은 하나다 — JS·Ruby에서는 "원시값이냐 객체냐"가 런타임 성질이지만, 자바는 선언한 타입이 미리 결정한다. int라고 쓰는 순간 값이고, Integer라고 쓰는 순간 주소다.

뿌에서 물리는 지점 ① — 넘긴 엔티티가 바뀐다

public void applyDiscount(Listing listing) {
    listing.setPrice(listing.getPrice() - 1000);   // 원본이 바뀐다
}

Rails에서 객체를 넘겨 고치는 것과 감각은 같지만, JPA에서는 여기에 한 겹이 더 얹힌다. 영속성 컨텍스트가 관리 중인 엔티티는 값을 바꾸기만 해도 커밋 시점에 UPDATE가 나간다(dirty checking). 즉 위 메서드는 "객체 하나 고친 것"으로 끝나지 않고 DB를 고친 것이 된다. save()를 부르지 않았는데도. 그 출발점이 바로 이 레슨의 참조 공유다.

초기화 — 필드는 봐주고 지역 변수는 안 봐준다

public class InitData {
    int value1;         // 자동으로 0
    int value2 = 10;    // 직접 지정도 가능
}

public static void main(String[] args) {
    int a;
    System.out.println(a);   // ❌ 컴파일 에러: variable a might not have been initialized
}

같은 int인데 대우가 다르다. 멤버 변수(필드)는 자동 초기화되고, 지역 변수는 직접 초기화해야 한다. 필드는 객체와 함께 만들어지므로 자바가 값을 채워줄 수 있지만, 지역 변수는 메서드가 실행되는 동안만 잠깐 존재해서 안 채운 건 실수일 가능성이 높다고 보고 컴파일러가 막는 것이다. 매개변수도 지역 변수의 한 종류인데, 이쪽은 호출할 때 반드시 값이 들어오니 문제가 없다.

null과 NullPointerException

null은 참조형 변수가 가리키는 객체가 없다는 뜻의 특별한 값이다. 택배 송장은 발급됐는데 배송지가 아직 안 정해진 상태다. 그 상태에서 주소로 찾아가려 하면 터지는 것이 NullPointerException(NPE)다. 

Data data = null;
System.out.println(data.value);
// 💥 NullPointerException — 갈 곳이 없는데 찾아가라고 했다

반대로 null을 넣는 것은 "이제 이 객체 안 쓴다"는 뜻이기도 하다. 아무도 참조하지 않게 된 객체는 JVM의 GC(가비지 컬렉션)가 알아서 회수한다. Ruby도 같은 방식이라 새로울 건 없다.

뿌에서 물리는 지점 ② — int와 Integer를 섞을 때

Integer price = listing.getPrice();   // 국토부 API에 가격이 없으면 null
int won = price;                      // 💥 NullPointerException

Integer(참조형)를 int(기본형)에 넣을 때 자바가 자동으로 값을 꺼내주는데(언박싱), 꺼낼 객체가 없으면 그 자리에서 NPE다. 대입문 한 줄에 예외가 숨어 있다는 게 고약한 점이다. 수집한 데이터에 빈 필드가 흔한 뿌에서는 이게 실제로 자주 터진다.

같은 상황에서 다른 언어는 이렇게 반응한다. Ruby는 nil + 1에 NoMethodError를 내고, JS는 undefined + 1을 NaN으로 조용히 넘긴다. 자바의 NPE는 요란하지만 그 줄에서 멈춰준다는 점에서 JS보다 낫다 — NaN이 계산을 타고 흘러 DB까지 들어가는 사고가 없다.

한 줄로 남기면

자바는 언제나 값을 복사한다. 질문은 "복사되느냐"가 아니라 "복사되는 그 값이 실제 값이냐 주소냐"다. 그리고 그 답은 런타임이 아니라 내가 타입을 쓰는 순간 정해진다. 그래서 뿌에서 필드 타입을 int로 할지 Integer로 할지 고르는 일은 취향이 아니라 "이 값이 없을 수 있는가"에 대한 선언이고, 잘못 고르면 0원으로 조용히 저장되거나 NPE로 요란하게 터진다.
