DB default는 "수정"을 보호하지 않는다

레슨 058 컬럼 default · nil vs 키 없음 · mass assignment 비대칭 ~12분
🎯 핵심성과 태그 필수 옵션 request spec을 쓰다가, weight를 안 보냈다는 이유만으로 500이 나는 걸 발견하고 코드를 3단계로 따라가 원인을 확인한 과정 — MISSION.md

상황 — 태그만 고치려던 요청이 500이 됐다

핵심성과 태그를 필수로 만드는 기능을 검증하려고, 기존 핵심성과에 tag_ids만 추가하는 PUT 요청 스펙을 썼다. weight는 이미 있는 값을 그대로 둘 생각이라 요청에 안 넣었다. 

put "/api/v2/workspaces/#{workspace.hash_id}/objectives/#{objective.id}", params: {
  key_results_attributes: [{
    id: key_result.id,
    name: key_result.name,
    kind: key_result.kind,
    target: key_result.target,
    tag_ids: [key_result_tag.id],   # weight는 안 보냄 — 어차피 안 바꾸니까
  }],
}

돌아온 건 200이 아니라 500이었다. 

Mysql2::Error: Column 'weight' cannot be null

스키마를 확인했다. weight는 default가 있는 NOT NULL 컬럼이다. 

# key_results 테이블
weight :decimal(13, 8) default(100.0), not null

직관적으로는 말이 안 됐다. default가 있으면 값을 안 줘도 알아서 채워지는 거 아닌가? 안 보낸 필드 때문에 왜 NULL을 넣으려고 하지?

코드를 3단계로 따라가 보니

weight는 요청에 없었다. 그런데 어딘가에서 그 "없음"이 nil이 되고, 그 nil이 그대로 DB까지 흘러간 것이다. 실제 반영 경로를 순서대로 짚었다.

1단계 — 요청이 diff로 변환된다

목표 수정 요청은 바로 저장되지 않고, 먼저 ObjectiveUpdateDiff가 "무엇이 바뀌는지"를 계산한다. 핵심성과 하나당 요청 파라미터를 그대로 훑는다. 

# app/services/objective_update_diff.rb
key_results_attributes.each do |item|
  next_data = %i[name description kind target weight position tag_ids]
    .index_with {|key| item[key] }
  ...

item은 요청에서 온 그 핵심성과 항목의 해시다. item[:weight]는 요청에 weight 키가 없으니 당연히 nil이다. 여기까지는 자연스럽다 — 문제는 이 nil이 그대로 다음 단계로 넘어간다는 것. 

# 같은 파일, 기존 핵심성과를 "수정"으로 분류하는 분기
next_hash = {
  id: item[:id],
  name: item[:name],
  ...
  weight: item[:weight],   # nil이면 nil 그대로
  ...
}

2단계 — 그 diff가 진짜 저장 값으로 재사용된다

next_hash는 "변경 이력 기록용"처럼 보이지만, 실제로는 승인 시점에 그대로 update의 인자로 재사용된다. 

# app/services/objective_approve_update.rb
def approve_key_result(value)
  ...
  if value[:prev].present? && value[:next].present?
    @objective.key_results.find_by(id: value[:prev][:id])&.update(value[:next])
    #                                                       ^^^^^^^^^^^^^^^^^^
    #                                     1단계에서 만든 next_hash가 그대로 여기로
  end
end

value[:next]가 곧 1단계의 next_hash다. 그 안에 weight: nil이 들어 있으니, update(value[:next])는 결국 weight = nil을 명시적으로 대입하는 것과 같다.

요청에 weight 없음
→
item[:weight]
nil
→
next_hash[:weight]
nil 그대로 보존
→
key_result.update(
weight: nil)

3단계 — DB가 거절한다

ActiveRecord는 weight 속성이 nil로 변경됐다고 판단하고 (Dirty Tracking — 레슨 20), UPDATE ... SET weight = NULL ...을 실행한다. MySQL은 NOT NULL 제약을 보고 그 자리에서 거절한다. default(100.0)은 이 순간 아무 역할도 하지 못했다.

결정적 단서 — 생성 경로는 이미 이걸 막아뒀다

같은 파일에서 딱 몇 줄 위, 새 핵심성과를 만드는 분기를 봤다. 

# 같은 change_or_create_key_result 메서드, 신규 생성 분기
next_key_result = {
  name: next_data[:name],
  ...
  weight: next_data[:weight] || BigDecimal('100.0'),  # ← nil이면 100.0으로!
  ...
}

정확히 같은 상황(요청에 weight가 없어서 nil)을, 생성 분기는 이미 방어하고 있었다. || BigDecimal('100.0') 한 줄이 그 방어다. 그런데 바로 아래, 기존 핵심성과를 수정하는 분기(weight: item[:weight])에는 이 방어가 빠져 있다.

레슨 51에서 본 것과 같은 모양이다 — 이름도 같고 다루는 개념도 같은 두 코드 경로가, 실제로는 서로 다른 정책으로 짜여 있었다. "생성이 안전하니 수정도 안전하겠지"는 근거 없는 가정이었다.

왜 default는 "수정"에서 못 지켜주는가

DB의 default는 컬럼을 아예 건드리지 않은 새 레코드에만 적용된다. KeyResult.new로 만든 뒤 weight를 한 번도 대입하지 않고 저장하면, INSERT 문에 그 컬럼이 값 없이 들어가거나 스키마 기본값이 실려서 DB가 100.0을 채운다.

반대로 이미 존재하는 레코드에 weight: nil을 명시적으로 대입하면, Rails 입장에서는 "이 속성이 nil로 바뀌었다"는 확정된 변경이다. Dirty Tracking이 이걸 변경분으로 잡아 UPDATE 문의 SET 절에 넣고, MySQL은 그 값을 보고 거절한다. default는 CREATE 시점의 개념이지, UPDATE 시점에는 아무 개입도 하지 않는다.

더 파고들면 — nil은 "안 보냄"과 "명시적으로 null"을 구분 못한다

한 단계 더 근본 원인이 있다. item[:weight]가 nil인 이유가 "클라이언트가 그 키를 아예 안 보내서"인지, "클라이언트가 명시적으로 null을 보내서"인지 — Ruby의 Hash#[]는 이 둘을 구분하지 않는다. 

{}[:weight]           # => nil  (키가 아예 없음)
{ weight: nil }[:weight]  # => nil  (키는 있는데 값이 nil)
# 완전히 같은 결과. 구분하려면:
{}.key?(:weight)            # => false
{ weight: nil }.key?(:weight) # => true
TypeScript로 치면 interface Props { weight?: number }(키가 없을 수 있음)와 interface Props { weight: number | null }(키는 반드시 있고 값이 null일 수 있음)는 타입 레벨에서 서로 다른 타입이라 컴파일러가 구분을 강제한다. Ruby 해시나 JSON 파싱 결과에는 이런 구분이 타입으로 남지 않는다 — []로 그냥 꺼내면 둘 다 nil이고, 구분하고 싶으면 key?로 직접 물어봐야 한다.

이건 이미 배운 개념의 연장선이다 — nil(값을 안 보냄)과 false(false라는 값)를 구분해야 한다는 것처럼, nil 안에도 "그 필드를 안 보냄"과 "명시적으로 null을 보냄"이라는 서로 다른 두 가지 의도가 뭉개져 있을 수 있다.

고친다면 이렇게 — 값이 아니라 "보냈는지"부터 물어야 한다

# 수정 분기도 생성 분기와 같은 방식으로:
weight: item.key?(:weight) ? item[:weight] : original.weight

|| BigDecimal('100.0') 방식(생성 분기)은 "값이 없으면 기본값"이라 새 레코드엔 맞지만, 기존 레코드를 수정할 땐 기본값이 아니라 원래 값을 유지해야 한다. 그래서 수정 분기의 올바른 방어는 key?로 "이 필드를 요청이 건드렸는가"부터 확인하는 것이다.

이번 작업에서는 이 버그가 내가 만들던 태그 기능과 무관한 기존 코드였다. 범위를 지키기 위해 고치지 않고, 스펙에 weight를 명시적으로 포함해 우회했다. 대신 work-log에 남겨서 다음 작업 후보로 넘겼다 — 범위를 지키는 것과 발견한 버그를 못 본 척하는 것은 다르다.

퀴즈 2 — 안 보냄과 null을 구분하려면

item[:weight]가 nil일 때, 그게 "클라이언트가 안 보낸 것"인지 "명시적으로 null을 보낸 것"인지 코드에서 구분하려면?

한 줄로 남기면

DB default는 컬럼을 아예 건드리지 않은 새 레코드에만 작동한다. 부분 수정 코드가 요청 파라미터를 그대로 대입하면, "그 필드를 안 보냄"과 "명시적으로 null을 보냄"이 똑같이 nil로 뭉개져 default를 무력화한다. 방어하려면 값이 뭔지가 아니라 그 키가 있었는지부터 물어야 한다.
