let_it_be가 공유하는 건 DB 레코드가 아니라 "그 Ruby 객체 자체"다

레슨 048 RSpec · test-prof · let_it_be ~10분
🎯 핵심성과 자동 반영 조건(auto_reflect_eligible?)을 테스트하다가, 랜덤 실행 순서에 따라 어쩔 때만 실패하는 테스트를 만나서 원인을 추적하며 배운 것 — MISSION.md

어쩔 때만 실패하는 테스트

KeyResult#auto_reflect_eligible?은 "목표가 open 상태가 아니면 false"라는 조건이 있다. 이걸 테스트하려고 이렇게 썼다. 

describe '#auto_reflect_eligible?' do
  let_it_be(:objective) { create(:objective, stage: :open) }
  subject(:key_result) { create(:key_result, objective: objective, auto_checkin_reflect: true) }

  it '세 조건을 모두 만족하면 true를 리턴한다' do
    expect(key_result.auto_reflect_eligible?).to be(true)
  end

  it '목표가 open 상태가 아니면 false를 리턴한다' do
    key_result.objective.stage = 'closed'   # 저장(save)은 안 하고 인메모리로만 바꿈
    expect(key_result.auto_reflect_eligible?).to be(false)
  end
end

RSpec은 기본적으로 각 it 블록(example)을 트랜잭션으로 감싸고, 끝나면 롤백한다 — 그래서 DB에 저장한 내용은 다음 example로 넘어가지 않는다고 배웠다(레슨 24). 그런데 이 두 테스트를 실행 순서를 바꿔가며 여러 번 돌리면, 가끔 첫 번째 테스트 ("모두 만족하면 true")가 실패한다 — 트랜잭션 롤백이 있는데 왜?

퀴즈 1 — 무엇이 롤백되고, 무엇이 롤백되지 않는가

RSpec의 트랜잭션 롤백은 각 example이 끝날 때마다 자동으로 일어난다. 이게 되돌리는 건 정확히 무엇인가?

범인 — let_it_be는 "example마다 새로 만들기"를 건너뛴다

보통 쓰는 let은 각 example마다 블록을 다시 평가해서 매번 새 객체를 만든다. 그런데 let_it_be(test-prof 젬)는 describe/context 블록 전체에서 딱 한 번만 만들고, 그 example group 안의 모든 example이 같은 객체를 공유한다 — DB 접근이 잦은 무거운 픽스처(workspace, cycle 등)를 매번 다시 만들지 않아서 테스트가 훨씬 빨라진다는 게 장점이다.

let은 매 example마다 "새 종이에 다시 적기"고, let_it_be는 "이미 적어둔 종이 한 장을 여러 example이 돌려가며 읽고 쓰기"다. 트랜잭션 롤백은 "그 종이를 원래 글자로 되돌리는 것"이 아니라 "그 종이 내용을 DB에 반영한 것 자체를 취소하는 것"이다. 누군가 종이(Ruby 객체) 위에 연필로 낙서만 하고(stage = 'closed', 저장 안 함) 잉크로 다시 쓰지(save!) 않았다면, DB 취소와 무관하게 그 낙서는 종이 위에 그대로 남아 다음 사람이 읽는다.

문제의 테스트를 다시 보면, 두 번째 테스트가 key_result.objective.stage = 'closed'로 저장 없이 인메모리 속성만 바꾼다. objective가 let_it_be로 공유되고 있었다면, 이 변경은 트랜잭션 롤백과 무관하게 그대로 남아서 다음 example이 이 오염된 객체를 그대로 넘겨받는다. RSpec은 기본적으로 example 실행 순서를 무작위로 섞기 때문에, "closed로 바꾸는 테스트"가 "open이어야 true인 테스트"보다 먼저 실행되는 순서에서만 실패가 재현된다 — 이게 "가끔만 실패하는 테스트"의 정체다.

실제 수정

실제 코드에서는 이렇게 고쳤다 — 매번 새로 만들어야 하는 것만 let으로 내리고, 진짜 재사용해도 안전한(어떤 테스트도 인메모리로 변형하지 않는) 픽스처만 let_it_be로 남겼다. 

# spec/models/key_result_spec.rb
describe '#auto_reflect_eligible?' do
  let_it_be(:current_user) { create(:user) }
  let_it_be(:workspace) { create(:workspace, creating_user: current_user, users: [current_user]) }
  let_it_be(:cycle) { create(:cycle, workspace: workspace) }

  # objective는 각 예제에서 stage를 직접(in-memory) 건드리므로 let_it_be로 공유하면
  # 한 예제의 변경이 저장되지 않아도 같은 Ruby 객체가 다음 예제에 그대로 넘어가 오염된다 (let로 매번 새로 생성)
  let(:objective) do
    create(:objective, workspace: workspace, cycle: cycle, creater: current_user, approver: current_user, stage: :open, privacy: 'all')
  end

  subject(:key_result) do
    create(:key_result, objective: objective, kind: :progress, target: 100, auto_checkin_reflect: true)
  end

  it '목표가 open 상태가 아니면 false를 리턴한다' do
    key_result.objective.stage = 'closed'
    expect(key_result.auto_reflect_eligible?).to be(false)
  end
end

current_user/workspace/cycle은 어떤 example도 속성을 직접 바꾸지 않으니 let_it_be로 공유해도 안전하다. 반면 objective는 최소 한 example에서 저장 없이 속성을 바꾸므로, 반드시 let이어야 한다.

퀴즈 2 — 어느 걸 let_it_be로 둬도 되는가

한 example group 안의 여러 it 블록 중 하나가 어떤 픽스처의 속성을 저장 없이 직접 바꾼다(obj.attr = value, .save 호출 없음). 이 픽스처를 let_it_be로 선언해도 안전한가?

핵심 요약

항목 설명
let/let! 매 example마다 블록을 다시 평가 — 항상 새 객체
let_it_be(test-prof) example group 전체에서 한 번만 생성 — 모든 example이 같은 Ruby 객체를 공유 (빠르지만 위험할 수 있음)
트랜잭션 롤백이 되돌리는 것 DB에 저장된 내용만 — 저장 없이 바꾼 인메모리 속성값은 안 되돌림
판단 기준 어떤 example도 그 픽스처의 속성을 저장 없이 직접 바꾸지 않는다 → let_it_be 안전. 하나라도 바꾼다 → let으로
