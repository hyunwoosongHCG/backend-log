Pundit의 authorize는 컨트롤러의 약속이지, 서비스의 약속이 아니다

레슨 046 Pundit · authorize · has_flags · 인가 아키텍처 ~14분
🎯 핵심성과 자동 반영 기능을 실제 체크인·승인 흐름으로 수동 검증하다가, "이 유저는 분명 HR admin인데 왜 승인이 안 되지"에서 시작해 발견한 것들 — MISSION.md

서비스 객체를 직접 호출하면 무슨 일이 일어나는가

체크인 승인 로직은 Objective::CheckIns::UpdateService라는 서비스 객체 안에 있다. 이 서비스를 콘솔에서 직접 호출해서, 정책상 승인 권한이 없는 유저로 승인을 시도해봤다. 

Objective::CheckIns::UpdateService.call(
  objective: objective,
  params: { response_type: 'approval' },
  current_user: some_user_without_permission
)
# => 그냥 성공해버린다. 체크인이 승인되고, 값이 반영된다.

이상하다 — ObjectivePolicy#approve_check_in?이 이 유저에 대해 false를 반환하는 걸 분명히 확인했는데도 승인이 통과됐다. 서비스 코드를 열어보니 이유가 명확했다. 

class Objective::CheckIns::UpdateService < ApplicationService
  def call
    if params[:response_type] == 'approval'
      objective.accept_check_ins_and_create_history(current_user.id, diff_history)
      # ... Pundit 체크가 어디에도 없다
    end
  end
end
건물 출입증 리더기(authorize)는 정문에만 달려있다. 정문을 거치지 않고 직원 전용 뒷문(서비스 객체를 직접 호출)으로 들어가면, 그 안의 회의실 문(비즈니스 로직)은 원래부터 잠겨있지 않았기 때문에 아무나 열 수 있다. "이 건물은 안전하다"고 말할 수 있는 건 정문으로 들어온 사람에 대해서일 뿐, 건물 내부 어디에도 그 자체로 잠금장치가 있는 게 아니다.

실제 인가는 컨트롤러(Grape API)에서 authorize objective, :approve_check_in?를 호출하는 시점에만 걸린다. 서비스 객체는 "이미 권한 확인이 끝났다"는 전제 하에 그냥 비즈니스 로직만 수행한다. 이건 딱히 이 코드베이스만의 버그가 아니라 Pundit이 원래 그렇게 설계된 것이다 — Pundit은 "인가를 강제하는 프레임워크"가 아니라 "정책을 어디서 물어볼지는 개발자가 명시적으로 골라야 하는 라이브러리"다. 그래서 서비스 객체나 콘솔, 배치 스크립트에서 이 서비스를 직접 호출하는 모든 곳은 인가를 스스로 챙겨야 한다.

퀴즈 1 — authorize는 어디서 지켜지는가

Grape 컨트롤러 액션 안에서 authorize objective, :approve_check_in?를 호출한 뒤, 실제 승인 로직은 별도의 서비스 객체(UpdateService)에 위임한다. 만약 다른 코드(예: Rails 콘솔, 배치 워커)에서 이 UpdateService를 직접 호출한다면?

ObjectivePolicy#hr_admin? — "본인 담당 건은 셀프 승인 금지" 가드

체크인 승인 정책(approve_check_in?)은 담당자 관리자거나 HR admin이면 통과된다. 그런데 hr_admin?이 기본 구현을 오버라이드하고 있었다. 

class ObjectivePolicy < ApplicationPolicy
  def hr_admin?
    return false if record.assignee_user?(user)  # 본인이 담당자면 여기서 즉시 false
    super
  end
end

HR admin이라는 이유만으로 자기 자신에게 할당된 목표의 체크인까지 셀프 승인해버리면 이해충돌이 생긴다 — 그래서 "본인이 담당자인 경우"를 명시적으로 걸러낸다. 겉보기엔 단순한 한 줄이지만, "관리자 권한이 있다"와 "이 특정 건에 대해 관리자 권한을 쓸 수 있다"가 다르다는 걸 보여주는 예다.

"HR admin"이 이 코드베이스에 두 가지로 존재한다

처음엔 workspace.hr_admins(내부적으로 work_hr_administrations 조인 테이블을 쓴다)로 HR admin 목록을 가져와서 테스트 시나리오를 짰다. 그런데 그 유저로 체크인을 승인하려니 정책이 계속 false를 반환했다. 원인을 추적해보니, Pundit의 ApplicationPolicy#hr_admin?은 이 테이블을 보는 게 아니었다. 

# app/policies/application_policy.rb
def hr_admin?
  member&.hr_admin? && member.workspace_id == workspace_id
end

member.hr_admin?은 Member 모델의 admin_roles라는 정수 컬럼 하나에 has_flags 젬으로 비트마스크를 씌운 메서드였다. 

# app/models/member.rb
has_flags 1 => :hr_admin, 2 => :system_admin, 3 => :sub_admin, column: 'admin_roles'
체크박스 3개짜리 설문지를 상상해보자. 종이(별도 boolean 컬럼 3개) 대신, 3자리 이진수 하나로 답을 저장하기로 한 것이다(101이면 1번째·3번째 체크). has_flags는 이 이진수를 member.hr_admin?, member.sub_admin?처럼 이름 붙은 메서드로 읽고 쓰게 해주는 젬이다. 컬럼 하나로 여러 boolean을 표현하는 대신, DB를 직접 봐서는 숫자만 보이고 무슨 뜻인지 바로 안 보인다는 대가가 있다.

즉 이 코드베이스에는 "이 사람이 HR admin인가"를 답하는 방법이 서로 독립된 두 군데 있다:

방식 저장 위치 누가 이걸 본다
workspace.hr_admins work_hr_administrations 조인 테이블 (status: super/hr) 일부 화면의 관리자 목록 조회
member.hr_admin? members.admin_roles 비트마스크 컬럼 Pundit 정책 (실제 인가 판정)

실제 dev 데이터에서 이 둘이 어긋나는 유저를 발견했다 — work_hr_administrations엔 있지만 admin_roles 비트는 안 켜진 경우다. 이런 유저는 "관리자 화면 목록엔 HR admin으로 보이지만, 실제 체크인 승인 정책은 통과하지 못한다." "겉보기 데이터"와 "실제 인가에 쓰이는 데이터"가 이름은 비슷해도 서로 다른 원천일 수 있다는 걸 몸으로 확인한 사례다.

퀴즈 2 — 두 HR admin 개념

어떤 유저가 workspace.hr_admins(work_hr_administrations 조인 테이블) 목록엔 있지만, Member#admin_roles 비트마스크엔 hr_admin 비트가 꺼져 있다. 이 유저로 체크인을 승인하려 하면 Pundit의 approve_check_in?은?

덤으로 발견한 것 — 슈퍼 어드민은 "구성원"이 아니다

work_hr_administrations의 status는 super/hr 둘 중 하나다. 목표 일괄 생성 엑셀을 업로드하다가 특정 유저만 "일치하는 구성원이 없습니다" 오류가 나서 조사해보니, 그 유저가 status: super(슈퍼 어드민)였다. 

# app/models/workspace.rb
def users_not_super_admin
  users.where.not(id: super_admin_ids)   # super_admin_ids: status='super'인 유저들
end

이 스코프가 관리자 화면 여러 곳(약 18개 컨트롤러)의 "선택 가능한 구성원" 목록을 만드는 데 쓰이고 있었다 — 슈퍼 어드민은 시스템 계정 취급이라 목표 담당자/관리자 등으로 지정할 수 있는 일반 "구성원" 후보에서 아예 빠지는 것이다. 데이터가 실제로 존재하고 워크스페이스에 소속돼 있어도, 특정 스코프에서 의도적으로 제외될 수 있다는 걸 보여주는 사례다.

핵심 요약

항목 설명
authorize의 범위 컨트롤러에서 명시적으로 호출한 곳에서만 강제됨 — 서비스 객체 직접 호출은 인가를 우회함
이해충돌 가드 "권한이 있다"와 "이 건에 대해 그 권한을 쓸 수 있다"는 다를 수 있음 (본인 담당 건 셀프승인 금지)
두 가지 HR admin 조인 테이블(work_hr_administrations)과 비트마스크(Member#admin_roles)가 서로 독립적으로 존재 — 실제 인가는 후자만 봄
스코프의 의도적 배제 실재하는 데이터도 특정 스코프(super admin 제외)에서 의도적으로 빠질 수 있음
