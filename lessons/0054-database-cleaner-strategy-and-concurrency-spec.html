상황 — 스레드 두 개를 띄웠더니 픽스처가 안 보인다

형제 목표 동시 승인 lost update를 스펙으로 고정하려면 진짜로 커넥션 두 개가 필요하다. 한 스레드가 계산하는 동안 다른 스레드가 커밋하는 상황을 만들어야 하니까. 그래서 이렇게 짰다. 

threads = [sibling_a, sibling_b].map do |objective|
  Thread.new do
    ActiveRecord::Base.connection_pool.with_connection { request_and_approve(objective, 100) }
  end
end
threads.each(&:join)

그런데 스레드 안에서 메인 스레드가 만든 목표를 못 찾는다. let!로 분명히 create했는데 RecordNotFound가 난다.

원인 — 테스트가 빠른 이유가 그대로 원인이다

Rails 테스트가 빠른 건 예제마다 트랜잭션을 열고 끝나면 롤백하기 때문이다. DELETE나 TRUNCATE 없이 즉시 원상복구된다. 이 레포는 DatabaseCleaner의 :transaction 전략을 쓴다. 

config.before(:suite) do
  DatabaseCleaner.clean_with(:truncation)
  DatabaseCleaner.strategy = :transaction     # ← 기본 전략
end

config.before { DatabaseCleaner.start }       # 예제마다 BEGIN
config.after  { DatabaseCleaner.clean }       # 예제 끝나면 ROLLBACK

여기서 레슨 44의 내용이 그대로 걸린다. 커밋되지 않은 데이터는 그 트랜잭션 밖에서 안 보인다. 스레드를 새로 띄우면 별도 커넥션을 쓰게 되고, 그 커넥션은 메인 스레드의 미커밋 트랜잭션 안을 들여다볼 수 없다.

메인 스레드
커넥션 A
BEGIN → 픽스처 생성
(커밋 안 함)
✗
서브 스레드
커넥션 B
SELECT → 빈 결과
프론트로 치면 jsdom에서 실제 브라우저의 렌더 타이밍 버그를 재현하려는 것과 비슷하다. 테스트를 빠르고 결정적으로 만들어준 바로 그 단순화가, 정확히 그 단순화가 지운 영역의 버그는 재현할 수 없게 만든다.

해결 — 그 그룹만 커밋되는 전략으로

config.before(:all) do
  # :concurrency 태그가 붙은 그룹만 실제로 커밋되는 :truncation으로 바꾼다
  DatabaseCleaner.strategy = self.class.metadata[:concurrency] ? :truncation : :transaction
  DatabaseCleaner.start
end

config.after(:all) do
  DatabaseCleaner.clean
  DatabaseCleaner.strategy = :transaction    # 원복
end

:truncation은 트랜잭션으로 감싸지 않고, 예제가 끝나면 테이블을 실제로 비운다. 그래서 픽스처가 커밋된 상태로 남고 다른 커넥션에서도 보인다.

:transaction
BEGIN → ROLLBACK
빠름 (ms)
다른 커넥션에 안 보임
vs
:truncation
실제 커밋 → TRUNCATE
느림 (예제당 10~15초)
다른 커넥션에 보임

대가가 크다. 이 PR의 동시성 스펙 7건이 96초 걸린다. 그리고 매 예제 후 테이블을 통째로 비우므로, 레슨 48에서 본 let_it_be/before(:all) 픽스처도 같이 날아간다. 그래서 이 전략을 쓰는 그룹은 예제마다 픽스처를 다시 만드는 let! 스타일로 짜야 한다.

보너스 — "지금 앱이 연 트랜잭션인가, 테스트 하네스가 연 트랜잭션인가"

이 PR엔 "락을 잡기 전에 트랜잭션이 열려 있으면 안 된다"는 규칙이 있고, 그걸 런타임에 검사한다. 그런데 테스트에서는 하네스가 항상 트랜잭션을 열어두고 있다. 그대로 검사하면 전 스펙이 죽는다. 

def app_transaction_open?
  ActiveRecord::Base.connection.current_transaction.joinable?
end

DatabaseCleaner는 트랜잭션을 joinable: false로 연다. 앱의 ActiveRecord::Base.transaction은 true다. 트랜잭션이 아예 없을 때 반환되는 NullTransaction도 false다. 그래서 joinable? 하나로 세 상태가 정확히 갈린다.

joinable은 원래 "이 트랜잭션에 다른 트랜잭션이 합류해도 되는가"를 뜻하는 플래그다 (레슨 45의 합류 동작을 제어한다). 테스트 하네스는 자기 트랜잭션에 앱 코드가 합류해서 커밋 콜백이 엉키는 걸 원치 않으니 false로 연다. 그 부수효과를 "하네스 트랜잭션 식별자"로 빌려 쓴 것이다 — 영리하지만 문서화되지 않은 계약에 기대는 것이라 주석이 필수다.

함정 — 태그로 뺐으면 CI에서 다시 넣어야 한다

config.filter_run_excluding concurrency: true unless ENV['RUN_CONCURRENCY_SPECS']

느리고 타이밍에 따라 flaky할 수 있으니 기본 스위트에서 빼는 건 표준적인 판단이다. 문제는 그다음이다. CI에 별도 실행 스텝을 안 만들면 이 스펙은 아무도 안 돌린다.

이 PR에서 가장 중요한 회귀 방어가 정확히 이 스펙인데, 지금 상태로는 누가 락을 통째로 되돌려도 CI가 초록이다. "테스트를 썼다"와 "테스트가 지켜준다" 사이에는 실행되는가라는 한 칸이 더 있다.

테스트 격리 전략은 "무엇을 테스트할 수 없는가"까지 정한다. 예제를 트랜잭션으로 감싸 롤백하는 방식은 빠르지만, 바로 그 미커밋 상태 때문에 커밋 가시성에 의존하는 버그(lost update, 데드락, 격리 수준 문제)는 재현할 수 없다. 그런 버그를 잡으려면 그 그룹만 실제로 커밋되게 바꾸고, 느려진 만큼 CI에서 따로 돌 자리를 반드시 만들어줘야 한다.
