생성자

자바 · 실전 자바 기본편 섹션 5 ~20분
🎯 지난 레슨(java-12)에서 this.value++의 this를 생략해도 되는 이유가 "이름이 안 겹쳐서"라고 했다. 이번 레슨은 이름이 겹치는 그 순간 — 생성자 — 을 본다. 뿌 엔티티마다 쓰는 public Listing(...) 패턴의 정체이기도 하다.
강의를 수강하지 않고 작성한 레슨이다. 김영한 「실전 자바 - 기본편」 섹션 5의 전개와 예제는 수강생 정리 글 3편을 교차 확인해 따라갔고(하단 출처), Ruby·TypeScript 대비와 뿌 연결은 직접 쓴 것이다.

핵심 한 줄

생성자(constructor)는 new로 객체가 만들어지는 바로 그 순간 자동으로 한 번 실행되는, 초기화 전용 특별한 메서드다. "일단 빈 객체를 만들고, 나중에 값을 채운다"는 두 단계를 하나로 합쳐서, 값이 안 채워진 반쯤 만들어진 객체가 존재할 틈을 없앤다.

두 단계의 문제

java-10에서 Student를 만든 뒤 필드를 하나씩 대입했던 것을 떠올려보자. 매번 세 줄씩 반복하기 귀찮으니 메서드로 뽑아본다. 

static void initStudent(Student student, String name, int age, int grade) {
    student.name = name;
    student.age = age;
    student.grade = grade;
}

Student student1 = new Student();               // 1단계: 일단 빈 객체
initStudent(student1, "학생1", 15, 90);          // 2단계: 따로 초기화

동작은 하지만 두 줄 사이에 틈이 있다. 1단계만 실행되고 2단계를 깜빡하면 student1은 이름·나이·성적이 전부 기본값(null, 0)인 채로 돌아다닌다 — 컴파일러는 이걸 막아주지 않는다. initStudent를 부르는 걸 잊는 것도, 순서를 헷갈리는 것도 전부 사람이 조심해야 하는 일로 남는다.

생성자로 한 번에

public class Student {
    String name;
    int age;
    int grade;

    Student(String name, int age, int grade) {
        this.name = name;
        this.age = age;
        this.grade = grade;
    }
}

Student student1 = new Student("학생1", 15, 90);   // 생성 + 초기화가 한 줄

생성자의 이름은 클래스 이름과 반드시 같고, 반환 타입이 아예 없다(void도 안 쓴다). new Student(...)가 실행되는 순간 자바가 이 생성자를 자동으로 찾아 실행한다. 이제 "빈 객체가 잠깐 존재하는" 틈 자체가 없다 — 만들어지는 순간 이미 값이 다 차 있다.

매개변수 이름을 필드와 똑같이 name, age, grade로 지은 건 우연이 아니라 관례다. 그런데 여기서 this.를 빼면 어떻게 될까? 

Student(String name, int age, int grade) {
    name = name;      // ❌ 매개변수를 매개변수 자기 자신에 대입할 뿐
    age = age;        //    필드는 건드리지도 않는다
    grade = grade;
}

Student student1 = new Student("학생1", 15, 90);
System.out.println(student1.name);   // null — 필드는 그대로다

자바는 이름을 찾을 때 항상 가장 가까운 스코프부터 본다. 메서드 안에 매개변수 name이 있으면, 그냥 name이라고 쓴 건 그 매개변수를 가리킨다 — 필드 name이 아니라. 그래서 name = name;은 매개변수를 자기 자신에게 대입하는, 아무 의미 없는 문장이 되고 필드는 계속 초기값(null)으로 남는다. this.name이라고 써야만 "지금 만들어지고 있는 이 객체의 필드"를 명시적으로 가리킬 수 있다. java-12에서 생략해도 되던 this가, 이름이 겹치는 순간 생략 불가능한 필수 문법이 된 것이다.

직접 타이핑해보기 — Student(String name, int age, int grade) 생성자를 작성하세요. this를 사용해 매개변수 값을 필드 세 개에 각각 대입합니다.

Ruby의 initialize도 감각이 똑같다 — def initialize(name); self.name = name; end처럼 self를 붙여야 필드(인스턴스 변수)와 매개변수를 구분한다. TS/JS 클래스의 constructor(name) { this.name = name; }은 자바와 문법까지 거의 그대로다. 이미 다 아는 패턴이라 새로 외울 건 없다 — 자바에서만 this를 뺐을 때 조용히 틀린다(에러가 안 나고 필드가 그냥 null로 남는다)는 게 낯선 지점이다.

기본 생성자 — 공짜는 조건부다

public class Student {
    String name;
    int age;
    int grade;
}

Student student1 = new Student();   // OK — 매개변수 없는 생성자가 자동으로 생긴다

생성자를 하나도 안 쓰면, 컴파일러가 매개변수 없는 빈 생성자를 대신 만들어준다 — 이것을 기본 생성자(default constructor)라고 부른다. java-10· java-11의 new Student()가 지금까지 아무 문제 없이 동작했던 이유다.

그런데 이 공짜 생성에는 조건이 있다. 생성자를 단 하나라도 직접 쓰는 순간, 기본 생성자는 더 이상 자동으로 생기지 않는다. 

public class Student {
    String name;
    int age;
    int grade;

    Student(String name, int age, int grade) {   // 생성자를 하나 직접 썼다
        this.name = name;
        this.age = age;
        this.grade = grade;
    }
}

Student student1 = new Student();   // ❌ 컴파일 에러 — 매개변수 없는 생성자가 없다

Ruby·JS는 initialize/constructor를 안 써도 그냥 new가 되고, 써도 인수 없는 호출이 막히지 않는다. 자바는 다르다 — 매개변수 없는 생성자가 필요하면, 다른 생성자를 몇 개를 쓰든 직접 하나 더 추가해야 한다. 이 규칙이 뿌에서 실제로 어떻게 물리는지는 아래에서 바로 나온다.

생성자 오버로딩과 this()

생성자도 메서드이므로 여러 개를 매개변수만 다르게 만들 수 있다(오버로딩). 성적을 아직 모르는 학생은 기본값 50으로 두고 싶다면 이렇게 하나 더 만든다. 

public class Student {
    String name;
    int age;
    int grade;

    Student(String name, int age, int grade) {
        this.name = name;
        this.age = age;
        this.grade = grade;
    }

    Student(String name, int age) {
        this.name = name;
        this.age = age;
        this.grade = 50;
    }
}

Student student1 = new Student("학생1", 15, 90);
Student student2 = new Student("학생2", 16);       // grade는 자동으로 50

두 생성자의 this.name = name; this.age = age;가 그대로 겹친다. 이 중복을 this(...)로 지울 수 있다 — 같은 클래스의 다른 생성자를 호출하는 문법이다. 

Student(String name, int age) {
    this(name, age, 50);   // 위의 3개짜리 생성자를 그대로 호출
}

규칙은 하나다: this(...)는 생성자의 첫 줄에서만 쓸 수 있다. 다른 생성자가 필드를 먼저 채워놓은 다음에야 이 생성자의 나머지 코드가 의미를 가지므로, 항상 제일 먼저 실행돼야 하기 때문이다.

직접 타이핑해보기 — 이름만 받는 생성자 Student(String name)을 작성하세요. this(...)로 위의 3개짜리 생성자를 호출하면서 age는 0, grade는 50으로 넘깁니다.

뿌에서는 이렇게 보인다

@Entity
public class Listing {
    private Long id;
    private String address;
    private int price;

    public Listing(String address, int price) {   // 이것만 있으면
        this.address = address;
        this.price = price;
    }
}
// 💥 실행 시점에 JPA가 엔티티를 매개변수 없이 못 만들어서 에러가 난다

JPA(Hibernate)가 DB 행을 엔티티 객체로 되돌리는 과정은 사실 두 단계다. 

// 1단계 — 매개변수 없는 생성자로 "껍데기"만 만든다
Listing listing = new Listing();

// 2단계 — DB에서 읽은 값을 필드에 하나씩 직접 대입한다 (리플렉션으로)
setField(listing, "address", resultSet.getString("address"));
setField(listing, "price", resultSet.getInt("price"));

여기서 헷갈리기 쉬운 지점 하나: 2단계에서 채워 넣는 값은 Listing(String address, int price) 생성자 안에 있던 값이 아니라, DB에서 막 읽어온 값이다. JPA는 이 2단계에서 생성자 코드를 아예 실행하지 않는다 — this.address = address; 같은 줄은 한 번도 안 거친다. 그 매개변수 있는 생성자는 오직 여러분이 코드에서 직접 new Listing("강남구", 50000)을 부를 때만 쓰인다. JPA가 DB에서 읽어올 때는 완전히 다른 경로(1단계 빈 생성자 + 2단계 필드 직접 대입)를 탄다.

그런데 1단계에 쓸 매개변수 없는 생성자가 없으면 처음부터 실패한다. 위 코드처럼 매개변수 있는 생성자만 있으면 — 오늘 배운 규칙 그대로 — 기본 생성자가 사라져서 JPA가 "빈 껍데기"조차 못 만든다. 그래서 JPA 엔티티에는 관례적으로 매개변수 없는 생성자를 하나 더 남겨둔다.

Rails도 똑같은 문제를 똑같은 방식으로 푼다. Listing.new(address: ...)처럼 직접 만들 때는 initialize가 불리지만, DB에서 레코드를 읽어올 때는 initialize를 아예 건너뛰고 빈 객체를 만든 다음 컬럼 값을 인스턴스 변수에 직접 꽂아 넣는다. Rails는 동적 언어라 이 우회가 별다른 준비 없이 조용히 일어나지만, 자바는 "그러려면 매개변수 없는 생성자가 문법적으로 존재해야 한다"고 강제한다는 점만 다르다 — 같은 문제, 다른 해결 방식이다. 
protected Listing() {}   // JPA 전용 — 코드에서 직접 부르는 일은 거의 없다

뿌 엔티티 코드에서 본 적 있는 그 "텅 빈 생성자"가 바로 이것이다. protected는 접근 제어자인데, 이건 java-15에서 다룬다 — 지금은 "매개변수 없는 생성자를 하나 더 만든다"는 처방만 기억해두면 충분하다.

"엔티티"라는 이름에 낚이지 말 것. Grape에서 쓰던 Entity는 API 응답 모양을 잡는 프레젠터 계층이었다(2026-07-03 학습). JPA의 @Entity는 완전히 다른 계층이다 — ActiveRecord 모델처럼 DB 테이블 하나를 객체 하나에 매핑하는 것뿐이고, API 응답 모양을 잡는 역할(Grape::Entity가 하던 일)은 자바에서 보통 별도의 DTO 클래스가 맡는다. 그래서 실무에서는 JPA 엔티티를 API 응답으로 그대로 내보내지 않는다 — 지연 로딩 프록시, 양방향 연관관계로 인한 무한 직렬화 루프, 방금 본 것처럼 영속성 컨텍스트가 추적하는 대상이라는 점 때문에 API 응답용 객체와는 애초에 목적이 다르다.

한 줄로 남기면

생성자는 "만들기"와 "채우기"를 한 순간으로 합친다. 그 대가로 매개변수 이름을 필드와 같게 짓는 관례가 생기고, 그 관례 때문에 this가 선택이 아니라 필수가 되는 지점이 생긴다. 그리고 생성자를 하나라도 직접 쓰는 순간 "매개변수 없는 생성" 능력이 공짜로 따라오지 않는다는 것 — 이 규칙 하나가 뿌의 모든 JPA 엔티티에 빈 생성자가 하나씩 더 있는 이유다.
