트랜잭션 경계는 누가 소유하는가

레슨 052 트랜잭션 경계 · 블록 래핑 · 서비스 객체 계약 · 실패 전파 범위 ~15분
🎯 "블록으로 감싸기"라는 무해해 보이는 리팩터링이 실패 전파 범위를 바꿔놓은 걸 리뷰에서 발견한 과정 — MISSION.md

상황 — 락을 걸려면 트랜잭션이 필요하다

형제 목표가 같은 상위 핵심성과에 동시에 체크인 승인되면 값이 덮어써지는 lost update가 있었다. 막으려면 상위 행에 SELECT ... FOR UPDATE를 걸어야 하는데, 행 잠금은 트랜잭션이 끝나는 순간 풀린다. 그래서 "락을 잡는다"는 건 필연적으로 "트랜잭션을 연다"와 같은 말이다.

락 헬퍼는 이렇게 생겼다. 블록을 받고, 안에서 트랜잭션을 열고, 락을 잡고, 블록을 실행한다. 

def lock(key_result_ids)
  return yield if key_result_ids.empty?
  ...
  ActiveRecord::Base.transaction do          # ← 여기서 트랜잭션이 열린다
    key_result_ids.sort.each {|id| KeyResult.lock.where(id: id).pluck(:id) }
    yield                                     # ← 호출부 코드가 이 안에서 돈다
  end
end

그리고 호출부를 이렇게 감쌌다. 겉보기엔 들여쓰기만 한 칸 늘어난 변경이다. 

# before
when 'pending_check_in'
  diff_history = ObjectiveCheckInDiff.call(self)
  accept_check_ins_and_create_history(user_id, diff_history)   # 자체 트랜잭션 → 커밋

  Objective::AutoCloseObjectiveIfProgressCompleteService.call( # 커밋된 뒤, 트랜잭션 밖
    workspace:, current_user_id: user_id, objective: reload,
  )

# after
when 'pending_check_in'
  ReflectToSuperKeyResultService.with_ancestor_locks(objective: self) do
    diff_history = ObjectiveCheckInDiff.call(self)
    accept_check_ins_and_create_history(user_id, diff_history)

    Objective::AutoCloseObjectiveIfProgressCompleteService.call( # ← 이제 트랜잭션 "안"
      workspace:, current_user_id: user_id, objective: reload,
    )
  end

무엇이 바뀌었나 — 실패 전파 범위

자동 마감 서비스는 내부에 rescue가 없다. 그래서:

before
체크인 승인 커밋 ✓
→ 자동 마감 실패
→ 승인은 남는다
vs
after
같은 트랜잭션
→ 자동 마감 실패
→ 승인까지 롤백

사용자 입장에서는 "승인 눌렀는데 아무 일도 안 일어났다"가 된다. 이전에는 "승인은 됐는데 목표가 자동 마감만 안 됐다"였다. 어느 쪽이 옳은지는 도메인이 정할 문제지, 리팩터링이 조용히 정할 문제가 아니다.

프론트로 치면 try/catch의 범위를 넓힌 것과 같다. try { save(); } catch {} 뒤에 있던 sendAnalytics()를 try 블록 안으로 옮기면, 분석 전송 실패가 저장 실패로 둔갑한다. 코드는 "감싸기만" 했는데 의미가 바뀐 것이다.

왜 눈에 안 띄는가 — Rails 트랜잭션은 조용히 합류한다

핵심은 레슨 45에서 본 성질이다. ActiveRecord::Base.transaction은 이미 열린 트랜잭션이 있으면 새로 열지 않고 그냥 합류한다. 예외도 경고도 없다. 

ActiveRecord::Base.transaction do      # 여기서 진짜 BEGIN
  ActiveRecord::Base.transaction do    # BEGIN 안 함. 그냥 합류.
    ...                                # 이 안의 롤백은 바깥까지 되돌린다
  end
end

그래서 accept_check_ins_and_create_history가 자기 안에서 ActiveRecord::Base.transaction을 열고 있어도 더 이상 "자체 트랜잭션"이 아니다. 바깥에 락 헬퍼의 트랜잭션이 생긴 순간, 그 메서드의 커밋 시점이 바깥으로 밀려난다. 메서드 본문은 한 글자도 안 바뀌었는데 동작이 바뀐다.

이게 트랜잭션 경계 소유권이 별도의 설계 항목인 이유다. "이 메서드는 자체 트랜잭션을 가진다"는 건 그 메서드 혼자 결정할 수 없다. 호출부 중 하나라도 트랜잭션을 열면 그 보장이 사라진다.

세 가지 소유 방식

① 호출부 소유
서비스는 절대 안 연다
경계가 명시적
서비스마다 반복
·
② 서비스 소유
서비스가 항상 연다
단독 호출이 안전
합류하면 보장 깨짐
·
③ 최상위만 소유
진입점 1곳만 연다
경계가 하나
진입점 규율 필요

이번 코드는 ②를 쓰면서 ①처럼 다루려다 사고가 났다. 락 헬퍼는 트랜잭션을 소유하는데(②), 호출부는 그걸 "그냥 감싸는 블록"으로 취급했다(①처럼). 그 결과 원래 경계 밖이던 후처리가 안으로 딸려 들어갔다.

고치는 방법은 간단하다. 후처리를 블록 밖으로 빼면 된다. 

ReflectToSuperKeyResultService.with_ancestor_locks(objective: self) do
  diff_history = ObjectiveCheckInDiff.call(self)
  accept_check_ins_and_create_history(user_id, diff_history)
end                                              # ← 여기서 커밋 + 락 해제

Objective::AutoCloseObjectiveIfProgressCompleteService.call(
  workspace:, current_user_id: user_id, objective: reload,
)

덤으로 락 보유 시간도 짧아진다. 자동 마감은 다른 목표를 건드리는 무거운 작업인데, 그동안 상위 핵심성과 행을 계속 잡고 있을 이유가 없다.

실무에서 쓸 판별 질문

  • "이 서비스/헬퍼는 트랜잭션을 여는가?" — 이건 메서드 이름이나 인자만 봐서는 모른다. 여는 쪽이면 문서화하거나, 최소한 with_ 같은 접두사로 "리소스를 소유하는 블록"임을 드러낸다. Ruby에서 File.open·with_lock처럼 블록을 받는 메서드는 대개 무언가를 열고 닫는다는 관습이 있다.
  • "블록 안에 넣은 코드가 원래 커밋 뒤에 돌던 것인가?" — 감싸기 리팩터링을 할 때 추가된 코드가 아니라 이동한 코드를 봐야 한다. 위치가 바뀐 줄이 있으면 경계가 바뀐 것이다.
  • "실패해도 본 작업은 살아야 하는 후처리가 있는가?" — 알림, 통계, 자동 마감처럼 부수적인 작업은 대개 그렇다. 있다면 트랜잭션 밖이거나, 최소한 requires_new: true + rescue로 격리돼야 한다.

퀴즈 1 — 무엇이 바뀌었나

기존에 accept_check_ins_and_create_history가 자기 안에서 ActiveRecord::Base.transaction을 열고 있었다. 호출부를 트랜잭션을 여는 블록으로 감싸면 이 메서드는 어떻게 되나?

퀴즈 2 — 후처리를 어디에 둘까

"실패해도 본 작업은 커밋돼야 하는" 후처리(알림 발송, 자동 마감 등)를 트랜잭션과 관련해 어디에 두는 게 맞나?

한 줄로 남기면

"블록으로 감쌌을 뿐"인 리팩터링은 없다. 그 블록을 제공하는 쪽이 트랜잭션을 연다면, 감싸는 순간 안에 들어간 모든 코드의 실패 전파 범위와 커밋 시점이 바뀐다. 특히 Rails의 트랜잭션은 조용히 합류하기 때문에 "이 메서드는 자체 트랜잭션이 있다"는 믿음이 호출부 하나 때문에 소리 없이 깨진다는 걸 기억하자.
