풀어야 했던 문제

appraisal_appraisers 테이블에는 "한 피평가자(appraisee)에게 같은 프로세스의 평가자가 1명만 배정돼야 한다"는 규칙이 있다 — 단, multi(다면평가)만 예외로 여러 명이 정상이다. 이 규칙은 이미 모델 검증(validate :single_appraiser_per_appraisee)으로 있었지만, 검증만으로는 못 막는 구멍이 셋 있었다.

  • insert_all — 대량 등록 시 쓰는 벌크 insert는 모델 콜백/검증을 아예 건너뛴다.
  • nested attributes 동시 저장 — 한 update! 안에서 여러 자식 레코드가 같이 저장되면 순서에 따라 검증이 서로의 존재를 못 볼 수 있다.
  • 진짜 동시 요청(TOCTOU) — "검증 시 조회"와 "실제 저장" 사이에 다른 요청이 끼어들면, 둘 다 통과한 뒤 저장되어 중복이 생긴다.

이런 구멍을 완전히 막는 유일한 방법은 DB 유니크 제약이다. 그런데 규칙이 "무조건 유니크"가 아니라 "multi만 제외하고 유니크"라는 게 문제였다.

Postgres였다면 — Partial Unique Index

Postgres는 WHERE 절이 붙은 부분(partial) 유니크 인덱스를 그대로 지원한다. 

-- Postgres라면 이렇게 한 줄로 끝난다
CREATE UNIQUE INDEX ON appraisal_appraisers (appraisal_process_id, appraisee_id)
  WHERE process_is_multi = FALSE;

"process_is_multi가 false인 행끼리만" 유니크를 강제하고, true인 행은 인덱스 대상에서 아예 빠진다. 그런데 MySQL(InnoDB)엔 이 문법 자체가 없다.

MySQL의 우회로 — "생성 컬럼 + NULL은 유니크 인덱스에서 중복 허용된다"는 성질

MySQL 유니크 인덱스에는 한 가지 성질이 있다 — NULL 값은 서로 "다르다"고 취급되어 몇 개가 있든 충돌하지 않는다. 이 성질을 이용하면 "조건부 유니크"를 흉내낼 수 있다.

① multi 여부를 컬럼으로 비정규화
process_is_multi
→
② "제외하고 싶은 행만 NULL"인
생성 컬럼을 만든다
→
③ (process_id, 그 생성 컬럼)에
유니크 인덱스
# db/migrate/..._add_single_appraiser_unique_index...rb
add_column :appraisal_appraisers, :process_is_multi, :boolean, default: false, null: false

add_column :appraisal_appraisers,
           :single_appraiser_appraisee_id,
           :bigint,
           as: 'CASE WHEN process_is_multi = TRUE THEN NULL ELSE appraisee_id END',
           stored: false

add_index :appraisal_appraisers,
          [:appraisal_process_id, :single_appraiser_appraisee_id],
          unique: true,
          name: 'uniq_single_appraiser_per_appraisee_process'

single_appraiser_appraisee_id는 "실제 저장되는 값"이 아니라 계산식(as: '...')으로 정의된 생성 컬럼이다 — multi 행이면 NULL, non-multi 행이면 진짜 appraisee_id 값을 갖는다. 그러면:

  • multi 행끼리는 이 컬럼 값이 전부 NULL → 유니크 인덱스가 NULL끼리는 충돌시키지 않음 → 몇 명이든 허용
  • non-multi 행끼리는 이 컬럼 값이 실제 appraisee_id → 같은 (process, appraisee) 조합이 2개면 진짜 유니크 위반으로 막힘

"조건부"라는 SQL 문법 없이, 조건을 컬럼 값으로 바꿔서(NULL이냐 아니냐) 평범한 유니크 인덱스에 넘기는 트릭이다.

퀴즈 1 — 이 트릭이 성립하는 이유

MySQL 유니크 인덱스에서 이 트릭이 통하는 핵심 성질은?

STORED로 만들면 벌어지는 일 — FK CASCADE와의 충돌

생성 컬럼은 STORED(디스크에 값을 실제로 저장, 조회 시 그대로 읽음)와 VIRTUAL(저장하지 않고 조회·인덱스 시점에 매번 계산) 두 방식이 있다. 처음엔 STORED로 시도했다가 이런 에러를 만났다. 

ERROR 1215 (HY000): Cannot add foreign key constraint

원인은 appraisee_id에 ON DELETE CASCADE FK가 걸려 있다는 것이다. 부모 행이 삭제되면 MySQL은 이 FK를 cascade로 처리하면서, STORED 생성 컬럼이 참조하는 값도 다시 계산해서 디스크에 반영해야 하는데, MySQL은 이 조합(STORED 생성 컬럼이 CASCADE 대상 컬럼을 참조)을 아예 거부한다. VIRTUAL은 애초에 아무것도 저장하지 않고 필요할 때마다 계산하기 때문에 이 문제가 없다 — 유니크 인덱스 강제력은 STORED와 동일하게 유지된다.

프론트의 computed property(Vue) / useMemo(React)로 비유하면, STORED는 "계산 결과를 변수에 캐싱해두는 것"이고 VIRTUAL은 "렌더링할 때마다 다시 계산하는 것"에 가깝다. 캐싱된 값이 있으면 그 값이 참조하는 원본이 바뀔 때 캐시도 다시 계산해서 저장해야 하는데, 여기선 그 "재계산 후 재저장" 스텝 자체가 CASCADE 삭제 상황과 맞물려 MySQL 내부적으로 지원되지 않는 조합이 된 것이다.

덤으로 걸린 문제 — MySQL DDL은 트랜잭션이 안 걸린다

이 마이그레이션은 add_column 두 번 + 백필 + add_index 여러 단계로 구성된다. MySQL의 DDL(ALTER TABLE 등)은 트랜잭션으로 묶이지 않는다 — 중간(예: add_index)에서 실패해도 그 전에 실행된 add_column들은 롤백되지 않고 그대로 남는다. 이 상태에서 마이그레이션을 단순 재실행하면 add_column이 "컬럼이 이미 존재한다"는 에러로 또 실패해 재시도 자체가 막힌다. 그래서 이 마이그레이션은 up/down 양쪽에 column_exists?/index_exists? 가드를 넣어, 몇 번을 재실행해도 "이미 되어 있으면 건너뛰고 안 된 부분만 마저 진행"하도록 멱등하게 만들었다. 

def up
  add_column :appraisal_appraisers, :process_is_multi, :boolean, default: false, null: false unless column_exists?(:appraisal_appraisers, :process_is_multi)
  # ... 백필은 재실행마다 항상 다시 돌려서, 이전 시도 이후 새로 생긴 잘못된 행까지 바로잡는다 ...
  return if index_exists?(:appraisal_appraisers, name: 'uniq_single_appraiser_per_appraisee_process')
  add_index ...
end

def down
  remove_index ... if index_exists?(...)
  remove_column ... if column_exists?(...)
end

퀴즈 2 — STORED가 거부되는 이유

이 생성 컬럼을 STORED로 만들면 왜 실패하는가?

핵심 요약

항목 설명
Postgres partial index CREATE UNIQUE INDEX ... WHERE 조건으로 조건부 유니크를 직접 지원
MySQL의 우회법 "제외 조건이면 NULL"인 생성 컬럼을 만들고, 유니크 인덱스의 NULL 중복 허용 성질을 이용
STORED vs VIRTUAL STORED는 디스크 저장(FK CASCADE 대상 참조 시 거부될 수 있음), VIRTUAL은 매번 계산(제약 없음, 인덱스는 동일하게 강제)
멱등한 마이그레이션 MySQL DDL은 트랜잭션이 안 걸리므로, 부분 실패 후 재시도가 가능하도록 up/down 모두 존재 여부 가드 필요
