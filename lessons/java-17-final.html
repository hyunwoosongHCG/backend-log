final

자바 · 실전 자바 기본편 섹션 9 ~20분
🎯 java-13에서 Member의 id처럼 "한 번 정해지면 그 이후로 아무도 못 바꾸게" 하고 싶은 필드가 있었다. 그걸 컴파일러가 강제하게 만드는 키워드가 final이다. 오늘은 변수·필드에 붙는 final만 다룬다 — 메서드·클래스에 붙는 final(오버라이딩·상속 금지)은 상속을 배우는 java-18 이후에 나온다.
강의를 수강하지 않고 작성한 레슨이다. 김영한 「실전 자바 - 기본편」 섹션 9의 전개는 정리 글 1편과 수강생 코드 저장소 1개를 교차 확인해 따라갔다 (하단 출처 — 이번 섹션도 정리 글 기준 3편에는 못 미친다, 대신 실제 예제 코드로 확인했다). Ruby·TypeScript 대비와 뿌 연결은 직접 쓴 것이다.

핵심 한 줄

final은 "한 번 값이 정해지면 그 이후로 다시 못 바꾼다"는 규칙을 컴파일러가 강제하게 만드는 키워드다. 지역 변수·매개변수·필드 어디에 붙어도 뜻은 같다 — 딱 한 번만 값을 넣을 수 있다.

지역 변수·매개변수에 붙이면

final int data1;
data1 = 10;        // 최초 한 번만 할당 가능
// data1 = 20;     // ❌ 재할당 시 컴파일 에러

final int data2 = 10;
// data2 = 20;     // ❌ 마찬가지

static void method(final int parameter) {
    // parameter = 20;   // ❌ final 매개변수도 값 변경 불가
}

final int data1;처럼 선언과 대입을 분리해도 된다 — 다만 그 딱 한 번의 대입 이후로는 자바가 재대입을 막는다. 매개변수에 붙이면 "이 메서드 안에서는 이 값을 절대 안 바꾼다"는 걸 코드로 명시하는 셈이다.

필드에 붙이면 — 두 가지 방식

public class ConstructInit {
    final int value;   // 초기값이 없으면 생성자에서 반드시 채워야 한다

    public ConstructInit(int value) {
        this.value = value;   // 생성 이후 값 변경 불가
    }
}
public class FieldInit {
    final int value = 10;   // 선언과 동시에 초기값 — 생성자에서는 못 바꾼다

    public FieldInit() {
        // this.value = 20;   // ❌ 이미 값이 있어서 재할당 불가
    }
}

final 필드는 딱 한 번, 둘 중 한 곳에서만 값을 받을 수 있다 — 선언하는 자리, 아니면 생성자 안. 둘 다 안 하면(초기값도 없고 생성자에서도 안 채우면) 컴파일 에러다 — java-13에서 배운 "필드는 자동 초기화된다"는 일반 규칙이 final에는 안 통한다. 자바 입장에서 "값이 안 정해진 final"은 말이 안 되기 때문이다.

직접 타이핑해보기 — ConstructInit(int value) 생성자를 작성하세요. final 필드 value에 매개변수 값을 대입합니다.

static final — 진짜 상수

public class Constant {
    public static final int MAX_USERS = 2000;
}

// 상수 없이 매직 넘버로 쓰면
if (currentUserCount > 1000) { ... }   // 1000이 뭘 뜻하는지 코드만 보면 모른다

// 상수로 쓰면
if (currentUserCount > Constant.MAX_USERS) { ... }   // 문맥이 바로 보인다

java-16에서 배운 static(클래스에 딱 하나, 모든 인스턴스가 공유)과 오늘의 final(한 번 정하면 재할당 불가)을 합치면 진짜 상수가 된다 — 값이 하나뿐이고, 그 하나가 절대 안 바뀐다. 관례상 이름은 전부 대문자 + 언더스코어로 쓴다(MAX_USERS, HOURS_IN_DAY). 매직 넘버(코드만 보고는 뜻을 알 수 없는 숫자)를 상수로 뽑아두면 문맥이 드러나고, 값을 바꿀 곳도 한 군데로 좁혀진다.

final 참조형 변수 — 헷갈리기 쉬운 지점

final Data data = new Data();
// data = new Data();   // ❌ 재할당 불가 — data에 다른 주소를 넣을 수 없다

data.value = 10;         // ✅ OK — data.value는 final이 아니다
System.out.println(data.value);
data.value = 20;         // ✅ 이것도 OK — 몇 번이고 바꿀 수 있다

java-11의 값 복사 대원칙을 그대로 가져오면 정확히 설명된다. final이 막는 건 data라는 상자 안의 값(주소)뿐이다. 참조형 변수의 값은 주소이므로, final은 "이 주소를 다른 주소로 바꿔치기하지 못한다"는 뜻이지 "그 주소가 가리키는 객체 내부를 못 바꾼다"는 뜻이 아니다. 상자를 다른 상자로 바꿔치기하는 것과, 상자 안의 물건을 계속 갈아 끼우는 것은 별개다. 

public class Member {
    private final String id;    // 한 번 정해지면 절대 안 바뀐다
    private String name;        // 계속 바뀔 수 있다

    public Member(String id, String name) {
        this.id = id;
        this.name = name;
    }

    public void changeData(String id, String name) {
        // this.id = id;   // ❌ 컴파일 에러 — id는 final
        this.name = name;   // ✅ name은 자유롭게 변경
    }
}

Member의 id처럼 객체가 살아있는 동안 절대 안 바뀌어야 하는 값에 final을 붙이면, "이 필드를 실수로라도 바꾸면 안 된다"는 규칙을 다른 개발자가 코드를 읽지 않아도 컴파일러가 대신 지켜준다.

직접 타이핑해보기 — Member의 changeData(String id, String name) 메서드를 작성하세요. id는 final이라 건드리지 않고, name만 매개변수 값으로 바꿉니다.

TS의 const가 똑같은 함정을 가지고 있다 — const arr = []; arr.push(1);은 되지만 arr = [2]는 안 된다. "재할당 금지"와 "내부 불변"은 다른 이야기라는 게 자바·TS 둘 다 같다. Ruby는 대문자로 시작하는 상수(MAX_USERS = 2000)에 재할당하면 에러가 아니라 경고만 뜨고 실제로는 바뀐다 — 자바는 final을 컴파일 에러로 완전히 막는다는 점이 다르다.

뿌에서는 이렇게 보인다

"절대 안 바뀌는 값"이라고 하면 엔티티의 id가 제일 먼저 떠오르지만, 실무에서는 보통 JPA 엔티티 필드에 final을 안 쓴다. 이유는 java-13에서 배운 그 메커니즘과 정면으로 부딪히기 때문이다. 

@Entity
public class Listing {
    private final Long id;   // ⚠️ 이렇게 하면 문제가 생긴다
    // ...

    protected Listing() {}   // JPA가 이 생성자로 빈 껍데기를 만든 뒤
    // 리플렉션으로 id 필드를 나중에 채워야 하는데, final은
    // "생성자 안에서 딱 한 번"만 허용하므로 이 2단계 채우기와 충돌한다
}

JPA는 DB에서 읽은 값을 빈 생성자로 껍데기를 만든 다음(1단계) 리플렉션으로 필드에 나중에 채워 넣는다(2단계). 그런데 final은 그 채우기가 정확히 "생성자 본문 안"에서 일어나야만 인정한다 — 생성자 밖(2단계)에서 리플렉션으로 채우는 방식과는 애초에 안 맞는다. 그래서 엔티티 필드는 보통 final 없이 private으로만 막고, "바꾸면 안 된다"는 규칙은 setter를 아예 안 만드는 것으로 대신 지킨다.

한 줄로 남기면

final은 "한 번 정해지면 다시 못 바꾼다"를 컴파일러가 지켜주는 키워드다. 변수·매개변수는 최초 한 번, 필드는 선언 자리나 생성자 중 한 곳에서만. 참조형에서는 상자(주소)를 못 바꾸는 것이지 상자 안의 물건까지 얼리는 게 아니라는 것만 조심하면 된다. 그리고 static과 합쳐지면 진짜 상수가 되지만, JPA 엔티티처럼 나중에 값을 채워 넣어야 하는 객체에는 오히려 못 쓰는 경우도 있다는 것이 오늘 배운 규칙의 실전 경계선이다.
