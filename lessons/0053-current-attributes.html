상황 — 인자로 넘기자니 중간이 너무 많다

상위 핵심성과 자동 반영에 락을 도입하면서 규칙이 하나 생겼다. 락은 쓰기 트랜잭션이 열리기 전에 잡아야 한다. 그런데 벌크 체크인 워커는 정상적으로 이 규칙을 두 번 밟는다.

안쪽 호출은 위반이 아니다. 바깥에서 이미 잠근 집합의 부분집합이니 다시 잠글 필요도 없고, 그 트랜잭션은 락 획득 이후에 열렸으니 안전하다. 하지만 안쪽 코드는 그걸 알 방법이 없다. "이미 잠갔음"을 알려면 인자를 뚫어야 하는데, 중간에 워커 → 서비스 → 모델 메서드가 줄줄이 있고 그 계층들은 락 얘기를 전혀 몰라도 되는 코드다.

프론트의 props drilling과 똑같은 문제다. 최상위에서 잡은 값을 6단계 아래 컴포넌트가 써야 하는데, 중간 5개는 그 값에 아무 관심이 없다. React는 이걸 Context로 푼다. Rails에서 대응하는 도구가 CurrentAttributes다.

왜 그냥 전역 변수를 쓰면 안 되나

Ruby에서 "아무 데서나 읽는 값"을 만드는 방법은 여러 가지다. 문제는 서버 환경이다.

  • $global / 클래스 변수 — 프로세스 전체가 공유한다. Puma/Sidekiq는 한 프로세스에서 여러 요청·잡을 스레드로 동시에 처리하므로, A 요청이 넣은 값을 B 요청이 읽는다. 즉시 사고.
  • Thread.current[:key] — 스레드 격리는 된다. 그런데 정리를 안 해준다. 스레드는 재사용되므로(스레드 풀), 이전 요청이 남긴 값이 다음 요청에 그대로 보인다. ensure로 매번 지우는 걸 사람이 기억해야 한다.

ActiveSupport::CurrentAttributes는 이 둘의 문제를 동시에 푼다. 내부적으로는 스레드(정확히는 IsolatedExecutionState) 단위 저장이고, Rails executor가 요청·잡의 경계마다 자동으로 reset한다.

실제 코드

class Objective::CheckIns::ReflectToSuperKeyResultService < ApplicationService
  # 이 스레드에서 이미 FOR UPDATE로 잠근 조상 KR id.
  class LockedKeyResults < ActiveSupport::CurrentAttributes
    attribute :ids
  end
  ...
end

attribute :ids 한 줄로 LockedKeyResults.ids / LockedKeyResults.ids = [...] 접근자가 생긴다. 그리고 사용부: 

def lock(key_result_ids)
  already_locked = LockedKeyResults.ids || []

  # 바깥 lock이 이미 전부 잠갔다면(정상 재진입) 다시 잠글 필요가 없다
  return yield if (key_result_ids - already_locked).empty?

  # 아직 안 잠근 id가 남았는데 트랜잭션이 이미 열려 있으면 진짜 위반
  report_lock_precondition_violation(key_result_ids - already_locked) if app_transaction_open?

  ActiveRecord::Base.transaction do
    LockedKeyResults.ids = already_locked | key_result_ids
    begin
      key_result_ids.sort.each {|id| KeyResult.lock.where(id: id).pluck(:id) }
      yield
    ensure
      LockedKeyResults.ids = already_locked      # ← 중첩 복원
    end
  end
end

핵심은 "정상 재진입"과 "진짜 위반"을 구분하는 것이다. 둘 다 겉보기엔 "트랜잭션이 열린 상태에서 락을 요청함"으로 똑같이 생겼는데, 이미 잠근 집합을 알고 있으면 부분집합인지 확인해서 갈라낼 수 있다.

executor가 리셋해주는데 ensure는 왜 있나

executor의 리셋은 요청·잡의 시작과 끝에 일어난다. 그건 "다음 요청에 안 새게" 하는 보장이고, 같은 요청 안에서 중첩 호출이 끝났을 때 이전 값으로 되돌리는 것은 별개다.

executor reset
요청·잡 경계
= 다음 요청 오염 방지
≠
ensure 복원
블록 경계
= 같은 요청 안 중첩 복원

ensure에서 already_locked(들어올 때의 값)로 되돌리는 이유가 이것이다. nil로 지우면 바깥 락이 아직 유효한데 안쪽이 그 기록을 지워버린다. React에서 Context Provider를 중첩할 때 안쪽이 끝나면 바깥 값이 다시 보여야 하는 것과 같다.

남용 주의 — 숨은 전역 상태다

CurrentAttributes는 Rails 공식 기능이지만 논쟁이 있는 도구다. 가장 흔한 용례인 Current.user조차 "모델이 현재 로그인 유저를 알게 되는 게 맞나"로 의견이 갈린다. 이유는 명확하다 — 인자로 안 받는 의존은 시그니처에 안 드러난다.

  • 메서드만 봐서는 이 값을 쓰는지 알 수 없다 (테스트에서 세팅을 빼먹기 쉽다)
  • 호출 순서에 의존한다 (누가 언제 넣었는지가 동작을 좌우)
  • 스레드 밖으로 못 넘어간다 — Thread.new나 perform_async로 넘어가면 값이 없다

이번 코드에서 괜찮다고 본 이유는 용도가 좁기 때문이다. 비즈니스 로직이 이 값을 읽어서 결과를 바꾸지 않는다. 오직 가드가 오탐을 내지 않도록 "이미 잠갔다"를 기억하는 용도고, 값이 없으면 []로 안전하게 떨어진다. 도메인 결정에 쓰이면 위험하고, 진단·가드에 쓰이면 상대적으로 안전하다가 기준이 된다.

CurrentAttributes는 "요청 하나의 수명만 사는 Context"다. props drilling을 피하는 값이지만, React Context와 마찬가지로 암묵적 의존을 만든다는 대가가 있다. 도메인 결정을 좌우하는 값보다는 진단·가드·감사 로그처럼 없어도 안전하게 떨어지는 값에 쓰는 게 안전하다. 그리고 스레드를 새로 띄우거나 잡으로 넘어가는 순간 값은 따라가지 않는다는 걸 기억할 것.
