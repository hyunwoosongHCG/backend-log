레슨 24는 "트랜잭션 하나 안"의 이야기였다

레슨 24에서 다룬 원자성(Atomicity)은 하나의 트랜잭션 내부의 이야기였다 — 그 안의 여러 쓰기가 전부 성공하거나 전부 실패하거나. 그런데 ACID에는 원자성 말고 격리성(Isolation)도 있다. 이건 완전히 다른 질문이다 — "동시에 실행 중인 서로 다른 트랜잭션들이 서로에게 어디까지 보이는가?"

두 명의 매니저가 동시에 같은 Objective 상세 페이지를 열어놓고, 한 명은 진행률을 조회하고 다른 한 명은 그 진행률을 수정해서 저장하는 상황을 생각해보자. 프론트에서는 "낙관적 UI 업데이트" 정도로 생각하고 넘어갈 수 있지만, DB 입장에서는 이게 정확히 격리 수준이 다루는 문제다 — 두 트랜잭션이 겹치는 순간, 한쪽이 다른 쪽의 "아직 커밋 안 된" 또는 "방금 바뀐" 데이터를 보게 해줄 것이냐를 DB가 결정해야 한다.

격리가 느슨하면 생기는 3가지 읽기 이상현상

격리 수준이 낮을수록 아래 현상들이 일어날 수 있다. SQL 표준이 정의하는 3가지다.

① Dirty Read — 커밋 전 데이터를 읽어버림

시점 트랜잭션 A 트랜잭션 B
t1 UPDATE objectives SET stage='open' WHERE id=1 (아직 커밋 안 함) —
t2 — SELECT stage FROM objectives WHERE id=1 → 'open'을 읽음
t3 ROLLBACK (A가 취소됨!) 이미 존재한 적 없는 값을 읽고 그걸로 뭔가 처리해버림

② Non-Repeatable Read — 같은 행을 두 번 읽었는데 값이 다름

한 트랜잭션 안에서 같은 행을 두 번 조회했는데, 그 사이에 다른 트랜잭션이 값을 바꾸고 커밋해버려서 두 번째 조회 결과가 첫 번째와 달라지는 현상.

③ Phantom Read — 같은 조건인데 행의 개수가 달라짐

한 트랜잭션 안에서 같은 WHERE 조건으로 두 번 조회했는데, 그 사이에 다른 트랜잭션이 조건에 맞는 행을 INSERT해버려서 두 번째 조회에서 없던 행(유령, phantom)이 나타나는 현상. Non-Repeatable Read가 "같은 행의 값 변화"라면, Phantom Read는 "같은 조건의 행 개수 변화"다.

퀴즈 1 — 현상 구분

트랜잭션 A가 WHERE status='pending'으로 두 번 조회했다. 첫 번째는 5건, 두 번째는 6건이었다 (그 사이 B가 새 pending 행을 커밋함). 이건 어떤 현상인가?

SQL 표준 4단계 격리 수준

이 3가지 현상을 각각 어디까지 막아주느냐로 SQL 표준은 4단계 격리 수준을 정의한다. 아래로 갈수록 더 엄격하고 안전하지만, 그만큼 락을 더 많이/오래 걸어서 동시 처리량(throughput)은 떨어진다 — 안전성과 동시성은 항상 트레이드오프다.

격리 수준 Dirty Read Non-Repeatable Read Phantom Read
READ UNCOMMITTED 발생 가능 발생 가능 발생 가능
READ COMMITTED ✅ 방지 발생 가능 발생 가능
REPEATABLE READ ✅ 방지 ✅ 방지 표준상 발생 가능 (MySQL은 실제로 대부분 방지 — 아래 참고)
SERIALIZABLE ✅ 방지 ✅ 방지 ✅ 방지

MySQL(InnoDB)의 기본값은 REPEATABLE READ

여기서 실무 함정 하나 — PostgreSQL, Oracle, SQL Server는 기본 격리 수준이 READ COMMITTED다. Performance Plus가 쓰는 MySQL만 기본값이 REPEATABLE READ다. 다른 DB를 먼저 써본 사람이 MySQL로 넘어오면 "어? 왜 이 값이 안 바뀌어 보이지"하고 헷갈리는 지점이 바로 여기다. 

SELECT @@transaction_isolation;
-- MySQL 기본값: REPEATABLE-READ

그리고 표에서 "표준상 발생 가능"이라고 써둔 Phantom Read — MySQL의 InnoDB는 MVCC(다중 버전 동시성 제어)와 Next-Key Lock이라는 자체 구현 덕분에 REPEATABLE READ에서도 실제로는 Phantom Read 대부분을 막아준다. 이건 SQL 표준이 요구하는 최소 보장을 MySQL이 자체 구현으로 더 얹어준 것이다 — 표준 이론과 특정 DB의 실제 동작이 다를 수 있다는 걸 보여주는 좋은 예다. (레슨 43에서 본 Next-Key Lock의 "갭 락(gap lock)"이 바로 이 방지 메커니즘의 일부다.)

퀴즈 2 — MySQL 기본 격리 수준

Performance Plus가 쓰는 MySQL(InnoDB)의 기본 격리 수준은?

그런데 격리 수준만으로는 못 막는 것 — Lost Update

Lost Update(유실된 업데이트)는 SQL 표준의 3대 현상 목록엔 없지만, 실무에서 가장 자주 만나는 동시성 버그다. 레슨 42 도입부에서 든 재고 예시가 정확히 이거였다 — 애플리케이션 코드가 읽고(SELECT) → 계산 → 쓰는(UPDATE) 두 단계로 나뉘어 있을 때 생긴다.

시점 트랜잭션 A 트랜잭션 B
t1 progress 읽음 → 5 progress 읽음 → 5
t2 앱 코드에서 5 + 1 = 6 계산 → UPDATE ... SET progress = 6 커밋 —
t3 — 앱 코드에서 5 + 1 = 6 계산 (A의 변경을 모름) → UPDATE ... SET progress = 6 커밋. A의 +1이 사라짐 (실제로는 7이어야 함)

핵심은 이거다 — REPEATABLE READ든 뭐든, 격리 수준은 "한 트랜잭션 안에서 읽은 값이 일관돼 보이는가"를 보장할 뿐, "다른 트랜잭션이 그 사이 값을 바꿨는지 앱 코드가 알아채게 해주는 것"은 아니다. A와 B는 각자 자기 트랜잭션 관점에서 "5를 읽고 6으로 바꿨다"고 믿지만, 두 UPDATE가 순서대로 실행되면서 B가 A를 그냥 덮어써버린다. 이걸 막으려면 격리 수준을 SERIALIZABLE까지 올리거나(동시성 대가가 큼), 레슨 42에서 배운 with_lock(비관적 락)으로 애초에 두 번째 트랜잭션이 첫 번째가 끝날 때까지 기다리게 만들어야 한다.

레슨 42에서 든 setCount(count + 1) vs setCount(prev => prev + 1) 비유를 다시 가져오면 — Lost Update는 정확히 setCount(count + 1) 패턴이 DB 버전으로 일어난 것이다. "오래된 값(count, progress)을 들고 계산해서 덮어쓰기" 자체가 문제의 근원이고, 이건 격리 수준이라는 "읽기 규칙"이 아니라 "쓰기 시점에 최신값을 다시 확인하거나 잠그는" 별도의 장치로만 막을 수 있다.

퀴즈 3 — 격리 수준의 한계

REPEATABLE READ(MySQL 기본값)만으로 애플리케이션의 "SELECT로 읽고 계산해서 UPDATE로 쓰는" 패턴에서 Lost Update를 완전히 막을 수 있는가?

Rails에서 격리 수준 지정하기

거의 안 쓰지만, 정말 필요하면 트랜잭션 블록 단위로 격리 수준을 올릴 수 있다. 

ActiveRecord::Base.transaction(isolation: :serializable) do
  # 이 블록만 SERIALIZABLE로 실행됨
end

단, 이미 열려 있는(중첩된) 트랜잭션 안에서는 격리 수준을 새로 지정할 수 없다 — 격리 수준은 트랜잭션이 "시작되는 시점"에만 정할 수 있는 값이기 때문이다. 이미 시작된 트랜잭션에 합류(join)하면서 격리 수준을 바꾸려 하면 Rails가 에러를 던진다(정확한 에러 메시지는 Rails 버전마다 다를 수 있음).

실무에서는 격리 수준 자체를 건드리기보다, 기본값(REPEATABLE READ)을 그대로 두고 진짜 동시성 경쟁이 생기는 지점만 with_lock으로 좁게 잠그는 쪽이 훨씬 흔한 패턴이다 — SERIALIZABLE로 전체를 올리면 안전하지만 그만큼 모든 요청의 처리량이 떨어지기 때문이다.
