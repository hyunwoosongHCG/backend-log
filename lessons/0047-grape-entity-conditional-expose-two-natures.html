🎯 핵심성과 자동 반영 기능의 API 응답에 필드 하나를 추가하면서, "이 필드도 쿼리 조건에 따라 조건부로 노출해야 하나?"를 고민하다가 기존 코드에서 이미 쓰이고 있던 같은 패턴을 다시 읽고 비교하며 정리한 것 — MISSION.md

Grape::Entity의 if:은 이렇게 생겼다

목표 목록 API의 응답 엔티티에는 if: 옵션이 붙은 필드가 여러 개 있다. 

class Entities::Objectives::IndexEntity < Grape::Entity
  expose :position, documentation: { desc: '개인목표순서' }, if: :sort_position
  expose :team_position, documentation: { desc: '팀 목표 순서' }, if: :view_team
  # ...
end

if: :view_team은 present :data, objectives, view_team: true, with: Entities::Objectives::IndexEntity처럼 present 호출 시 넘긴 옵션 해시를 보고, 그 키가 참일 때만 해당 필드를 응답에 넣겠다는 뜻이다. 여기까지는 "쿼리 조건에 따라 응답 모양을 바꾸는 관례"로 단순하게 이해하고 넘어가기 쉽다. 그런데 이 두 필드가 if:가 붙은 이유는 서로 완전히 다르다.

이유 ① — 다른 SQL 분기에서 만들어진 "가상 컬럼"이라 크래시가 난다

컨트롤러를 보면 team_position은 조회 조건이 'team'일 때만 특별한 SQL로 만들어진다. 

# app/controllers/v2/objectives/objectives.rb
case view_type
when 'team'
  objectives = objectives.left_joins(:team_objective_positions)
                          .select('team_objective_positions.position AS team_position')
when 'assigned'
  # team_position을 SELECT하지 않는 다른 쿼리
end

team_position은 objectives 테이블의 진짜 컬럼이 아니라, 이 SELECT ... AS team_position으로 그 순간에만 만들어지는 가상 컬럼이다. view_type이 'assigned'인 분기로 로드된 레코드에는 애초에 team_position이라는 속성 자체가 없다. 만약 엔티티가 if: 가드 없이 이 필드를 무조건 노출하려 하면, 그 분기에서 로드된 레코드에 대해서는 ActiveModel::MissingAttributeError가 난다.

영수증에 "포인트 적립액"란이 있는데, 이 란은 포인트 카드로 결제했을 때만 실제로 계산되는 값이라고 하자. 카드 결제 없이 결제한 영수증에는 그 항목 자체가 계산될 방법이 없다 — 빈칸으로 두는 게 아니라, "이 영수증 양식엔 그 항목이 아예 없다"에 가깝다. if: 가드는 "이 영수증엔 그 항목이 실제로 존재하는 경우에만 인쇄해라"는 조건이다. 이 가드가 없으면 프린터가 존재하지도 않는 값을 읽으려다 멈춰버린다(에러).

즉 if: :view_team은 성능 최적화가 아니라 "이 필드가 계산될 수 있는 상황인지"를 확인해서 크래시를 막는 정합성 가드다.

퀴즈 1 — 이 if:이 없으면 무슨 일이 생기는가

team_position이 'team' 조회 분기에서만 SELECT되는 가상 컬럼일 때, if: :view_team 가드 없이 'assigned' 분기로 로드된 레코드를 직렬화하면 어떻게 되는가?

이유 ② — 계산은 항상 가능하지만, 안 쓸 땐 굳이 안 하고 싶은 경우

반면 핵심성과 자동 반영 기능에서 새로 추가한 필드는 사정이 다르다. 

expose :auto_reflect_target_key_result_ids,
       documentation: { desc: '이 목표의 체크인이 처리되면 자동 반영을 받게 될 상위 핵심성과 Ids' }

# Objective 모델의 순수 Ruby 메서드 — 어떤 조회 분기로 로드됐든 항상 계산 가능
def auto_reflect_target_key_result_ids
  # super_key_result 체인을 순회해서 계산
end

auto_reflect_target_key_result_ids는 DB의 가상 컬럼이 아니라 순수 Ruby 모델 메서드다. 어떤 쿼리 분기로 로드된 레코드든 이 메서드는 항상 정상적으로 계산된다 — 크래시 위험이 없다. 그런데도 "특정 화면(승인 대기 목록)에서만 필요한 필드인데, 다른 화면 조회에서까지 매번 계산하는 게 비용 낭비 아닌가"라는 고민이 들 수 있다. 이건 계산이 가능한가의 문제가 아니라, 계산이 필요 없을 때 굳이 계산하지 않고 싶은 페이로드/성능 최적화 문제다.

실제로 이 필드는 프론트에서 아직 실사용 패턴이 확정되지 않은 상태라, "성급한 최적화"를 피하려고 게이팅 없이 그대로 뒀다 — 크래시 위험이 없는 필드라 나중에 실제 트래픽 패턴을 보고 필요할 때 게이팅해도 늦지 않다는 판단이었다.

퀴즈 2 — 두 이유 구분하기

순수 Ruby 모델 메서드를 expose하는 필드에 if: 게이팅을 안 붙이고 모든 조회 분기에서 항상 노출하기로 했다. 이 결정이 위험한가?

핵심 요약

게이팅 이유 예시 안 하면 생기는 일
정합성 (필수) team_position — 특정 SQL 분기에서만 SELECT되는 가상 컬럼 ActiveModel::MissingAttributeError 크래시
성능/페이로드 (선택) auto_reflect_target_key_result_ids — 항상 계산 가능한 순수 Ruby 메서드 크래시는 없음, 불필요한 계산/페이로드 비용만 있음

같은 if: 문법이라도, "이 필드가 지금 계산될 수 있는 상태인가"(정합성)와 "계산은 되지만 지금 굳이 계산할 필요가 있는가"(최적화)는 완전히 다른 질문이다. 코드 리뷰에서 if:이 붙은 필드를 볼 때 이 둘 중 어느 쪽인지 구분해서 읽는 습관이 필요하다 — 전자라면 게이팅을 없애면 안 되고, 후자라면 게이팅 여부는 실사용 패턴을 보고 결정해도 된다.
