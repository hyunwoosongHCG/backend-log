상황 — 락을 빼도 스펙이 통과했다

형제 목표 동시 승인 갱신 손실을 막으려고 워커에 조상 목표 잠금을 넣었다. 레슨 54에서 배운 대로 :truncation 전략에 태우고 실제 스레드 두 개로 동시성 스펙도 썼다. 전부 초록.

그런데 스펙이 진짜로 뭘 지키는지 확인하고 싶어서, 고친 것을 임시로 되돌려봤다. 워커의 .lock을 한 단어 지운 것이다. 

# 이렇게 있던 것을
Objective.where(id: lock_objective_ids).order(:id).lock.load

# 이렇게 바꿔서 돌려봤다
Objective.where(id: lock_objective_ids).order(:id).load

값 수렴 스펙 2개가 그대로 통과했다. 락을 통째로 지웠는데도.

원인 — 경합 자체가 성립하지 않았다

스펙이 이렇게 생겨 있었다. 

first_event  = check_in_and_create_event!(first_child, 200)   # 100%
second_event = check_in_and_create_event!(second_child, 100)  # 50%

run_concurrently([first_event.id, second_event.id])           # 스레드 2개

expect(parent_key_result.reload.value).to eq(75)              # (100% + 50%) / 2

문제는 두 체크인이 워커가 돌기 전에 이미 다 커밋돼 있다는 것이다. 그러면 두 워커가 읽는 데이터가 같으니, 둘 다 같은 값 75를 계산한다. 누가 먼저 쓰든 결과가 75다. 락이 있든 없든 같다.

내가 쓴 스펙
체크인 A 커밋
체크인 B 커밋
→ 워커 2개 시작
둘 다 75 계산
≠
실제 버그
체크인 A 커밋
→ 워커 A가 읽음
체크인 B 커밋
→ 워커 A가 씀 (덮어씀)
"스레드를 두 개 띄웠다"는 동시성을 재현했다는 뜻이 아니다. 두 스레드가 같은 입력에서 같은 답을 내면, 아무리 병렬로 돌려도 순서가 결과를 바꾸지 않는다. 경합은 한쪽이 읽은 뒤 다른 쪽이 쓰는 창이 있을 때만 생긴다.

해결 — 인터리빙을 강제한다

"A가 계산을 마친 뒤에 B의 체크인이 커밋된다"는 순서를 코드로 못 박아야 한다. sleep으로 맞추면 flaky해지니 Queue로 신호를 주고받는다. 

calculated = Queue.new
resume     = Queue.new

# 반영값 계산이 끝난 직후 첫 호출만 붙잡는다
allow_any_instance_of(ReflectService).to receive(:calculate_reflected_value)
  .and_wrap_original do |original, key_result|
    value = original.call(key_result)
    unless paused
      paused = true
      calculated << :done   # "나 계산 끝났어"
      resume.pop            # 재개 신호를 기다린다
    end
    value
  end

first_thread = perform_in_thread(first_event.id)
calculated.pop                                    # A가 stale한 값으로 계산을 마칠 때까지 대기

second_event = check_in_and_create_event!(second_child, 160)   # 이제서야 B가 커밋
second_thread = perform_in_thread(second_event.id)
sleep 0.5                                         # 락이 없다면 B가 이 사이에 끝까지 진행

resume << :go
[first_thread, second_thread].each(&:join)

expect(parent_key_result.reload.value).to eq(90)  # (100% + 80%) / 2

이제 락을 빼면 90이 아니라 50이 나오며 실패한다. A가 B를 못 본 상태로 계산한 50이, B가 쓴 90을 덮어쓰기 때문이다. 비로소 스펙이 락의 존재를 증명한다.

같은 함정의 다른 얼굴 — 무엇을 재지 않았는가

락 보유 시간도 측정했다. "같은 조상을 공유하는 배치 크기"를 늘려가며 쟀다. 

하위  5건 → 락 보유 1.06초
하위 20건 → 1.27초
하위 50건 → 4.26초
하위160건 → 11.29초   (timeout 50초까지 4.4배 여유)

숫자가 있으니 안심했다. 그런데 리뷰에서 다른 축을 물었다 — "워크스페이스 전체 미처리 이벤트가 많을 때는?" 그 축은 재지 않았다. 재보니 후보 이벤트마다 재귀 조회를 돌아 이벤트당 쿼리가 5N이었다. 

이벤트 120건 → 스캔 1회 337ms · 596쿼리 · 전체 13.14초   (O(N²))
                ↓ 후보를 SQL 단계에서 좁힌 뒤
             → 스캔 1회   4ms ·   5쿼리 · 전체  2.31초   (이벤트당 쿼리 24.0 고정)

판별력 문제와 뿌리가 같다. "쟀다"가 "충분히 쟀다"는 뜻이 아니다. 측정에는 축이 여러 개 있고, 한 축의 그래프가 예쁘면 나머지 축을 안 보게 된다.

이벤트당 쿼리 수를 세는 것이 축을 구분하는 가장 싼 방법이었다. 시간은 노이즈가 섞여 선형인지 제곱인지 헷갈리는데, 쿼리 수는 24.0처럼 딱 떨어져서 O(N)인지 O(N²)인지 바로 갈린다. (레슨 9의 sql.active_record 구독을 그대로 쓴다)

통과하는 스펙은 두 가지 중 하나다 — 코드가 맞거나, 스펙이 아무것도 안 보고 있거나. 둘을 구분하는 유일한 방법은 고친 것을 되돌려 실패를 확인하는 것이다. 같은 의심을 측정에도 적용해야 한다: 한 축을 재고 만족하기 전에 "무엇을 재지 않았는가"를 스스로 물어야 한다.
