접근 제어자

자바 · 실전 자바 기본편 섹션 7 ~20분
🎯 java-12에서 "지금은 필드가 아직 public이라 캡슐화는 강제가 아니라 약속 수준"이라고 했다. 이번 레슨이 그 약속을 진짜 강제로 바꾸는 도구다. java-13에서 미뤄둔 protected Listing() {}의 protected도 여기서 매듭짓는다.
강의를 수강하지 않고 작성한 레슨이다. 김영한 「실전 자바 - 기본편」 섹션 7의 전개와 예제는 수강생 정리 글 3편을 교차 확인해 따라갔고(하단 출처), Ruby·TypeScript 대비와 뿌 연결은 직접 쓴 것이다.

핵심 한 줄

접근 제어자(access modifier)는 "누가 이 필드·메서드를 볼 수 있는가"를 자바 컴파일러가 직접 검사하게 만드는 키워드다. private · (생략 시) default · protected · public 네 단계로, 범위가 좁을수록 제한이 강하다.

왜 필요한가 — 막을 수 없는 자유는 위험하다

public class Speaker {
    int volume;

    Speaker(int volume) {
        this.volume = volume;
    }

    void volumeUp() {
        if (volume >= 100) {
            System.out.println("음량을 증가할 수 없습니다. 최대 음량입니다.");
        } else {
            volume += 10;
            System.out.println("음량을 10 증가합니다.");
        }
    }
}

volumeUp()은 100을 넘지 않게 막아준다. 그런데 volume이 아직 public이라, 이 안전장치를 통째로 무시하고 speaker.volume = 200;을 직접 쓸 수 있다 — 스피커가 고장 나는 값이다. java-12에서 배운 캡슐화("메서드로만 바꾸자")는 약속일 뿐 강제가 아니었다. 좋은 프로그램은 무한한 자유를 주는 프로그램이 아니라 적절한 제약을 주는 프로그램이다 — 그 제약을 문법으로 강제하는 것이 접근 제어자다.

네 가지 접근 제어자

접근 제어자 접근 가능 범위
private 모든 외부 호출을 막는다 — 같은 클래스 안에서만
default(생략) 같은 패키지 안에서는 허용
protected 같은 패키지 + 패키지가 달라도 상속 관계면 허용
public 모든 외부 호출을 허용

제한이 강한 순서로 외우면 편하다: private > default > protected > public. java-14에서 배운 패키지가 여기서 다시 나온다 — default와 protected의 경계가 바로 "같은 패키지냐 아니냐"이기 때문이다.

Speaker를 실제로 막아보기

public class Speaker {
    private int volume;    // 이제 클래스 밖에서 못 건드린다

    Speaker(int volume) {
        this.volume = volume;
    }

    void volumeUp() {
        if (volume >= 100) {
            System.out.println("음량을 증가할 수 없습니다. 최대 음량입니다.");
        } else {
            volume += 10;
        }
    }
}

Speaker speaker = new Speaker(50);
speaker.volumeUp();       // OK — 메서드를 통해서만 접근
speaker.volume = 200;     // ❌ 컴파일 에러 — private 필드는 밖에서 못 본다

int volume;이 private int volume;으로 바뀐 것뿐인데, speaker.volume = 200;이 이제 런타임 버그가 아니라 컴파일 에러가 된다. java-12의 MusicPlayer도 지금까지는 필드가 다 열려 있었다 — 거기에 private만 붙이면 오늘 배운 게 바로 적용된다.

값을 읽고 싶으면 — getter

막상 private으로 잠그면 클래스 밖에서 값을 읽을 방법도 없어진다. System.out.println(speaker.volume)도 이제 컴파일 에러다. 그래서 "읽기 전용 문"을 메서드로 하나 열어준다 — 관례상 이름은 get + 필드명이다. 

public class Speaker {
    private int volume;

    // ...

    int getVolume() {
        return volume;
    }
}

System.out.println(speaker.getVolume());   // OK — 문을 통해서 읽는다

값을 바꾸는 문도 필요하면 setVolume(int volume)처럼 만들 수 있지만, 아무 검증 없이 그대로 대입만 하는 setter는 public 필드와 다를 게 없다는 점을 조심해야 한다. volumeUp()처럼 규칙이 들어간 메서드가 진짜 캡슐화이고, setter는 그 규칙 없이 값만 바꿔주는 가장 약한 형태다.

Ruby의 attr_accessor :volume이 정확히 이 getter/setter 한 쌍을 자동으로 만들어준다 — 자바는 그걸 손으로 하나씩 쓴다는 차이뿐이다. TS 클래스의 private/public도 개념이 거의 그대로 겹친다. 주의할 건 Ruby의 private/protected다 — 이름은 같지만 뜻이 다르다. Ruby의 private은 "리시버(obj.method의 obj)를 명시하지 않고 호출해야 한다"는 규칙이지, 자바처럼 "어디서 접근 가능한가"라는 범위 개념이 아니다. 같은 단어로 다른 개념을 가리키니, Ruby 감각을 그대로 자바에 옮기면 오히려 헷갈린다.

뿌에서는 이렇게 보인다 — protected의 정체

java-13에서 미뤄둔 질문을 이제 풀 수 있다. JPA 엔티티는 왜 빈 생성자를 public도 private도 아닌 protected로 열어둘까. 

@Entity
public class Listing {
    private Long id;
    private String address;
    private int price;

    protected Listing() {}   // JPA 전용 빈 생성자

    public Listing(String address, int price) {
        this.address = address;
        this.price = price;
    }
}
  • public이면 안 되는 이유 — 아무 코드나 new Listing()으로 속이 텅 빈 엔티티를 만들 수 있게 된다. 의미 있는 생성자를 쓰도록 유도하고 싶은데 그 규칙이 무너진다.
  • private이면 안 되는 이유 — Hibernate는 지연 로딩을 위해 Listing을 상속한 프록시 클래스를 내부적으로 만든다. 이 프록시는 Listing과 다른 패키지에 있을 수 있는데, private은 자식 클래스에도 안 보이므로 프록시가 부모 생성자를 호출할 방법이 없어진다.
  • protected가 맞는 이유 — "같은 패키지 + 패키지가 달라도 상속 관계"라는 범위가 정확히 여기 들어맞는다. 아무 데서나는 못 만들지만, 상속으로 이어진 Hibernate 프록시는 쓸 수 있다.

java-14의 패키지, java-13의 생성자, 오늘의 접근 제어자 — 세 레슨이 여기서 한 줄로 합쳐진다.

한 줄로 남기면

접근 제어자는 캡슐화를 약속에서 강제로 바꾼다. private으로 막고 필요한 문만 메서드로 열어두는 것이 오늘 배운 전부지만, 그 문을 여는 방식(검증이 있는 메서드냐, 그냥 대입만 하는 setter냐)이 캡슐화의 질을 가른다. 그리고 protected처럼 "아무나는 안 되지만 특정 관계는 된다"는 중간 지점을 만드는 능력이, 뿌에서 JPA가 요구하는 정확한 그 타협을 가능하게 한다.
