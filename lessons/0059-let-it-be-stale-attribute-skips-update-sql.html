값이 같으면 update!는 SQL조차 안 나간다

레슨 059 Dirty Tracking · let_it_be · partial_writes ~11분
🎯 자동 마감 동시성 보호 스펙을 쓰다가, 혼자 돌리면 통과하고 특정 랜덤 시드로 돌리면 실패하는 테스트를 만나 원인을 추적한 과정 — MISSION.md

상황 — 혼자 돌리면 통과, 시드를 주면 실패

자동 마감 워커의 스펙을 새로 썼다. 워크스페이스 설정을 켠 뒤 목표를 마감시키는 평범한 테스트였다. 

before {
  mock_es_search
  workspace.objective_setting.update!(completion_trigger_rate_enabled: true)
}

let_it_be(:workspace) { create(:workspace, ...) }

it '진행률이 100%면 목표를 마감한다' do
  create(:key_result, objective: objective, kind: :progress, target: 100, value: 100)
  objective.update_progress

  described_class.new.perform(objective.id, current_user.id)

  expect(objective.reload.stage).to eq('closed')  # 'open'이 나옴
end

파일 하나만 돌리면 통과했다. 그런데 --seed 7940으로 돌리면 같은 테스트가 실패했다. 테스트 코드는 한 글자도 안 바뀌었는데, 실행 순서만 바뀌었을 뿐인데.

가짜 단서를 먼저 쫓았다

처음엔 progress가 계산 컬럼이라 key_result를 만드는 것만으로 자동 갱신되지 않는다는 걸 의심했다. 맞는 의심이었고 실제로 objective.update_progress를 명시적으로 불러 고쳤다. 하지만 시드 7940은 여전히 실패했다.

다음 의심은 진짜 원인이 있는 곳 근처였지만 방향이 틀렸다 — "progress가 또 stale한가?"가 아니라 "이 테스트가 보는 워크스페이스 설정 자체가 stale한가?"를 물었어야 했다. 말로 계속 추론해도 수렴이 안 돼서, 워커 코드에 임시로 puts를 박아 실제 값을 봤다. 

[DEBUG] closed?=false progress=100 stage=open
[DEBUG] calling service, obj_setting.completion_trigger_rate_enabled=false

completion_trigger_rate_enabled가 false였다. 분명 before 훅에서 매 예제마다 true로 켜고 있는데.

같은 파일 안에서 순서를 바꿔 재현했다

디버그 스펙을 따로 만들어 두 예제를 이 순서로만 돌렸다. 

it 'A: 이미 마감된 목표면' do
  # ... objective_setting 관련 로직 없음, 그냥 다른 목표를 다룸
end

it 'B: 진행률이 100%면 목표를 마감한다 (debug)' do
  # 위와 같은 before 훅 + 위와 같은 검증
end

A 다음에 B를 돌리면 B가 실패했다. B를 단독으로 돌리면 통과했다. A는 completion_trigger_rate_enabled를 건드리는 코드가 전혀 없는데도, A가 먼저 실행됐다는 사실 자체가 B의 실패를 결정했다.

원인 — let_it_be는 예제 사이에도 같은 Ruby 객체를 들고 있다

workspace는 let이 아니라 let_it_be다. let은 예제마다 새로 만들지만, let_it_be는 예제 그룹 전체에서 딱 한 번만 레코드를 만들고 같은 Ruby 인스턴스를 계속 재사용한다 — 매 예제 생성 비용을 줄이려는 최적화다. 각 예제는 여전히 자기 트랜잭션(세이브포인트) 안에서 돌고 끝나면 롤백되지만, 그건 DB 쪽 값만 되돌릴 뿐 인메모리 Ruby 객체의 속성값은 그대로 남는다.

예제 A 시작
completion_trigger...=false(기본값)
→
B의 before 훅이
이미 실행된 적 있음
(인메모리 =true)
→
예제 종료 → 롤백
DB만 false로 복원
→
예제 B 시작
같은 객체, 인메모리는
여전히 =true

이제 B의 before 훅이 실행된다. 

workspace.objective_setting.update!(completion_trigger_rate_enabled: true)

update!는 내부적으로 assign_attributes 후 save!를 부른다. assign_attributes는 completion_trigger_rate_enabled = true를 대입하려 하는데 — 이미 그 속성의 현재 값이 true다. 같은 값을 대입하면 Dirty Tracking은 "변경된 게 없다"고 판단한다. Rails는 기본적으로 partial_writes가 켜져 있어서, 변경된 컬럼만 UPDATE 문의 SET 절에 넣는다. 변경분이 없으니 이 컬럼은 아예 SQL에 실리지 않는다.

결과적으로 update!는 예외 없이 "성공"하지만, 실제 DB 행은 한 글자도 안 바뀐다. 롤백으로 이미 false가 된 그 행은 계속 false로 남아 있고, 워커가 새로 Objective.find_by로 워크스페이스를 다시 읽으면 (인메모리 캐시가 아니라 진짜 쿼리이므로) 정직하게 false를 돌려준다.

레슨 48에서 이미 "let_it_be는 예제 사이에 같은 Ruby 객체를 공유하고, 트랜잭션 롤백은 DB만 되돌린다"를 배웠었다. 그때 정리한 판단 기준은 "어떤 예제도 속성을 저장 없이 직접 바꾸지 않으면 안전하다"였다. 이번 코드는 그 기준을 지켰다 — obj.attr = value가 아니라 매번 정식으로 update!를 불렀다. 그런데도 걸렸다. 레슨 48의 판단 기준은 "저장 없는 변경"만 봤지, "저장은 하는데 그 값이 이미 인메모리와 같아서 실제로는 아무것도 안 바뀌는 경우"는 다루지 않았다. 같은 뿌리(공유된 인메모리 객체 + DB만 되돌리는 롤백)에서 나온, 한 단계 더 미묘한 변종이다.

이미 같은 파일 옆에 답이 있었다

이 버그를 고치려고 검색하다가, 바로 옆 스펙 파일(reflect_worker_spec.rb)의 before 훅이 이미 다르게 짜여 있는 걸 발견했다. 

before {
  mock_es_search
  workspace.reload.objective_setting.update!(use_key_result_auto_checkin_reflect: true)
}

workspace.reload가 먼저 있었다. 처음엔 왜 있는지 몰랐던 한 줄이, 사실은 정확히 이 문제를 막고 있었던 것이다.

레슨 58과 같은 모양이다 — "이미 겪은 사람이 옆 코드에 조용히 방어를 심어뒀는데, 그 이유를 모른 채 지나쳤다." 다른 점은 그때는 생성 분기에 있던 방어를 수정 분기가 놓친 것이었고, 이번엔 다른 스펙 파일에 있던 방어를 내 새 스펙 파일이 놓친 것이다.

고친다면 이렇게 — reload로 "진짜 현재 값"부터 확보한다

before {
  mock_es_search
  workspace.reload.objective_setting.update!(completion_trigger_rate_enabled: true)
}

reload는 그 레코드를 DB에서 다시 읽어와 인메모리 속성을 실제 현재 값 (이 경우 롤백된 false)으로 되돌린다. 그 다음에야 true를 대입하면 진짜 변경이 되고, Dirty Tracking이 이를 잡아 SQL에 싣는다.

같은 패턴이 프로덕션 코드에도 그대로 적용된다 — AutoCloseObjectiveIfProgressCompleteService를 objective.with_lock으로 감싸 처리 직전 closed?를 재확인하도록 고친 것도 결국 "지금 들고 있는 객체를 믿지 말고 잠금을 통해 DB의 진짜 현재 값을 다시 보라"는 같은 원칙이다. 테스트에서 만난 원인과 그날 고친 동시성 버그가 뿌리에서 같은 개념이었다.

퀴즈 1 — 왜 이 버그는 특정 실행 순서에서만 나타나는가

let_it_be(:workspace)를 쓰는 파일에서, 왜 이 update! 버그는 "먼저 실행되는 예제가 있을 때만" 나타나는가?

퀴즈 2 — reload 없이 같은 값을 다시 대입하면

이미 인메모리로 true인 속성에 update!(같은_컬럼: true)를 다시 호출하면 무슨 일이 일어나는가?

한 줄로 남기면

Rails의 update!는 "지금 대입하려는 값이 실제로 바뀌는가"만 SQL로 내보낸다. let_it_be처럼 예제 사이에 Ruby 객체를 재사용하는 상황에서는, 트랜잭션 롤백이 되돌리는 건 DB뿐이라 인메모리 값과 실제 DB 값이 어긋날 수 있다. 그 상태에서 "이미 인메모리로 맞는 값"을 다시 대입하면 아무 SQL도 안 나가고 DB는 낡은 채로 남는다. 공유되는 레코드를 다루기 전엔 reload로 진짜 현재 값부터 확보해야 한다.
