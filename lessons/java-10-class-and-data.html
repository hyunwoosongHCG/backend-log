클래스와 데이터

자바 · 실전 자바 기본편 섹션 2 ~15분
🎯 뿌의 엔티티를 짜기 전에, 자바에서 "클래스를 만든다"가 무슨 뜻인지부터 정확히 본다. TypeScript의 type과 비슷해 보이는데 결정적으로 다른 지점이 있다.
강의를 수강하지 않고 작성한 레슨이다. 김영한 「실전 자바 - 기본편」 섹션 2의 전개와 예제는 수강생 정리 글 3편을 교차 확인해 따라갔고(하단 출처), Ruby·TypeScript 대비와 뿌 연결은 직접 쓴 것이다.

핵심 한 줄

자바에서 클래스(class)를 정의하는 것은 변수 여러 개를 묶는 문법이 아니라 새로운 타입(type)을 하나 만드는 일이다. int, String을 쓰던 자리에 내가 지은 이름을 쓸 수 있게 되고, 그 타입으로 만든 실체는 참조값을 통해 다루게 된다.

왜 필요한가 — 변수도 배열도 안 되는 지점

학생 두 명의 정보(이름·나이·성적)를 출력하는 프로그램을 짠다고 하자. 변수로만 관리하면 학생이 하나 늘 때마다 변수가 세 개씩 늘어난다. 

String student1Name = "학생1";
int student1Age = 15;
int student1Grade = 90;

String student2Name = "학생2";
int student2Age = 16;
int student2Grade = 80;

"배열로 묶으면 되지 않나?" 싶지만, 배열은 같은 종류의 데이터만 담는다. 이름은 String, 나이·성적은 int라 한 배열에 못 들어간다. 그래서 이렇게 쪼개게 된다. 

String[] studentNames  = {"학생1", "학생2"};
int[]    studentAges   = {15, 16};
int[]    studentGrades = {90, 80};

여기서 진짜 문제가 나온다. 한 학생의 데이터가 배열 세 개에 흩어져 있고, 그 셋을 묶어주는 건 오직 인덱스 번호뿐이다. 중간에 한 배열만 정렬하거나 한 명을 지우면 이름과 성적이 어긋나는데, 컴파일러는 아무 말도 하지 않는다.

필요한 것은 서로 다른 종류의 데이터를 "학생"이라는 하나의 개념으로 묶는 방법이고, 그게 클래스다.

클래스 도입

public class Student {
    String name;    // 멤버 변수(member variable) = 필드(field)
    int age;
    int grade;
}

클래스 안에 선언한 변수를 멤버 변수 또는 필드라고 부른다. 둘은 같은 말이다. "특정 클래스에 소속된 멤버"라서 멤버 변수, 데이터 항목을 가리키는 전통적인 용어(DB·엑셀에서 쓰는 그 필드)라서 필드다.

관례상 클래스 이름은 대문자로 시작하는 카멜 케이스다 (Student, MemberService). 변수는 소문자로 시작한다. 강제는 아니지만 자바 생태계 전체가 지키는 규칙이라, 안 지키면 코드 리뷰에서 먼저 지적당한다.

클래스를 만든다 = 타입을 만든다

Student student1 = new Student();
//  ↑ 타입       ↑ 변수    ↑ 인스턴스 생성
student1.name = "학생1";      // . 으로 필드에 접근
student1.age = 15;
student1.grade = 90;

주목할 곳은 Student student1의 왼쪽이다. int, String을 쓰던 자리에 내가 만든 이름이 들어갔다. 클래스를 정의한 순간 Student는 사용자 정의 타입(user-defined type)이 된 것이다.

TypeScript에서 type Student = { name: string; age: number }로 타입을 만드는 것과 모양은 비슷하다. 하지만 TS는 구조가 같으면 호환된다(구조적 타이핑). 자바는 이름이 다르면 필드가 똑같아도 다른 타입이다(명목적 타이핑, nominal typing). TS에서 Student와 Member의 필드가 같으면 서로 대입되지만, 자바에서는 컴파일 에러다. 이 차이가 나중에 스프링이 "무엇을 주입할지"를 타입 이름으로 찾는 방식의 근거가 된다.

객체는 참조값으로 다룬다

new Student()가 실제로 하는 일은 두 가지다. ① 메모리에 객체를 만들고 ② 그 객체에 접근할 수 있는 참조값(주소)을 돌려준다. 변수에 담기는 건 객체 자체가 아니라 그 참조값이다.

1. Student student1;
Student 타입의 참조값을 담을 수 있는 변수를 선언한다. 아직 가리키는 곳이 없다(null).
↓
2. new Student()
메모리 어딘가에 필드 세 칸을 가진 객체가 만들어지고, 그 위치(예: x001)가 반환된다.
↓
3. student1 = x001
변수에 참조값이 저장된다. 이제 student1.name은 "x001에 가서 name 칸을 꺼내라"는 뜻이다.

그래서 객체를 그냥 출력하면 값이 아니라 주소처럼 생긴 것이 찍힌다. 

System.out.println(student1);
// study_class1.Student@66a29884
//     ↑ 패키지.클래스명    ↑ 참조값(해시)을 16진수로
JS에서 const a = { x: 1 }; const b = a; 하면 b를 바꿀 때 a도 바뀌는, 그 "객체는 참조로 전달된다"와 같은 이야기다. 이미 아는 감각이라 새로울 게 없다. 다른 점은 자바가 이 둘을 타입 차원에서 갈라놓았다는 것이다 — int 같은 기본형은 값을 직접 담고, 클래스 타입은 참조값을 담는다. JS처럼 "원시값은 값, 객체는 참조"가 런타임 성질인 게 아니라 선언한 타입이 결정한다. 다음 레슨(java-11)이 통째로 이 이야기다.

클래스 · 객체 · 인스턴스

세 단어가 섞여 쓰이는데, 강의에서 정리하는 기준은 이렇다.

  • 클래스(class) — 설계도. 어떤 속성과 기능을 가질지의 정의.
  • 객체(object) — 설계도대로 메모리에 만들어진 실체. student1과 student2는 같은 클래스에서 나왔지만 서로 독립된 상태를 가진다.
  • 인스턴스(instance) — 같은 것을 가리키되 "어느 클래스로부터"인지 관계를 강조할 때 쓴다. "student1은 Student의 인스턴스다."

실무에서 객체와 인스턴스는 거의 구분 없이 쓰인다. 다만 "인스턴스"라고 말할 때는 어느 클래스의가 따라붙는다고 기억하면 된다.

그리고 다시 배열로

클래스로 묶고 나면 아까 실패했던 배열이 이번에는 된다. 타입이 하나가 됐기 때문이다. 흩어진 배열 세 개가 배열 하나가 된다. 

Student[] students = {student1, student2};

for (Student s : students) {                       // 향상된 for문(for-each)
    System.out.println("이름:" + s.name + " 나이:" + s.age + " 성적:" + s.grade);
}

이게 섹션 2의 결론이다. 클래스는 데이터를 묶는 도구이고, 묶고 나면 그 묶음을 다시 하나의 값처럼 다룰 수 있다 — 배열에 담고, 반복하고, 메서드에 넘기고, 반환한다. 인덱스를 맞춰가며 관리하던 일이 사라진다.

Ruby · TypeScript와 갈리는 세 지점

1. 이름이 타입을 가른다

class Student { String name; int age; }
class Member  { String name; int age; }   // 필드 구성이 완전히 같다

Student s = new Member();   // ❌ 컴파일 에러

Ruby는 덕 타이핑(duck typing)이라 name에 응답하면 그냥 쓴다. TS는 구조가 같으면 호환된다. 자바만 이름으로 가른다. 그래서 자바에서는 타입 이름을 짓는 일이 곧 설계다.

2. 필드는 자동 초기화되고, 지역 변수는 아니다

클래스의 필드는 값을 넣지 않아도 타입별 기본값으로 자동 초기화된다. 반면 메서드 안의 지역 변수(local variable)는 초기화하지 않고 쓰면 컴파일 에러다.

타입 필드 기본값 주의
int, long 0 "값 없음"과 0이 구분되지 않는다
double 0.0 위와 같음
boolean false "안 정했음"이 false로 보인다
String, Integer 등 참조형 null 값 없음을 표현할 수 있다

Ruby는 초기화 안 한 인스턴스 변수가 전부 nil, JS는 전부 undefined로 하나인데, 자바는 타입마다 기본값이 다르고 그중 일부는 "값 없음"을 표현하지 못한다.

3. 파일 이름과 클래스 이름이 묶여 있다

public 클래스는 파일 이름과 클래스 이름이 같아야 한다. Student.java 안에 public class Student. Ruby도 JS도 강제하지 않는 규칙이라, 자바 프로젝트의 디렉터리 구조가 곧 타입 목록이 된다는 점이 처음에는 낯설다.

뿌에서는 이렇게 보인다

지금 배운 것이 앞으로 뿌에서 만들 엔티티의 뼈대 그대로다. 어노테이션을 걷어내면 남는 건 클래스 = 타입, 필드 = 데이터뿐이다. 

@Entity
public class Listing {              // ← 클래스 하나 = 타입 하나 = 테이블 하나
    @Id
    private Long id;                // 참조형 → 기본값 null (저장 전이면 id 없음)

    private String address;         // 참조형 → null 가능
    private int price;              // ⚠️ 기본형 → 기본값 0
}

마지막 줄이 함정이다. 매물에 가격이 아직 없는 경우를 int price로 두면 "가격 미상"과 "0원"이 같은 값이 된다. 값 없음을 표현해야 한다면 Integer여야 한다. Rails에서 price 컬럼이 nil인 것과 0인 것이 다른 것과 같은 이야기인데, 자바에서는 타입 선택으로 결정된다는 점이 다르다.

퀴즈 1 — 필드 구성이 완전히 같은 Student와 Member가 있다. Student s = new Member(); 는 되는가?

퀴즈 2 — System.out.println(student1)을 찍었더니 Student@66a29884가 나왔다. 왜인가?

퀴즈 3 — 가격이 "아직 없음"일 수 있는 매물을 int price로 선언하면 무슨 일이 생기나?

한 줄로 남기면

클래스를 만드는 것은 타입을 만드는 것이고, 그 타입의 실체는 참조값으로 다룬다. 흩어진 데이터를 하나의 이름으로 묶는 순간 배열에 담고 반복하고 넘길 수 있게 되는데, 이때 오가는 것은 객체가 아니라 객체를 가리키는 값이다. 그리고 자바는 "이 데이터 뭉치가 무엇인가"를 반드시 이름으로 선언하게 만들기 때문에, 스프링이 ListingRepository를 넣어야 할 자리에 정확히 그것을 찾아 넣을 수 있다.
