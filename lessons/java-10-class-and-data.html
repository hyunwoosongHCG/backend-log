클래스와 데이터

자바 · 실전 자바 기본편 섹션 2 ~12분
🎯 뿌의 엔티티를 짜기 전에, 자바에서 "클래스를 만든다"가 무슨 뜻인지부터 정확히 본다. TypeScript의 type과 비슷해 보이는데 결정적으로 다른 지점이 있다.
주제 선정은 김영한 「실전 자바 - 기본편」의 섹션 제목을 커버리지 기준으로 빌렸다. 강의를 수강하지 않고 직접 작성한 레슨이라, 설명 방식과 예제는 강의와 다르다.

핵심 한 줄

자바에서 클래스(class)를 정의하는 것은 변수 여러 개를 묶는 문법이 아니라 새로운 타입(type)을 하나 만드는 일이다. 컴파일러가 아는 타입 목록에 내가 지은 이름이 추가되고, 그때부터 그 이름으로 변수를 선언하고, 메서드 인자로 받고, 반환할 수 있다.

왜 필요한가 — 변수도 배열도 안 되는 지점

학생 정보를 다룬다고 하자. 학생 한 명에게 이름·국어점수·영어점수가 있다. 변수로만 관리하면 이렇게 된다. 

String student1Name = "학생1";
int student1Korean = 90;
int student1English = 80;

String student2Name = "학생2";   // 학생이 하나 늘 때마다
int student2Korean = 80;         // 변수가 세 개씩 늘어난다
int student2English = 70;

"그럼 배열로 묶으면 되지 않나?" 싶지만 안 된다. 배열은 같은 종류의 데이터만 담는다. 이름은 String이고 점수는 int라 한 배열에 들어가지 않는다. 이름 배열, 국어 배열, 영어 배열로 쪼개면 "3번 학생"의 정보가 세 군데에 흩어져 인덱스가 어긋나는 순간 데이터가 섞인다.

필요한 것은 서로 다른 종류의 데이터를 하나의 단위로 묶는 방법이고, 그게 클래스다. 

public class Student {
    String name;      // 필드(field) — 이 타입이 가지는 데이터
    int korean;
    int english;
}
Student student1 = new Student();
//  ↑ 타입      ↑ 변수      ↑ 객체 생성
student1.name = "학생1";
student1.korean = 90;

주목할 곳은 Student student1의 왼쪽이다. int, String을 쓰던 자리에 내가 만든 이름이 들어갔다. 클래스를 정의한 순간 Student는 int와 같은 급의 타입이 된 것이다.

TypeScript에서 type Student = { name: string; korean: number }로 타입을 만들고 객체를 담는 것과 모양이 비슷하다. 하지만 TS는 구조가 같으면 호환된다(구조적 타이핑). 자바는 이름이 다르면 필드가 똑같아도 다른 타입이다(명목적 타이핑, nominal typing). TS에서 Student와 Member의 필드가 같으면 서로 대입되지만, 자바에서는 컴파일 에러다. 이 차이가 나중에 스프링이 "무엇을 주입할지"를 타입 이름으로 찾는 방식의 근거가 된다.

클래스 · 객체 · 인스턴스

세 단어가 섞여 쓰이는데, 가리키는 대상이 다르다.

클래스(class) — 설계도. Student라는 타입이 어떤 데이터를 갖는지의 정의. 코드에 한 번만 쓴다.
↓ new
객체(object) — 설계도대로 메모리에 실제로 만들어진 것. new Student()를 두 번 부르면 객체가 둘 생긴다.
↓
인스턴스(instance) — 같은 것을 가리키되 "무엇의" 객체인지 관계를 강조할 때 쓴다. "student1은 Student의 인스턴스다."

실무에서 객체와 인스턴스는 거의 구분 없이 쓰인다. 다만 "인스턴스"라고 말할 때는 어느 클래스의가 따라붙는다고 기억하면 된다.

Ruby · TypeScript와 갈리는 세 지점

1. 이름이 타입을 가른다

class Student { String name; int korean; }
class Member  { String name; int korean; }   // 필드 구성이 완전히 같다

Student s = new Member();   // ❌ 컴파일 에러

Ruby는 덕 타이핑(duck typing)이라 name에 응답하면 그냥 쓴다. TS는 구조가 같으면 호환된다. 자바만 이름으로 가른다. 그래서 자바에서는 타입 이름을 짓는 일이 곧 설계다.

2. 필드는 자동 초기화되고, 지역 변수는 아니다

클래스의 필드는 값을 넣지 않아도 타입별 기본값으로 자동 초기화된다. 반면 메서드 안의 지역 변수(local variable)는 초기화하지 않고 쓰면 컴파일 에러다.

타입 필드 기본값 주의
int, long 0 "값 없음"과 0이 구분되지 않는다
double 0.0 위와 같음
boolean false "안 정했음"이 false로 보인다
String, Integer 등 참조형 null 값 없음을 표현할 수 있다

Ruby는 초기화 안 한 인스턴스 변수가 전부 nil, JS는 전부 undefined로 하나인데, 자바는 타입마다 기본값이 다르고 그중 일부는 "값 없음"을 표현하지 못한다. 이게 다음 레슨(java-11 기본형과 참조형)의 출발점이다.

3. 파일 이름과 클래스 이름이 묶여 있다

public 클래스는 파일 이름과 클래스 이름이 같아야 한다. Student.java 안에 public class Student. Ruby도 JS도 강제하지 않는 규칙이라, 자바 프로젝트의 디렉터리 구조가 곧 타입 목록이 된다는 점이 처음에는 낯설다.

뿌에서는 이렇게 보인다

지금 배운 것이 앞으로 뿌에서 만들 엔티티의 뼈대 그대로다. 어노테이션을 걷어내면 남는 건 클래스 = 타입, 필드 = 데이터뿐이다. 

@Entity
public class Listing {              // ← 클래스 하나 = 타입 하나 = 테이블 하나
    @Id
    private Long id;                // 참조형 → 기본값 null (아직 저장 전이면 id 없음)

    private String address;         // 참조형 → null 가능
    private int price;              // ⚠️ 기본형 → 기본값 0
}

마지막 줄이 함정이다. 매물에 가격이 아직 없는 경우를 int price로 두면 "가격 미상"과 "0원"이 같은 값이 된다. 값 없음을 표현해야 한다면 Integer여야 한다. Rails에서 price 컬럼이 nil인 것과 0인 것이 다른 것과 같은 이야기인데, 자바에서는 타입 선택으로 결정된다는 점이 다르다.

퀴즈 1 — 필드 구성이 완전히 같은 Student와 Member가 있다. Student s = new Member(); 는 되는가?

퀴즈 2 — 가격이 "아직 없음"일 수 있는 매물을 int price로 선언하면 무슨 일이 생기나?

한 줄로 남기면

클래스를 만드는 것은 타입을 만드는 것이다. 자바에서는 "이 데이터 뭉치가 무엇인가"를 반드시 이름으로 선언해야 하고, 그 이름이 다르면 내용이 같아도 다른 것으로 취급된다. 번거로워 보이지만, 스프링이 ListingRepository를 주입해야 할 곳에 정확히 그것을 찾아 넣어주는 근거가 바로 이 타입 이름이다.
