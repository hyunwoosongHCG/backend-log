동시성 문제란 무엇인가

두 명의 유저(또는 같은 유저의 중복 클릭)가 같은 순간에 같은 데이터를 수정하려고 하면, 어느 한쪽의 변경이 사라지거나 데이터가 뒤섞일 수 있다. 예를 들어 재고 1개 남은 상품에 두 요청이 동시에 "재고 -1"을 하면, 둘 다 "재고 1"을 읽고 각자 "재고 0"으로 저장해서 실제로는 2개가 팔렸는데 재고는 0으로만 남는 식이다.

React의 setState를 이전 상태 기반으로 갱신할 때 setCount(count + 1) 대신 setCount(prev => prev + 1)을 써야 한다고 배운 적이 있을 것이다. 이유는 여러 업데이트가 배치(batch)로 몰릴 때 count라는 "오래된 값"을 기준으로 계산하면 일부 업데이트가 유실되기 때문이다. DB의 동시성 문제도 본질은 같다 — 여러 트랜잭션이 "오래된 값"을 동시에 읽고 각자 계산해서 저장하면 하나의 변경이 덮어써진다. 다만 DB는 여러 서버 프로세스, 여러 유저에 걸쳐 이 문제가 생기기 때문에 언어 차원의 해결책(클로저로 최신값 캡처)이 아니라 DB 차원의 잠금 장치가 필요하다.

비관적 락(Pessimistic Locking) — SELECT ... FOR UPDATE

이 문제를 막는 한 가지 방법이 비관적 락(Pessimistic Locking)이다. "충돌이 날 것이라고 비관적으로 가정하고, 아예 미리 잠가버리는" 전략이다. MySQL에서는 이렇게 표현한다: 

SELECT * FROM objective_revisions WHERE id = 42 FOR UPDATE;
-- 이 트랜잭션이 커밋/롤백될 때까지, 다른 트랜잭션은 이 행을
-- 다시 SELECT ... FOR UPDATE로 읽거나 수정하려 할 때 대기(block)한다

Rails는 이걸 with_lock 메서드로 감싸서 제공한다. 레슨 24의 transaction do와 SELECT ... FOR UPDATE를 한 번에 해주는 헬퍼다. 

# app/services/objective_approve_update.rb:22
pending_revision.with_lock do
  # 이 블록에 들어오는 순간:
  # 1. SELECT * FROM objective_revisions WHERE id = ? FOR UPDATE 실행됨
  # 2. 트랜잭션이 열림 (이미 열려있으면 합류)
  # 3. 블록이 끝나면 커밋, 예외 나면 롤백
  revision = pending_revision.data.deep_symbolize_keys
  # ...
end

이렇게 하면 같은 pending_revision 행을 동시에 승인하려는 두 번째 요청은, 첫 번째 트랜잭션이 끝날 때까지 대기한다 — 즉 "같은 revision을 동시에 두 번 승인 처리하는" 문제는 이미 막혀 있었다.

퀴즈 1 — with_lock의 역할

record.with_lock do ... end이 실제로 하는 일은?

그런데 왜 데드락이 났나 — 락은 "그 행 하나"에만 걸린다

with_lock이 잠그는 건 딱 그 한 행(pending_revision)뿐이다. 같은 트랜잭션 안에서 추가로 실행하는 다른 테이블의 UPDATE는 각자 별도로 락을 잡는다 — with_lock이 "이 트랜잭션 안의 모든 것"을 대신 안전하게 만들어주는 마법은 아니다. 

pending_revision.with_lock do        # ① objective_revisions 행 1개 잠금
  # ...
  KeyResult.where(super_key_result_id: X).update_all(...)   # ② key_results 테이블 일부 잠금
  Objective.where(super_key_result_id: X).update_all(...)   # ③ objectives 테이블 일부 잠금
end

문제는 ②, ③이 PK(기본키) 단건 조회가 아니라 super_key_result_id라는 일반 컬럼으로 여러 행을 한 번에 찾아 잠근다는 점이다(레슨 43에서 다룰 인덱스 문제 때문에 실제로는 더 넓은 범위가 잠긴다). 두 개의 서로 다른 update_approval 요청(트랜잭션 A, B)이 겹치는 key_result 트리를 손보다가, 서로 다른 순서로 행을 잠그면:

시점 트랜잭션 A 트랜잭션 B
t1 key_result 그룹 X 잠금 성공 key_result 그룹 Y 잠금 성공
t2 그룹 Y 잠금 시도 → 대기(B가 쥐고 있음) 그룹 X 잠금 시도 → 대기(A가 쥐고 있음)
t3 서로가 서로를 기다리는 순환 대기(circular wait) — 영원히 안 풀림

데드락(Deadlock)이란 — 그리고 MySQL이 하는 일

데드락은 두 개 이상의 트랜잭션이 서로가 가진 락을 기다리며 영원히 멈춰있는 상태다. MySQL(InnoDB)은 이걸 스스로 감지할 수 있다 — 락 대기 그래프를 추적하다가 순환이 생기면, 둘 중 하나(보통 되돌리기 비용이 더 적은 쪽)를 강제로 롤백시키고 그 트랜잭션에 에러를 던진다. 그게 바로 우리가 본 ActiveRecord::Deadlocked다.

즉 데드락은 버그로 인해 "영원히 멈추는" 사고가 아니라, DB가 스스로를 지키기 위해 한쪽을 희생시키는 정상적인 방어 기제다. 다만 애플리케이션 입장에서는 그 요청이 500 에러로 실패한다 — 그래서 이런 코드 경로에는 보통 재시도(retry) 로직을 둔다.

JS로 치면 두 개의 Promise가 서로 await하며 영원히 안 끝나는 상황과 비슷하다. 다만 브라우저/Node엔 이런 순환을 자동으로 감지해서 강제로 하나를 reject시켜주는 장치가 없다 — 그냥 영원히 멈춘다(deadlock인데 아무도 안 잡아줌). MySQL은 여기에 "감시자"를 하나 더 두고 있다고 생각하면 된다.

퀴즈 3 — with_lock의 한계

record.with_lock do ... update_all(...) ... end에서, with_lock은 블록 안의 update_all이 잠그는 행까지 안전하게 만들어주는가?

핵심 요약

항목 설명
비관적 락 충돌을 미리 가정하고 SELECT ... FOR UPDATE로 행을 잠가버리는 전략
with_lock 그 레코드 한 행에 대한 SELECT ... FOR UPDATE + 트랜잭션을 함께 걸어주는 헬퍼
데드락 두 트랜잭션이 서로의 락을 기다리는 순환 대기. MySQL이 감지해서 한쪽을 강제 롤백
이번 버그의 교훈 with_lock은 그 레코드만 지킨다 — 블록 안 다른 테이블의 update_all이 얼마나 넓게 잠그는지는 별개로 확인해야 한다 (→ 레슨 43 인덱스)
