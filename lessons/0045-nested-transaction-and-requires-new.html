중첩 트랜잭션 — transaction do end을 두 번 쓰면 뭐가 달라지는가

레슨 045 Nested Transaction · SAVEPOINT · requires_new ~12분
🎯 핵심성과 자동 반영 기능에 "반영으로 완료된 상위 목표도 자동 마감"을 추가하면서, "트랜잭션이 너무 길어지지 않을까"라는 질문에 답하려다 발견한 것. 레슨 24(트랜잭션 원자성)·42(행 잠금)와 이어지는 심화 — MISSION.md

겉보기엔 똑같은 코드인데

아래 두 코드는 똑같이 생겼다. 하나는 이미 트랜잭션이 열려있는 상태에서 호출되고, 하나는 아무것도 없는 상태에서 호출된다. 

ActiveRecord::Base.transaction do
  reflect_values_up_the_chain     # 이미 바깥에서 transaction do가 열려있는 상태
end

ActiveRecord::Base.transaction do
  reflect_values_up_the_chain     # 아무것도 없는 상태 (이 호출이 최상위)
end

직관적으로는 "transaction do end이라고 썼으니 여기서 새 트랜잭션이 시작되겠지"라고 생각하기 쉽다. 하지만 첫 번째 코드는 새 트랜잭션을 시작하지 않는다 — 이미 열려있는 바깥 트랜잭션에 그냥 합류(join)할 뿐이다. 실제로 BEGIN도, COMMIT도 일어나지 않는다.

회의실을 하나 빌리는 상황으로 생각해보자. "회의실 예약해줘"라고 했을 때, 이미 내가 그 회의실에 들어가 있는 상태라면 새로 예약이 잡히는 게 아니라 그냥 "이미 내가 쓰고 있는 회의실"로 처리된다. 회의가 끝나는 시점(COMMIT)은 내가 처음 들어갔을 때 잡은 예약이 끝나는 시점이지, 두 번째로 "예약해줘"라고 말한 시점이 아니다.

직접 재현해보기

이걸 직접 눈으로 확인하는 가장 쉬운 방법은, 중첩된 블록 안에서 예외를 던져보는 것이다.

ActiveRecord::Base.transaction do
  puts "1. transaction 진입"
  raise "실패!"
  puts "2. 이 줄은 절대 실행 안됨"
end
puts "3. 여기 도달하면 안됨"

실제로 rails runner로 실행해보면 "3. 여기 도달하면 안됨"도 출력되지 않는다. transaction do end 블록 안에서 예외가 발생하면, Rails가 내부적으로 ROLLBACK을 실행한 뒤 그 예외를 그대로 다시 던진다(re-raise). 그리고 Ruby의 순차 실행 규칙상, 예외가 던져진 지점 이후의 코드는 같은 메서드 안이든 밖이든 실행되지 않는다. 즉 "트랜잭션 블록이 끝난 뒤에 실행되는 코드"는 별도의 rescue나 플래그 체크 없이도, 반영 자체가 실패하면 자동으로 스킵된다.

퀴즈 1 — 중첩 트랜잭션의 정체

이미 transaction do end이 열려있는 상태에서, 그 안에서 다시 ActiveRecord::Base.transaction do end을 호출했다. 이 안쪽 블록은 기본적으로 어떻게 동작하는가?

진짜 독립된 서브 트랜잭션이 필요하다면 — requires_new: true

"A라는 항목을 처리하다 실패해도, B라는 항목이나 바깥 트랜잭션 전체는 롤백시키고 싶지 않다"는 상황이 실무에서 자주 나온다 — 예를 들어 반영으로 진행률이 100%가 된 상위 목표들을 자동으로 마감하는데, 그중 하나가 실패해도 다른 목표나 원래 체크인 자체는 영향받지 않아야 하는 경우다. 이럴 땐 requires_new: true를 준다. 

ActiveRecord::Base.transaction do          # ① 바깥 트랜잭션
  reflect_values_up_the_chain
end

reflected_objectives.each do |objective|
  ActiveRecord::Base.transaction(requires_new: true) do   # ② 진짜 SAVEPOINT
    AutoCloseObjectiveIfProgressCompleteService.call(objective:)
  end
rescue StandardError => e
  Rails.logger.error("자동 마감 실패: #{e.message}")   # ②만 롤백, ①과 다른 objective는 안전
end

requires_new: true를 주면 MySQL(InnoDB)이 실제로 SAVEPOINT를 찍고, 안쪽에서 예외가 나면 ROLLBACK TO SAVEPOINT로 그 부분만 되돌릴 수 있다. 단, Rails가 자동으로 예외를 삼켜주지는 않는다 — SAVEPOINT까지만 롤백해줄 뿐, 예외 자체는 계속 위로 전파되므로 원하는 지점에서 직접 rescue로 잡아줘야 한다.

퀴즈 2 — SAVEPOINT가 안 해주는 것

바깥에 이미 큰 트랜잭션이 열려있는 상태에서, 안쪽 작업 10개를 각각 transaction(requires_new: true)로 감쌌다. 이렇게 하면 바깥 트랜잭션이 잡고 있는 row lock의 보유 시간도 줄어드는가?

실무에서 쓸 때 확인해야 할 것 — 이 서비스가 정말 최상위인가?

실제로 부딪힌 문제는 이거였다 — 어떤 서비스의 transaction do end이 "정말 이 호출의 최상위 트랜잭션"인지, 아니면 "이미 누군가 열어둔 트랜잭션에 합류하는 것"인지는 그 서비스 코드만 봐서는 알 수 없다. 실제 호출부를 하나하나 추적해야 한다.

예를 들어 체크인 반영 서비스는 6곳에서 호출되는데, 그중 4곳은 이미 자기만의 transaction do end으로 감싸고 있었고 2곳은 아니었다. 그 4곳에서는 "반영 트랜잭션과 자동 마감을 분리했다"고 해도 실제로는 이미 열려있던 트랜잭션에 계속 합류할 뿐이라, 원했던 "락 보유 시간 단축" 효과는 그 4곳에서는 얻지 못했다 — 다만 "부분 실패 격리"는 requires_new: true 덕분에 여전히 유효했다.

핵심 요약

항목 설명
기본 중첩 transaction do 이미 열린 트랜잭션이 있으면 새로 시작하지 않고 그냥 합류한다 (BEGIN/COMMIT 없음)
예외 전파 블록 안 예외는 ROLLBACK 후 다시 던져진다 → 블록 뒤 코드는 자동으로 실행 안 됨(Ruby 순차 실행)
requires_new: true 진짜 SAVEPOINT를 만들어 부분 실패 격리는 되지만, 락 조기 해제는 안 됨. 예외도 직접 rescue해야 함
실무 체크리스트 이 코드가 정말 최상위 트랜잭션인지는 코드만 봐선 모른다 — 모든 호출부를 추적해야 한다
