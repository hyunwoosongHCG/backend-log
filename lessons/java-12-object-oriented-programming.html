핵심 한 줄

객체 지향은 데이터와 그 데이터를 다루는 기능(메서드)을 하나의 객체 안에 묶는 것이다. 반대는 절차 지향 — 데이터는 그냥 값 상자이고, 그 값을 바꾸는 로직은 상자 바깥 여기저기에 흩어져 있는 방식이다. "무엇(what)을 하나로 묶을 것인가" 중심으로 생각하면 객체 지향, "어떻게(how) 순서대로 처리할 것인가" 중심으로 생각하면 절차 지향이다.

절차 지향의 문제 — 아무나 값을 바꿀 수 있다

public class ValueData {
    int value;
}

public class ValueDataMain {
    public static void main(String[] args) {
        ValueData valueData = new ValueData();
        valueData.value = 10;
        valueData.value++;             // 여기서도 바꿀 수 있고
        System.out.println(valueData.value);
    }
}

// 다른 메서드, 다른 파일에서도
valueData.value = -9999;               // 아무 제약 없이 이렇게도 된다

ValueData는 필드만 있는 빈 상자다. value를 바꾸는 코드가 ValueDataMain은 물론이고 이 클래스를 아는 코드라면 어디서든 실행될 수 있다. 지금은 필드가 하나뿐이라 별문제 없어 보이지만, 필드가 늘고 "이 값은 0 밑으로 못 내려간다" 같은 규칙이 생기는 순간 — 그 규칙을 지키는지 아무도 보장할 수 없다. 규칙을 아는 곳이 한 곳도 없기 때문이다.

객체가 스스로를 지킨다 — 캡슐화

public class ValueObject {
    int value;

    void add() {
        this.value++;
    }
}

public class ValueObjectMain {
    public static void main(String[] args) {
        ValueObject valueObject = new ValueObject();
        valueObject.add();
        valueObject.add();
        System.out.println(valueObject.value);   // 2
    }
}

바뀐 것은 딱 하나다. value를 바꾸는 로직(value++)이 클래스 밖에서 안으로 들어왔다. 이제 value를 1 늘리고 싶으면 valueObject.value++가 아니라 valueObject.add()를 부른다. 이렇게 속성(데이터)과 기능(메서드)을 하나로 묶어서, 값을 바꾸는 방법을 메서드로만 제공하는 것을 캡슐화(encapsulation)라고 부른다. 나중에 "0 밑으로 못 내려간다"는 규칙이 생기면 add() 안에 if 한 줄만 추가하면 된다 — 그 규칙을 지켜야 하는 곳이 이 메서드 하나뿐이기 때문이다.

this.value++의 this는 "이 메서드를 호출한 객체 자기 자신"을 가리키는 참조값이다. 지금은 메서드 안에 value라는 이름의 지역 변수나 매개변수가 없어서 그냥 value++라고만 써도 똑같이 동작한다 — this.는 생략 가능한 선택이다. this가 생략 불가능해지는 순간은 다음 레슨(java-13 생성자)에서 나온다: 매개변수 이름과 필드 이름이 똑같아지는 순간이다.

여러 상태를 가진 객체 — MusicPlayer

필드가 하나뿐이면 캡슐화의 이점이 잘 안 보인다. 필드 두 개(전원, 볼륨)를 여러 메서드가 함께 다루는 예제로 넘어가면 왜 이게 "묶여" 있어야 하는지가 분명해진다. 

public class MusicPlayer {
    int volume = 0;
    boolean isOn = false;

    void on() {
        isOn = true;
        System.out.println("음악 플레이어를 시작합니다");
    }

    void off() {
        isOn = false;
        System.out.println("음악 플레이어를 종료합니다");
    }

    void volumeUp() {
        volume++;
        System.out.println("음악 플레이어 볼륨:" + volume);
    }

    void volumeDown() {
        volume--;
        System.out.println("음악 플레이어 볼륨:" + volume);
    }

    void showStatus() {
        System.out.println("음악 플레이어 상태 확인");
        if (isOn) {
            System.out.println("음악 플레이어 ON, 볼륨:" + volume);
        } else {
            System.out.println("음악 플레이어 OFF");
        }
    }
}

public class MusicPlayerMain {
    public static void main(String[] args) {
        MusicPlayer player = new MusicPlayer();
        player.on();
        player.volumeUp();
        player.volumeUp();
        player.volumeDown();
        player.showStatus();   // 음악 플레이어 ON, 볼륨:1
        player.off();
    }
}

MusicPlayerMain은 volume이라는 필드가 있다는 사실조차 몰라도 된다. volumeUp(), showStatus() 같은 메서드 이름만 알면 된다. "전원이 꺼져 있으면 볼륨을 못 올리게 막자"는 규칙이 생겨도 volumeUp() 안에서만 고치면 되고, MusicPlayerMain은 한 글자도 안 바뀐다. 이것이 필드 하나짜리 ValueObject에서는 잘 안 보이던, 캡슐화가 진짜 값을 하는 지점이다.

React 컴포넌트에서 state를 직접 this.state.count = 5로 바꾸지 않고 setCount(5) 같은 함수를 통해서만 바꾸게 강제하는 것과 감각이 같다. 상태를 바꾸는 입구를 하나로 좁혀두면, 나중에 "0 밑으로는 못 내려간다" 같은 검증을 추가할 곳이 명확해진다. 자바가 다른 점은, useState처럼 라이브러리가 강제하는 게 아니라 필드를 private로 막아서 언어 차원에서 강제한다는 것이다 — 그 private는 다음다음 레슨(java-14 패키지, java-15 접근 제어자)에서 다룬다. 지금은 필드가 아직 열려 있어서, 캡슐화는 "강제"가 아니라 "메서드로만 바꾸자"는 약속 수준이다.

직접 타이핑해보기 — MusicPlayer에 mute()라는 메서드를 추가해보세요. 호출하면 volume을 0으로 만들고, "음소거했습니다"를 출력합니다.

뿌에서는 이렇게 보인다

@Entity
public class Listing {
    private Long id;
    private int price;

    void applyDiscount(int amount) {
        if (this.price - amount < 0) {
            throw new IllegalArgumentException("가격은 0 밑으로 내려갈 수 없습니다");
        }
        this.price -= amount;
    }
}

listing.price = listing.price - amount;를 호출하는 쪽마다 반복해서 쓰면, "0 밑으로 못 내려간다"는 검증을 어느 한 군데서 빠뜨려도 아무도 모른다. applyDiscount() 메서드 하나로 묶어두면 검증을 지킬 수 있는 문(門)이 하나뿐이라 빠뜨릴 곳이 없다. MusicPlayer의 volumeUp()과 정확히 같은 이야기다.

한 줄로 남기면

객체 지향은 데이터를 바꾸는 로직을 데이터와 함께 가둬두는 것이다. value++를 클래스 밖에 흩어두면 규칙을 지키는지 아무도 보장 못 하지만, add() 메서드 안에 가두면 규칙을 지킬 문(門)이 하나로 좁혀진다. 지금은 필드가 아직 public이라 이 캡슐화가 "약속"에 머물지만, 다음 레슨들에서 생성자로 초기화를 강제하고(java-13) 접근 제어자로 필드를 아예 잠그면서 (java-15) 이 약속이 진짜 강제로 바뀐다.
