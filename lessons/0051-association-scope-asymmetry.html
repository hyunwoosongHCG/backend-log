연관관계 스코프는 조인 대상의 부모를 보지 않는다

레슨 051 has_many 스코프 · 소프트 삭제 · joins 조건 · 계산과 표시의 분리 ~15분
🎯 이름이 대칭인 두 연관관계가 같은 정책을 표현한다고 믿었다가, 한쪽만 부모 상태를 검사한다는 걸 발견한 과정 — MISSION.md

상황 — 평균을 내려면 분모가 필요했다

핵심성과 자동 반영을 "하위 하나로 덮어쓰기"에서 "연계된 하위 전체의 평균"으로 바꾸는 작업이었다. 평균을 내려면 분모에 넣을 하위 목록이 필요하다. 정책은 이랬다 — 연계돼 있으면 체크인 이력이 없어도 포함, 마감된 것도 포함, 삭제된 것만 제외.

모델에 이미 쓸 만해 보이는 연관관계가 둘 있었다. 하위 목표를 가져오는 것과 하위 핵심성과를 가져오는 것. 이름도 대칭이라 그대로 쓰면 될 줄 알았다. 

class KeyResult < ApplicationRecord
  # 연계된 하위 목표
  has_many :child_objectives,
           -> { where(stage: Objective::ACTIVE + Objective::CLOSED).kept },
           class_name: :Objective, foreign_key: :super_key_result_id

  # 연계된 하위 핵심성과
  has_many :child_key_results,
           -> { where(active: true) },
           class_name: :KeyResult, foreign_key: :super_key_result_id
end

자세히 보면 조건이 다르다. 위쪽은 목표의 stage와 삭제 여부를 보는데, 아래쪽은 핵심성과 자신의 active만 본다. 그 핵심성과가 어떤 목표에 속했고 그 목표가 살아 있는지는 조건에 없다.

왜 이게 문제가 되나 — 삭제가 부모 쪽에서만 일어난다

조건이 다르다고 무조건 문제는 아니다. 핵심성과를 삭제할 때 active가 항상 내려간다면 결과적으로 같을 수도 있다. 그래서 삭제 코드를 확인했다. 

# 목표 삭제 — stage만 바꾼다
def archive_and_create_history(current_user_id)
  update!(stage: :archived)
  create_history('Archived', current_user_id)
end

# active: false로 내리는 곳은 임시저장 삭제 하나뿐이었다
def temp_discard
  key_results.update_all(active: false, super_key_result_id: nil)
  ...
end

목표를 삭제해도 그 목표에 속한 핵심성과의 active는 그대로 true다. 그래서 결과가 갈린다.

목표를 삭제
stage: :archived
→
child_objectives
제외됨 ✓
→
child_key_results
그대로 포함 ✗

그대로 썼다면 삭제된 목표의 핵심성과가 평균의 분모에 들어간다. 분모가 부풀려지니 상위 값이 실제보다 낮게 나오고, 눈에 잘 안 띈다. 값이 틀린 게 아니라 조금 낮을 뿐이라서.

프론트로 치면 items.filter(i => !i.deleted)로 걸렀는데, 정작 삭제는 아이템이 아니라 그 아이템이 담긴 폴더에 표시되는 구조인 것과 같다. 필터는 정상 동작하고 있고, 보는 곳이 틀렸을 뿐이다.

이미 알려진 문제였다 — 다만 화면에서만 메우고 있었다

고치려고 코드를 뒤지다가 프론트 응답을 만드는 엔티티에서 이걸 발견했다. 

# Entities::Objectives::KeyResult::ShowEntity
object.child_key_results.select {|kr|
  kr.objective.stage.in?(Objective::ACTIVE + Objective::CLOSED) && !kr.objective.discarded?
}

정확히 같은 조건을 Ruby select로 덧대고 있었다. 즉 비대칭은 이미 알려져 있었고, 발견한 사람이 연관관계를 고치는 대신 자기 화면에서만 보정한 것이다.

이게 이 레슨의 핵심이다. 연관관계 자체를 안 고치면, 그 연관관계를 새로 쓰는 코드는 매번 같은 함정을 처음부터 다시 밟는다. 나는 운 좋게 계산 전에 발견했지만, 발견 못 했다면 조용히 틀린 분모로 몇 달을 갔을 것이다.

고치기 — joins로 부모 조건까지 SQL에 넣는다

has_many :reflect_source_key_results,
         lambda {
           unscope(:order)
             .joins(:objective)
             .where(active: true,
                    objective: { stage: Objective::ACTIVE + Objective::CLOSED, deleted_at: nil })
         },
         class_name: :KeyResult, foreign_key: :super_key_result_id,
         inverse_of: :super_key_result

두 가지를 짚어둔다.

  • joins의 where 조건에는 .kept(Discard gem의 스코프)를 직접 못 쓴다. 그건 Objective에 걸리는 스코프지 조인 조건이 아니다. 그래서 deleted_at: nil로 같은 정책을 손으로 표현해야 한다 — Discard 설정이 바뀌면 이쪽도 같이 고쳐야 하는 결합이 생긴다. 주석으로 남겼다.
  • unscope(:order)가 필요했다. KeyResult에 default_scope { order(:position) }가 걸려 있어서, 정렬이 필요 없는 집계 쿼리에 불필요한 ORDER BY가 따라붙는다.

Ruby select가 아니라 SQL로 거른 이유

엔티티는 Ruby select로 걸렀는데 나는 SQL로 걸렀다. 어느 쪽이 맞는 게 아니라 쓰임이 다르면 답이 다르다.

이건 레슨 9· 레슨 49에서 본 것과 이어진다. 이미 includes로 로드해둔 컬렉션을 다시 where로 필터링하면 새 쿼리가 나가고, 반대로 로드할 이유가 없는데 전부 불러와서 Ruby로 세면 메모리를 낭비한다. "이 데이터를 왜 가져오는가"가 필터 위치를 정한다.

기존 연관관계를 고치지 않고 새로 만든 이유

child_key_results를 직접 고칠 수도 있었다. 그러지 않은 이유는 두 가지다.

  • 영향 범위. 그 연관관계는 시리얼라이저·엔티티 등 화면 노출에도 쓰인다. 조건을 바꾸면 응답이 바뀌는 API가 여러 개다.
  • 계산이 표시에 끌려가지 않게. 화면 요구는 바뀐다. "삭제된 것도 회색으로 보여달라"는 요청 하나에 조건이 바뀌면, 그 순간 반영값 계산이 조용히 함께 바뀐다. 계산의 입력을 표시용 연관관계에 묶어두면 안 된다.

그래서 reflect_source_objectives / reflect_source_key_results라는 전용 연관관계를 새로 뒀다. 목표 쪽은 조건이 child_objectives와 같아서 중복처럼 보이지만, 중복을 감수하고 분리했다. 이름이 용도를 말해주면 나중에 조건을 바꿀 때 "이건 반영 계산용이구나"가 바로 보인다.
