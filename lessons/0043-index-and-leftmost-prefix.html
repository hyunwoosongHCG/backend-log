인덱스란 무엇인가 — 그리고 복합 인덱스의 Leftmost-Prefix 규칙

레슨 043 Index · Composite Index · Leftmost-Prefix ~15분
🎯 레슨 42(데드락)에서 남긴 질문 — "with_lock 안의 update_all이 왜 하필 넓은 범위를 잠갔나"에 대한 답 — MISSION.md

출발점 — 인덱스가 없는 컬럼으로 조회하면?

레슨 42에서 본 데드락의 진짜 원인은 이 한 줄이었다. 

# app/services/objective_approve_update.rb:78
KeyResult.where(super_key_result_id: value[:prev][:id]).update_all(super_key_result_id: nil)

이 쿼리가 "행 몇 개만 딱 짚어서" 잠그면 문제가 없다. 그런데 실제로는 key_results 테이블을 훨씬 넓게 훑으면서 잠갔다 — 그 이유가 인덱스에 있다.

인덱스(Index)란 무엇인가

테이블에 인덱스가 없으면, 조건에 맞는 행을 찾기 위해 DB는 모든 행을 처음부터 끝까지 확인해야 한다 — 이걸 풀 테이블 스캔(Full Table Scan)이라고 한다. 행이 100만 개면 100만 개를 다 본다.

JS로 치면 array.find(x => x.id === target)과 map.get(target)의 차이다. Array#find는 조건에 맞는 게 나올 때까지 앞에서부터 순서대로 본다 — O(n). Map#get은 내부적으로 해시 구조를 이용해 바로 그 위치로 찾아간다 — O(1)에 가깝다. 인덱스는 DB 버전의 Map/해시 구조다 — 특정 컬럼 값으로 "이 값은 어느 행에 있다"를 미리 정렬된 자료구조(보통 B-Tree)로 만들어두고, 조회할 때 그 구조를 타고 바로 찾아간다.

대가는 있다 — 인덱스도 데이터이므로 저장 공간을 차지하고, 데이터가 바뀔 때마다(INSERT, UPDATE, DELETE) 인덱스도 같이 갱신해야 해서 쓰기 성능이 조금 느려진다. 그래서 "자주 WHERE/JOIN/ORDER BY에 쓰이는 컬럼"에만 선별적으로 건다.

복합 인덱스(Composite Index)와 컬럼 순서

key_results 테이블의 실제 스키마를 보자. 

# db/schema.rb:1685
t.index ["active", "super_key_result_id"], name: "child_key_result_index"

이건 active 컬럼과 super_key_result_id 컬럼을 이 순서 그대로 묶어서 만든 복합 인덱스다. 책의 색인(index)에 비유하면, "가나다순으로 첫 글자 → 둘째 글자" 순서로 정렬된 것과 같다 — 첫 글자를 모르는 채 둘째 글자만으로 책을 뒤지면 색인을 제대로 활용할 수 없다.

Leftmost-Prefix 규칙

복합 인덱스 (A, B)는 A로 시작하는 조회에서만 온전히 활용된다. 이걸 leftmost-prefix(최좌측 접두사) 규칙이라 부른다.

쿼리 조건 인덱스 (active, super_key_result_id) 활용?
WHERE active = true ✅ 가능 — 맨 앞 컬럼(A)만 써도 leftmost prefix
WHERE active = true AND super_key_result_id = 5 ✅ 가능 — (A, B) 둘 다 순서대로 사용
WHERE super_key_result_id = 5 ← 우리 코드 ⚠️ 비효율적 — 맨 앞 컬럼(A) 없이 B만 쓰면 이 인덱스로 바로 찾아갈 수 없다

KeyResult.where(super_key_result_id: value[:prev][:id])는 active 조건이 없다. 색인의 "둘째 글자"만 들고 책을 뒤지는 것과 같아서, MySQL은 이 인덱스를 깔끔하게 타지 못하고 훨씬 많은 행(최악의 경우 테이블 전체)을 훑어야 한다. 그 과정에서 UPDATE가 잠그는 행(과 인덱스 갭)도 함께 넓어진다 — 이게 레슨 42에서 본 데드락의 락 범위가 넓어진 진짜 이유다.

TypeScript 타입으로 억지로 비유하면, 복합 인덱스는 중첩 객체 키 순서와 비슷하다. { [active: string]: { [superKeyResultId: number]: Row[] } } 구조가 있다고 하자. data['true']는 바로 꺼낼 수 있지만, "active 값에 상관없이 superKeyResultId가 5인 것만 다 찾아줘"는 바깥 키를 모르니 모든 active 값을 순회하며 안쪽을 뒤져야 한다 — 정확히 같은 비대칭이다.

반대로 objectives 테이블은 어떨까. 

# db/schema.rb:2273
t.index ["super_key_result_id"], name: "index_objectives_on_super_key_result_id"

여긴 super_key_result_id 단독 인덱스가 따로 있다. 그래서 같은 서비스 코드의 Objective.where(super_key_result_id: ...).update_all(...)은 key_results 쪽보다 훨씬 좁게 잠긴다 — 같은 패턴의 코드인데 테이블마다 안전도가 다르다는 뜻이다.
