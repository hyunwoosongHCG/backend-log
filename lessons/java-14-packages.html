핵심 한 줄

패키지(package)는 관련 있는 클래스를 묶는 폴더다. 폴더 이름이 점(.)으로 이어져 있어서 a.b가 a의 하위처럼 보이지만, 자바에게는 이름이 다르면 그냥 완전히 다른 패키지다 — 부모·자식 관계 같은 건 없다.

왜 필요한가 — 이름이 겹친다

클래스가 몇 개뿐일 때는 이름이 안 겹친다. 그런데 여러 사람이, 또는 여러 라이브러리가 각자 User라는 클래스를 만들었다고 하자. 한 프로젝트 안에 User가 둘 있으면 자바는 어느 것을 말하는지 알 수 없다. 패키지는 이 충돌을 이름공간(namespace)으로 분리한다. 

package pack.a;

public class User {
    // pack.a 소속 User
}
package pack.b;

public class User {
    // pack.b 소속 User — 이름은 같지만 완전히 다른 클래스
}

클래스 파일 맨 위에 쓰는 package pack.a;가 "이 클래스는 pack.a라는 묶음에 속한다"는 선언이다. 이제 두 User는 pack.a.User와 pack.b.User라는 서로 다른 이름이 되어 공존할 수 있다.

계층처럼 보이지만 — 사실은 전부 남남

pack, pack.a, pack.b는 점으로 이어져 있어서 마치 pack이 부모고 pack.a·pack.b가 그 자식처럼 보인다. 하지만 자바에게는 셋 다 완전히 다른, 서로 무관한 패키지다. pack.a 안에 있다고 해서 pack에 있는 것에 자동으로 접근할 수 있는 것도 아니고, pack.a와 pack.b가 형제라서 서로 뭔가를 공유하는 것도 아니다. 이름이 계층처럼 생긴 것뿐이지, 실제 관계는 폴더 경로 이상도 이하도 아니다.

import와 완전한 이름

다른 패키지의 클래스를 쓰려면 완전한 이름(FQCN, Fully Qualified Class Name)을 쓰거나, import로 미리 알려두고 짧은 이름만 써야 한다. 

import pack.a.User;   // 이 클래스 하나만 짧게 쓰겠다는 선언
// import pack.a.*;   // pack.a 안의 클래스 전부를 짧게 쓰겠다는 선언(와일드카드)

public class Main {
    public static void main(String[] args) {
        User userA = new User();                    // import 덕분에 짧게
        pack.b.User userB = new pack.b.User();       // import 안 했으면 완전한 이름으로
    }
}

pack.a.User만 import했으므로 User라고 쓰면 그쪽을 가리킨다. pack.b.User는 import하지 않았으니 pack.b.User라고 전체 경로를 다 써야 컴파일러가 어느 User인지 알 수 있다. 이름이 겹치는 두 클래스를 한 파일에서 동시에 쓸 때 이렇게 "하나는 짧게, 나머지는 완전한 이름으로" 구분한다.

패키지 이름 = 폴더 위치

패키지 이름과 실제 디렉터리 구조는 반드시 같아야 한다. package pack.a;라고 쓴 파일은 실제로 pack/a/ 폴더 안에 있어야 한다 — 관례가 아니라 컴파일러가 강제하는 규칙이다. 명명 규칙은 두 가지다: 전부 소문자를 쓰고, 회사 도메인을 거꾸로 적는다 (예: hcg.com → com.hcg). 전 세계 누구와도 이름이 안 겹치게 하려는 관례다.

TS/JS의 import { User } from './pack/b/User'도 파일 경로로 모듈을 찾는다는 점은 비슷하다. 다른 점은, JS는 import 경로가 상대 경로·별칭(alias) 등으로 자유롭고 "모듈 이름"이라는 게 따로 강제되지 않는다. 자바는 패키지 이름 자체가 곧 폴더 경로이고, 그 일치를 컴파일러가 검사한다. Ruby의 module은 이름공간을 만들지만 파일 위치와 강제로 묶이지 않는다 (관례일 뿐, require로 아무 경로나 불러올 수 있다). 자바만 "이름 = 위치"를 규칙으로 못 박는다.

패키지 선언을 아예 안 하면 — 이름 없는 패키지

package 문을 안 쓰면 클래스가 소속 없이 떠 있는 게 아니라, 이름 없는 패키지(unnamed package)에 속하게 된다. 그런데 자바 언어 자체가 이름 있는 패키지에서는 이름 없는 패키지의 클래스를 import할 수 없다고 못 박아뒀다 — 컴파일러 설정 문제가 아니라 언어 사양이다. 

// Foo.java — 패키지 선언이 아예 없다
public class Foo {
}
package pack.a;

import Foo;   // ❌ 컴파일 에러 — 이름 없는 패키지에서는 import 자체가 불가능하다

이유는 지금까지 배운 것의 자연스러운 결과다. 다른 패키지 클래스를 쓰려면 pack.b.User처럼 완전한 이름이 있어야 했다. 그런데 이름 없는 패키지는 애초에 앞에 붙일 이름 자체가 없다 — 참조할 완전한 이름을 만들 방법이 원천적으로 없으니 import가 막히는 게 당연한 결과다. (이름 없는 패키지 안에서만은 서로 볼 수 있다 — 문제는 오직 "이름 있는 패키지 ↔ 이름 없는 패키지" 경계를 넘을 때다.)

그래서 실무에서는 패키지 선언 없는 클래스를 절대 안 쓴다 — 만드는 순간 어떤 이름 있는 패키지에서도 못 가져다 쓰는 "고립된 섬"이 되기 때문이다. IDE가 패키지 없이 클래스를 만들면 바로 경고를 띄우는 이유이기도 하다.

이름이 같아서 헷갈리기 쉬운 것 하나 — java-15의 default 접근 제어자(필드·메서드에 아무것도 안 붙이면 같은 패키지 안에서만 열리는 것)와, 지금 이야기한 "이름 없는 패키지"는 완전히 다른 개념인데 우연히 둘 다 "default"라고 부른다. 하나는 접근 범위고, 하나는 패키지 자체가 없는 상태다. 섞어서 기억하면 나중에 꼬인다.

뿌에서는 이렇게 보인다

스프링 부트 프로젝트에서 흔히 쓰는 계층형 패키지 구조는 이런 식이다. 

com.hcg.ppu.domain        // 엔티티 (Listing, Member ...)
com.hcg.ppu.repository    // JPA 리포지토리
com.hcg.ppu.service        // 서비스 계층
com.hcg.ppu.controller    // API 엔드포인트

Listing과 ListingController가 이름은 겹치지 않지만, 패키지를 계층별로 나눠두면 "이 클래스가 무슨 역할인지"가 위치만 보고도 드러난다. Rails의 app/models, app/controllers 디렉터리 분리와 하는 일은 같다 — 다만 Rails는 파일 위치가 관례일 뿐이고, 자바는 그 위치가 package 선언과 정확히 일치해야 하는 컴파일 규칙이라는 점이 다르다.

한 줄로 남기면

패키지는 이름이 겹치지 않게 클래스를 묶는 폴더이자 이름공간이다. 점으로 이어진 이름이 계층처럼 보여도 패키지끼리는 서로 아무 관계가 없고, 이름과 실제 폴더 위치가 어긋나면 아예 컴파일이 안 된다. java-10에서 본 study_class1.Student@...의 study_class1.이 바로 이 규칙의 결과였다 — 모든 클래스는, 이름을 안 정해도, 사실 어떤 패키지엔가는 반드시 속해 있다.
